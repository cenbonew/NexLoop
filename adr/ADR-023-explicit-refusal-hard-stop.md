# ADR-023｜明确拒绝联系的硬性停发

状态：**采用**（负责人 2026-10-10 确认）。
关联：docs/handoff/docs/02_ARCHITECTURE.md §7（实时与后台分层：关键拒绝联系先进入保护性检查）；14_TEST_ACCEPTANCE.md（“无明确拒绝被忽略”）；NX-022（控制面与派发检查）、NX-025（闭环验收，缺口 G2）、NX-028（负责人工作台）。

## 1. 背景

客户说“别再联系我”之类的话，后台提取会得到 `epistemic_kind=constraint` 的 Claim；匹配可能把它写进 Consumer 属性，v6 上下文也会把它钉住并标为联系限制。但在 NX-025 审核时发现：外发在派发时没有任何检查读取这一状态。现在能拦住外发的，只有负责人手动设置的 consumer 级暂停。

所以，模型只要忽略上下文，或者后台提取有延迟，外发就会照常发生。这不符合架构文档 §7 的要求（关键拒绝先进入保护性检查，不能让后台提取的延迟变成可以忽略拒绝），也不符合验收文档“无明确拒绝被忽略”的不可变条件。

## 2. 决定

1. **入站即检查。** 入站消息在持久化的同一事务里，做一次确定性的保护性检查，用规则识别“拒绝联系”。规则沿用并扩展现有的守卫规则，不调用模型。
2. **命中即限制。** 命中后，在同一事务里，通过 NX-022 控制面的内部函数，为该 consumer 写入一条联系限制控制，并推进控制 revision。这条控制与消息原文、命中规则一起留证。
3. **派发时拒绝。** 已有的 `nexloop_assert_dispatch_controls` 在派发时读取这条控制并拒绝：意图不派发，provider 收到零请求。不新增派发路径。已经排队的旧意图同样在派发时被拒。
4. **只有负责人能解除。** 解除是受治理的人类 Action，留证。Agent、Run、服务主体都不能解除，后台提取或模型输出也不能自动解除。
5. **后台提取只补证据。** 之后后台提取得到的 constraint Claim 只作为补充证据，不能取消或弱化入站时写下的限制。
6. **受限期间可以回复客户本次来信**（负责人 2026-10-10 补充）。联系限制只挡主动外发；对客户主动发来的某一条消息，允许回复：
   - 回复意图必须绑定它所回复的那条入站消息（`reply_to_message_id`），并且来自同一会话、同一 consumer；
   - 每条入站消息至多对应一条回复，只能在入站后的有限时间窗内派发（时间窗可配置）；
   - 派发检查在读取联系限制时识别这种绑定：绑定有效就放行，否则照旧拒绝。不绑定入站消息的外发、跟进、营销、复评计划发起的触达，一律拒绝；
   - 回复不会解除或弱化联系限制。
7. **客户主动发来的消息一定要回复**（兜底，负责人 2026-10-10 补充；适用于所有客户，不限于受限客户）。
   - 每条客户主动发来、已受理的入站消息，登记一项“待回复”；任何绑定这条消息、已被渠道接受的回复都会把它结清。
   - 时间窗到期仍未结清（Agent 没有回复、判断不行动、Run 失败或回复被拒），系统启动一个**兜底回复 Run，由 LLM 生成回复，不使用写死的模板**（负责人 2026-10-10 明确）：
     - 使用 v6 上下文，内容包括这条来信、会话近况，以及该客户的联系限制等钉住约束；
     - 只开放一个工具：发送一条绑定这条来信的回复（第 6 条的绑定约束同样适用），不开放其他工具，也不能发起新的触达；
     - 预算小且固定（模型轮数、工具次数、时长），写在版本化的部署配置里；
     - 生成的回复照常经受治理 Action 和派发检查发出。客户处于联系限制时，回复只能回应本次来信，不得继续推销或约定后续联系。
   - 兜底回复 Run 也失败时（模型不可用或超时、回复被拒、渠道故障），升级给负责人处理，留证，不静默丢弃；不退回写死的模板。
   - 时间窗与兜底 Run 的预算写在版本化的部署配置里。
   - 兜底只保证“有回复”，不改变授权：不能借此主动发起新的触达。

## 3. 后果与约束

- **误判**：规则可能把正常语句误判为拒绝，从而挡住正常联系。为此：
  - 规则版本化、可审计，命中时记录规则版本和原文片段；
  - 负责人必须能看到被限制的客户及原因，并能解除。这个入口属于 NX-028（负责人工作台），在它完成之前，至少提供受治理的解除 Action 与查询端口；
  - 宁可多挡：识别不确定时按限制处理（与 §7“关键保护状态未能确认时限制相关触达”一致）。
- **范围**：只影响主动外发和 Agent 外发；客户自己发来消息时，入站处理照常，不丢消息，并按第 6、7 条回复本次来信。
- **不触达客户的服务交付照常执行**（负责人 2026-10-10 确认，来自 NX-026 设计 D6）：联系限制只挡会触达该客户的外发 effect（消息、通知、外呼等各渠道）。不触达客户的服务交付 effect（例如后台处理退款、内部履约操作）照常派发；其中如果附带对客户的通知，通知部分仍受联系限制，按第 6 条处理。effect 是否触达客户由 Action 定义中声明的 effect 类别判定，未声明的一律按“触达客户”处理（宁可多挡）。最初实现（迁移 0109）对受限客户的全部 effect 都拒绝，按本条在 NX-026 中调整。
- **与 AT-029（不行动）的关系**：AT-029 说的是“不为完成 KR 而主动发消息”，针对主动触达；第 7 条针对客户主动发来的消息，两者不冲突。复评计划判断“不行动”时，不会触发兜底回复。
- **测试**：NX-025 的 E2E-C 第 1 步作为验收：确定性脚本故意让 Pi 仍然尝试主动外发，派发必须拒绝，provider 收到零请求。另需覆盖：
  - 规则的正例、反例与误判负例集，以及“只有负责人能解除”的负例；
  - 受限客户发来消息后，绑定该消息的一条回复能派发；第二条回复、不绑定的外发、绑定别人的消息、时间窗外的回复都被拒；
  - 兜底：Agent 不回复或判断不行动时，到期启动兜底回复 Run，并由 LLM 生成、发出一条绑定来信的回复（测试中用确定性 provider）；已有回复时不启动兜底；兜底 Run 只有一个发送工具，试图调用其他工具或发起不绑定的外发都被拒；兜底 Run 失败时升级给负责人。
- 实现由 NX-025 内的一个小切片完成（L2 线）。

## 4. 修订：拒绝规则 v2，营销之后的“退订”只停营销（负责人 2026-10-20 选方案 B）

负责人原话：“拒绝规则 v2 选 B”。方案对比和推荐理由见 `docs/implementation/outreach-impl-plan.md` §7。

**决定**：
- 拒绝规则 v2（`deploy/configuration/contact-refusal-rules.v2.json`）保留 v1 的全部条目和顺序，只增加一个窄例外：条目 `unsubscribe`（退订、取消订阅、unsubscribe）和 `sms-stop-keyword`（整句 TD 或 stop），在**最近一条已派发的主动消息是营销、且在 30 天内**时，只停营销。
  - “只停营销”的做法是写入营销退订记录，留下消息、规则版本和条目、它回应的那条营销发送，不写联系限制。
  - 判断与入站消息的持久化在同一事务内完成。
- 不满足这个条件时（窗口外、最近一条不是营销、或者从未发过营销），这两个条目照旧写联系限制，全部停发。
- 其他拒绝条目和全部 uncertain 条目始终全部停发。v1 的 `unsubscribe` 条目原来也包括拉黑、屏蔽你们、删除我的号码，这些拆到 `block-or-erase`，始终全部停发。
- 同一条消息里，只要还命中任何一条全部停发的条目，就全部停发。例如“退订，别再联系我”：全停条目优先，不会同时出现“只停营销”。
- v1 仍然保留，规则只追加，不修改。从 v1 切换到 v2 记录在 `control.nexloop_contact_refusal_rule_switches`（迁移 0244），每次命中都记录规则版本。

**风险**：
- 这是对一条保护性规则的放宽。客户如果其实想全部停止，营销会停，但服务类触达（预约提醒、工单结果）还会继续。
- 判断“最近一条是营销”时，以已派发或结果未知的外联发送为准，窗口按派发准入时间计算。判断出错的后果是少拦，所以测试覆盖了窗口外、非营销、混合说法和无营销四种情况。

**客户想全部停止时**：再说一次任何全停说法即可，例如“别联系我”“不要再发了”“拉黑”。系统照 §2 写联系限制，只有负责人能解除。

**两处细节，负责人 2026-10-20 按推荐确认**（原话：“拒绝规则细节按推荐”）：
- “取消订阅”“unsubscribe”与“退订”“TD”“stop”同属这个窄例外：营销后 30 天内只停营销。
- 营销后 30 天内，“怎么退订”“如何退订”这类问句也按只停营销处理，**不加问句排除项**。这是有意为之：问句与真正的退订在这个窗口里难以区分；只停营销的代价小；而 v1 对同一句话是全部停发。

§2.6（受限期间只能回复本次来信）和 §2.7（来信必有回复）不变。只停营销的客户没有联系限制，服务类外发照常经全部派发闸门。
