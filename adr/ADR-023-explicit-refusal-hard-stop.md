# ADR-023｜明确拒绝联系的硬性停发

状态：**采用**（负责人 2026-10-10 确认）。
关联：docs/handoff/docs/02_ARCHITECTURE.md §7（实时与后台分层：关键拒绝联系先进入保护性检查）；14_TEST_ACCEPTANCE.md（“无明确拒绝被忽略”）；NX-022（控制面与派发检查）、NX-025（闭环验收，缺口 G2）、NX-028（负责人工作台）。

## 1. 背景

客户说“别再联系我”之类的话，后台提取会得到 `epistemic_kind=constraint` 的 Claim；匹配可能把它写进 Consumer 属性，v6 上下文也会把它钉住并标为联系限制。但在 NX-025 审核时发现：外发在派发时没有任何检查读取这一状态。现在能拦住外发的，只有负责人手动设置的 consumer 级暂停。

所以，模型只要忽略上下文，或者后台提取有延迟，外发就会照常发生。这不符合架构文档 §7 的要求（关键拒绝先进入保护性检查，不能让后台提取的延迟变成可以忽略拒绝），也不符合验收文档“无明确拒绝被忽略”的不可变条件。

## 2. 决定

1. **入站即检查。** 入站消息在持久化的同一事务里，做一次确定性的保护性检查，用规则识别“拒绝联系”。规则沿用并扩展现有的守卫规则，不调用模型。
2. **命中即限制。** 命中后，在同一事务里，通过 NX-022 控制面的内部函数，为该 consumer 写入一条联系限制控制，并推进控制 revision。这条控制与消息原文、命中规则一起留证。
3. **派发时拒绝。** 已有的 `nexloop_assert_dispatch_controls` 在派发时读取这条控制并拒绝：意图不派发，provider 收到零请求。不新增派发路径。已经排队的旧意图同样在派发时被拒。
4. **只有负责人能解除。** 解除是受治理的人类 Action，留证。Agent、Run、服务主体都不能解除，后台提取或模型输出也不能自动解除。
5. **后台提取只补证据。** 之后后台提取得到的 constraint Claim 只作为补充证据，不能取消或弱化入站时写下的限制。

## 3. 后果与约束

- **误判**：规则可能把正常语句误判为拒绝，从而挡住正常联系。为此：
  - 规则版本化、可审计，命中时记录规则版本和原文片段；
  - 负责人必须能看到被限制的客户及原因，并能解除。这个入口属于 NX-028（负责人工作台），在它完成之前，至少提供受治理的解除 Action 与查询端口；
  - 宁可多挡：识别不确定时按限制处理（与 §7“关键保护状态未能确认时限制相关触达”一致）。
- **范围**：只影响主动外发和 Agent 外发；客户自己发来消息时，入站处理照常，不丢消息。是否允许在受限状态下回复客户本次来信，由负责人在 NX-028 中另定；在那之前一律按受限处理。
- **测试**：NX-025 的 E2E-C 第 1 步作为验收：确定性脚本故意让 Pi 仍然尝试外发，派发必须拒绝，provider 收到零请求；另有规则正例、反例与误判的负例集，以及“只有负责人能解除”的负例。
- 实现由 NX-025 内的一个小切片完成（L2 线）。
