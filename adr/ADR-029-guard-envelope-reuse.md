# ADR-029｜guard 在同一 Run 的多次授权间复用 Source 签名的上下文信封

状态：**采用**（Accepted）。决策人：负责人，2026-10-12，原话“按推荐，附条件批准 ADR-029”。实现在分支 `guard-envelope-reuse`（自 main b1b3418），临时迁移 0420。

关联：AGENTS.md“派发时按当前权限复查”；ADR-022 §4（guard 单次调用 2 s 时限）；ADR-024（guard 多进程）；ADR-027、ADR-028；调度员 2026-10-12 对 guard-authz-memo 的约束（备忘只限一次授权或同一事务，不跨请求）——本 ADR 提议对**签名信封**放宽这条约束，因此需要负责人裁定。

## 1. 背景

AT-060 阶梯在 CI 主机上正确性已干净（100/200 客户 0 失败），瓶颈是吞吐：历史回复约 0.2/s，外推 1000 客户需 2.4–2.9 h。目标是翻倍到 ≥0.4/s。

实测（本机，main a58c42b + history-monitor）：

- 200 客户模板，pg_stat_statements：每次 guard 授权的 SQL（`nexloop_runtime_activation_command`）平均约 36 ms，约 4150 条嵌套语句；最重的是权威事实主键查询（每次授权约 295 + 197 次，单次约 0.06 ms）、grants 存在性检查、凭据与身份相关读取。单条都很便宜，代价来自次数。
- 但 history-monitor 读到的 guard 每次授权 p50 约 170 ms（100 客户），远大于 36 ms 的 SQL。cProfile（一次 model 授权，单进程无并发）：**每次约 214 ms，其中约 146 ms（68%）在构建服务目录信封**（`_context_catalog_envelope` → `service_offerings` → `object_reads` → 事实解析，每次授权 2 次），其余主要是角色、关系与正式读取信封和事实规范化（`facts._canonical_value`，每次授权约 4 万次递归调用、约 57 ms 纯 CPU）。
- 这些信封由 Source 身份签名、带不超过约 25 s 的有效期；SQL 在每次使用时按**当前**权威数据重新校验（记录摘要、目录摘要、授权事实）。目前同一信封只在一次 guard 工具请求内复用（`scoped_envelope`），跨授权每次都重建。

## 2. 决定

1. guard 进程对**同一 Run** 的 Source 签名上下文信封（服务目录、角色、关系、正式读取）做进程内复用：键为（Run 的来源摘要、上下文定义的规范摘要、信封种类），只在信封自身签名的有效期内复用，并留出安全余量（例如剩余有效期 < 5 s 即重建）。
2. **SQL 的每次使用校验完全不变**：复用的只是“由 Python 构建并签名的证明”，SQL 照旧按当前事实、记录摘要与目录摘要验证；只要权威、对象或目录有任何变化，校验失败，这次授权即被拒绝，guard 丢弃该 Run 的缓存，下一次授权现场重建。一次授权只有一个结果，guard 内部不重试（锁等待中跨过的截止时间必须让这次授权失败）。
3. 缓存只在内存中、只按 Run 维度、有条目上限，进程重启即清空；从不跨 Run、跨租户或跨 world 共享；不缓存任何拒绝结果。
4. 不改变任何时限、授权范围、ADR-027/028 的复查组。

## 2a. 四类信封的 SQL 校验覆盖面（批准条件 1，实现前核对）

信封本身不带独立有效期；有效期由其中各读证明的 `expires_at` 决定，SQL 接受到“当前时间 + 30 s”（0015:120）。每次使用时 SQL 都重新执行完整的 READ 校验：签名密钥仍有效且 HMAC 相符；`read_object` 读取 `ontology.objects` 的**当前**行；`assert_read_authority` 复查凭据、主体、目录摘要（凭据行 + 租户 authority_revision 与 status）、每条权威事实的 record_hash 与租户行。Run 凭据的状态与到期由激活核心对每个命令复查（0037:96-97）。

| 信封 | SQL 校验位置 | 每次使用复查的当前状态 | 不与当前状态比对的部分 |
|---|---|---|---|
| 服务目录 | `nexloop_service_catalog_scope`（0053:51-97）、`nexloop_assert_service_offering`（0053:4-44），0110:149/154 | 签名、读证明到期、Source 身份与目录摘要、权威事实、ServiceOffering 当前修订等于请求修订（0053:27）、ConsumerServiceOffering 当前属性（0053:29-30）、条款与 `valid_until`（0053:31-41）、与绑定上下文包的 supply 相等（0110:150/155）、consumer 与命令一致（0110:151） | 不含 run_id（按 Source 与 consumer 绑定）；联系限制、消除（erasure）不在此检查 |
| 角色（含策略与角色 formal_reads） | `nexloop_role_run_current`/`_validate`（0063、0064）、策略 0081/0085、formal-current 0075 | 签名、Run 凭据有效（0063:59-62）、绑定含 run_id（0063:143/215，0085:15）、Link/Role/Step 当前修订等于绑定行（0063:100-104）、活动属性与时限、策略上限/预算当前值（0081:139-170、215）、正式对象修订（0075:89-94） | 联系限制不在此检查 |
| 关系 | `nexloop_relationship_context_snapshot`（0076:39-125）每次重建并须等于上下文包（0110:152/157），截止检查 0076:131-143 | 签名、读证明到期、凭据与目录摘要（0076:55-56、106-107）、权威事实、配方、评估的修订与当前值、陈述有效期、证据消息当前正文与成员 | 端点对象只复查读权限，不比较其修订与值（0076:64-69）；不含 run_id；联系限制不在此检查 |
| 正式读取 | `nexloop_context_formal_current`（0075:12-33），0110:159/164/166 | 签名、权威事实、身份、到期、对象种类与 id 等于上下文包、对象修订等于包内修订（0075:25）、EffectControl `valid_until` | 不含 run_id（由绑定包的对象 id 限定）；联系限制不在此检查 |

据此对批准条件 2 的结论（下一次授权使用仍在有效期内的复用信封）：

| 变化 | 目录 | 角色 | 关系 | 正式读取 |
|---|---|---|---|---|
| Source 权威撤销 / 租户权威修订变化 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |
| 对象/目录修订 | 拒绝 | 拒绝 | 拒绝（端点对象本身的修订除外，与新建信封相同） | 拒绝 |
| 联系限制生效 | 不在激活时检查 | 同左 | 同左 | 同左 |
| Run 凭据撤销 | 拒绝（激活核心） | 拒绝 | 拒绝（激活核心） | 拒绝（激活核心） |

联系限制在整条激活链中都不检查（新建信封同样如此），只在效应派发时由 `control.nexloop_contact_assert_intent`（0109、0112）执行，因此复用不改变这一点。复用只发生在同一 Run 内（缓存键含 Run 的摘要），因此目录与关系信封本身不含 run_id 不会造成跨 Run 复用。

核对中发现的问题（已在 0420 修复）：0171（ADR-027）与 0173（ADR-028）拒绝“携带上下文信封的 inspect / 收尾复查”的检查只看 payload，而 guard 把信封放在签名的 claims 中，这道防线从未生效；0420 让两个分支对 claims 中的信封同样拒绝。

## 2b. 实现

- `nexloop_eios/role_runs.py`：`run_envelope_scope(run_digest)`、`scoped_envelope` 在同一 Run 内按（Run 摘要, 信封键）复用；只缓存能读出所有读证明 `expires_at` 的信封；剩余有效期 < `RUN_ENVELOPE_MARGIN`（5 s）即重建；进程内存、条目上限 `RUN_ENVELOPE_LIMIT`（512，LRU）；构建失败不缓存。
- `runtime_activation.authorize`：在 Run 作用域内构建信封并授权；若用了复用的信封而 SQL 拒绝，这次授权照常报错，并丢弃该 Run 的全部缓存，下一次授权用新建的信封（实现初版曾在 guard 内重试一次，CI 的 `test_role_tail` 截止时间用例证明这会绕过“锁等待后截止复查”，已撤销）。
- inspect、收尾复查与效应工具请求内的复用（`request_envelope_scope`）不变。

## 3. 理由

- 撤销与变更的生效仍取决于 SQL 的每次校验，而不是信封是否新建：信封只是“Source 在某一时刻能读到这些内容”的签名证明，SQL 校验它在**当前**是否仍成立。复用一个仍在有效期内、且当前仍校验通过的证明，与现场新建一个内容相同的证明，在授权结果上等价。
- 风险在于：如果某项变化不体现在 SQL 校验的摘要里，复用会让旧证明多存活至多一个有效期（≤25 s）。实现前须逐一核对四类信封的 SQL 校验覆盖面，并以测试证明撤销、对象修订、目录变化、限制生效都会让复用的信封立即被拒。

## 4. 后果与验证

- 预期：每次授权的 Python 侧耗时从约 214 ms 降到约 70 ms 以下（只省去信封重建），按 guard 为瓶颈估算吞吐提升约 2 倍；以 200 客户模板 + history-monitor 实测为准，再到 CI 主机复测。
- 测试须覆盖：缓存命中时 SQL 仍逐次校验；权威撤销、对象/目录修订、联系限制、Run 凭据撤销后，下一次授权拒绝或重建（不得沿用旧证明通过）；有效期临近时重建；不同 Run 之间不共享。
- 另一项同语义的纯 CPU 优化（事实规范化，约 57 ms/次）在 vendored 的 EIOS 内核 `eios/authz/facts.py`，可以对冻结模型的规范摘要做实例级缓存或改写递归；它不改语义，但会扩大与上游的差异，单独提交、记录到 PROVENANCE。
- 被拒绝：直接加大 guard 进程数或连接池（受连接预算 60 的限制，且不解决单次授权的成本）；跨 Run 共享信封。
