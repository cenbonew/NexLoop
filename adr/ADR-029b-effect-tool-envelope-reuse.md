# ADR-029b｜效应工具请求在同一 Run 内复用 Source 签名的上下文信封

状态：**采用**（Accepted）。负责人 2026-10-26 同意方案 A。实现分支 `l2/v6-relationships-flake`。

修订对象：ADR-029 第 52 行。原文为“inspect、收尾复查与效应工具请求内的复用（`request_envelope_scope`）不变”，本 ADR 只把其中的效应工具请求改为下文的规则；inspect 与收尾复查不变。

关联：ADR-022 §4（guard 单次调用 2 s 时限）；ADR-028（结果不明确时再试一次）；ADR-029；调度员 2026-10-12 的约束“备忘只限一次授权或同一事务，不跨请求”。

## 1. 背景

- 用例 `test_v6_carries_v4_relationships_with_hypotheses_as_evidence_only` 在 CI 上偶发失败：第三十批 seq 119 一次，合并批 seq 133 一次；2026-10-12 也出现过。失败结果是 `runtime_failed`，具体为 `runtime_tool_error` / `nexloop.service.request`。
- 本机用 `taskpolicy -b` 降速后可以稳定复现（9 次全部失败）。原因是 guard 处理效应 submit 超过了 Host 的 2 s 效应时限，按 ADR-028 再试一次仍然超时。把时限临时调到 15 s 时，同样条件下 3 次全部通过；该改动只用于验证，已还原。
- 每次效应请求，guard 都在 `request_envelope_scope` 中从头重建 Context 信封。其中关系评估、正式事实和目录三类信封，在同一 Run 前面的授权（start、model）里已经生成过，并且已经按 ADR-029 缓存在该 Run 名下。
- 这不只是测试问题：生产环境负载高时同样可能超时。

## 2. 测量（guard 端计时，不含 profiler，单位 s）

| | 正常负载 submit | 降速 submit |
|---|---|---|
| 修改前 | 0.40–0.42 | 2.49 / 4.18 / 2.66 / 3.64（用例 9/9 失败） |
| 修改后 | 0.23–0.26 | 1.20–1.43（用例 3/3 通过，51–62 s） |

- 修改前，降速条件下各部分的耗时为：关系评估信封 0.56–0.83，目录信封 0.28–0.84，正式事实信封 0.15–0.22，guard/intent SQL 0.60–0.76，其余 0.7–1.5。
- 方案 B（只降低关系评估信封里的权限解析成本）的理论上限是降速条件下 1.9–3.4 s，未采用。
- 修改后，同一 Run 后面的 find 偶尔要 2.0–2.2 s：缓存的信封剩余有效期不足 5 s，于是重建。这符合 ADR-029 的规则。

## 3. 决定

1. **复用范围**：效应工具请求（`RuntimeActivationPort.effect_tool`）在 guard_before 之前，打开该 Run 的 `run_envelope_scope`，并限定信封种类为 `EFFECT_REUSE_KINDS`。限定的三类是：
   - 关系评估信封（`relationship`）；
   - 正式事实信封（`context_formal`）；
   - 目录信封（`catalog`）。

   负责人同意的放宽范围还包括 Context 读证明，但它在 ADR-029 中本来就不进入 Run 缓存，每次约 0.005 s，本次不缓存。
2. **其他种类不变**：角色信封、策略信封、正式读信封等，在效应请求中仍然只在本次请求内复用；即使该 Run 的缓存里有同键条目，也不会拿来用。
3. **复用规则与 ADR-029 相同**：
   - 只复用能读出全部 `expires_at` 的信封；
   - 剩余有效期不足 5 s（`RUN_ENVELOPE_MARGIN`）时重建；
   - 只放在进程内存里，按 Run 摘要分键，有条目上限，不缓存失败。
4. **SQL 照常复查**：SQL 每次使用信封时，都按当前权威数据重新校验签名、到期时间、记录摘要和授权事实，与对待新信封完全相同。guard_before 被拒，且这次请求用过 Run 缓存里的信封时，删除该 Run 的全部条目，下一次请求从头重建。一次请求只给一个答复，请求内不重试。因此在撤销权限或修订对象之后，第一次 submit 若用了 Run 缓存里的信封，一定被 SQL 拒绝，同时清空本 Run 的缓存，下一次请求从头重建。这是失败即拒绝，与 ADR-029 一致。
5. **权限决定备忘（O1）不变**：仍只在一次请求之内，不跨请求。调度员 2026-10-12 的约束只对“Source 签名、SQL 每次复查的上述三类信封”放宽。
6. **以下各项都不变**：2 s 时限（ADR-022 §4）；ADR-028 的再试一次；锁顺序（同一 Run 的 advisory 锁先于 guard，执行锁先于行锁）；授权范围；效应 intent 的写入；收尾复查（只复查激活核心，不带 Context 信封）。

## 3a. Host 端效应时限可配置（调度员 2026-10-26）

- 运行配置新增可选项 `effect_timeout_ms`。不填时仍是 2 s（`EFFECT_TIMEOUT_MS`），ADR-022 §4 的语义不变：每次效应请求一个时限，结果不明确时按 ADR-028 只再试一次。
- 填写时必须是 1000–5000 的整数，并且要求 `effect_tools: true`。**超出范围、类型不对，或没开效应工具时，Host 拒绝启动**（`runtime configuration refused`），不截到上限：配置写错要在启动时暴露，不能静默改成另一个值。
- 这个值只在 Host 端生效，不交给 Pi 侧；guard 端的时限不变。
- 诊断：效应请求以 `runtime_effect_unavailable` 结束时，Host 在 stderr 写一行 JSON：`{event:'runtime_effect_unavailable', run_id, operation, effect_timeout_ms, elapsed_ms}`。只有代码和数字，没有参数、消息正文或凭据。
- 按 p99 来定时限，以及后台提前刷新信封，都不在本 ADR 范围内，以后另写 ADR。

## 4. 验证

- `tests/test_effect_envelope_reuse_pg.py` 包含 5 个用例：
  1. 复用确实发生，且角色信封每次请求都重建；Run 缓存里放一个会被拒的角色信封，效应请求也不会使用它；
  2. 撤销 Source 读权限后，下一次效应请求被拒；
  3. ServiceOffering 修订后，下一次效应请求被拒，该 Run 的缓存被清空；
  4. 被 SQL 拒绝的复用信封会被清掉，下一次请求重建后成功；
  5. 单元检查：种类过滤只在请求作用域内生效。
- 变异验证：分别注入“被拒时不清缓存”“不限定种类”“请求内不查 Run 缓存”“关闭种类过滤”四个变异，每个都至少有一个用例失败。
- 回归：ADR-029 原有测试，以及所有涉及效应工具、角色和 Context 的测试，均通过。
- 补充用例：剩余有效期 4 s 时重建、6 s 时复用。把“剩余不足 5 s”的判断改成恒为真的变异会被这个用例抓住。
- Host 端：`apps/agent-host/test/effect-timeout-config.test.ts`，覆盖拒绝启动的六种配置、三个合法值、默认值与上下限，以及实际限时（不配置 2 s，配置 1 s、3 s）和诊断行。两个变异（请求仍用常量 2 s、去掉范围检查）都会被抓住。

## 5. 风险

- 撤权在下一次 SQL 校验时生效，SQL 每次都复查，所以撤权后的第一次请求就会被拒。风险与 ADR-029 相同。
- 进程内缓存在多进程 guard（ADR-024）中各进程独立，命中率较低，但正确性不受影响。
