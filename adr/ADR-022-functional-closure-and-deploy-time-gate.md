# ADR-022｜NX-018 功能收口与部署主机工具时限门槛

状态：**采用**（负责人 2026-10-09 确认）。
关联：ADR-020 §4（合并标准）、ADR-021 §2（AT-009 一次性例外与退出条件）；NX-018、AT-004、AT-009；新增 NX-049。

## 1. 背景

ADR-021 把 `tests/test_relationship_context_v4.py::test_real_human_message_v4_bound_artifact[complete]`（AT-009 的两 Pi 正向场景）登记为基线 B 类，退出条件是授权时延优化落地或 NX-018 完成 v4 之后，该用例必须通过。

之后落地的时延优化：O1（请求内决策去重）、O3（事实解析缓存）、O2a（身份事实每请求只加载一次）、O2b（服务目录与 Role 信封按对象批量判定）。实测结果：

- 开发机：该用例在 O1 之后单独与回归中多轮通过；O2b 之后本机 4 轮全部通过，authorize 最慢一次 1225–1517 ms。
- CI 测试机：integration-s3q（main `57a224c`）同一检出、主机空闲（load≈1）时串行 5 次，**0/5 通过**（`runtime_transport_unavailable` ×3、`runtime_failed` ×2）。全量 CI 中同样失败。

CI 测试机就是规划中的应用部署主机。因此这一差距不只是 CI 测试机的问题：在目标硬件上，该路径会在 2 s 工具时限下确定性失败。

## 2. 决定

1. **NX-018 按功能收口。** 功能正确性以开发机上的实测证据为准：Role N:M、关系更正进入新 Context、Role 权限上限与范围在绑定期和调度期强制、Message 与证据的读权限派生。AT-004 记为 passed。AT-009 记为 passed，并在证据中明确写明：依据是开发机证据，CI 测试机（部署主机）在 2 s 工具时限下 0/5，由第 3 项的门槛跟踪。
2. **不放宽 2 s 工具时限。** 不通过调大时限、跳过用例或改写断言来让部署主机通过。
3. **新增 NX-049「部署主机工具时限达标」**，作为 S5 部署前的硬门槛：
   - 验收：在部署主机（即 CI 测试机）上，`relationship_context_v4[complete]` 与两 Pi Role 用例在全量 CI 中连续 2 轮通过，且同一检出串行 5 次全部通过；时限保持 2 s。
   - 先行手段：O5b 级别 1（同一语句、同一阶段内的读断言去重；锁后尾验完整重跑；设计见 `docs/implementation/perf-o5b-design.md`）。级别 2（锁后尾验只复核时钟）不在本 ADR 授权范围内，需另立 ADR 并由负责人确认。
   - NX-032（双机 TLS 与隔离部署）及之后的部署任务依赖 NX-049。
4. **基线不变。** 该用例继续留在合并基线 B 类，直到 NX-049 达成后移除。ADR-021 §2 的一次性例外随本 ADR 结束，其退出条件由 NX-049 的验收取代。

## 3. 后果

- 依赖 NX-018 的任务不再被 NX-018 阻塞，但每个任务能否标 done，仍按其自身交付物与验收逐项判断，不因本 ADR 一并完成。
- 在 NX-049 达成之前，任何部署到部署主机的操作（B 类，本就需负责人确认）都不应启用依赖该路径的真实 Run。

## 4. 修订：NX-049 门槛的测量方式（负责人 2026-10-10 确认）

**背景。** NX-049 之后的优化（手段 8a/8b/8c、5、4a、同 Run 锁顺序修复、submit 路径 SQL 削减）与 ADR-024（guard 多进程，部署配置 4 个进程）落地后，部署主机上的实测：

| 场景（guard 4 进程） | v4[complete] | 两 Pi Role |
|---|---|---|
| 单独串行（累计 8 次） | 8/8 通过 | 8/8 通过 |
| 全量 CI（pytest 6 路并行，2 轮） | 0/2 | 2/2 通过 |

单进程时同一串行条件下为 4/6。全量 CI 让 6 路测试同时运行，同一台主机上并存几十个一次性数据库和 Agent 进程，负载远超部署要求的“Agent Host 全局并发 ≤ 4”。v4 只在这种负载下超时。

**决定。**
1. 2 s 工具时限不变。
2. NX-049 的门槛改为在**接近部署负载**的条件下测量：本地 CI 新增一个**串行时限阶段**，在并行阶段之前，以 guard 4 进程（`NEXLOOP_TEST_GUARD_WORKERS=4`）单独串行运行 `relationship_context_v4[complete]` 与两 Pi Role 用例，不与其他测试同时运行。
3. NX-049 验收：部署主机上，该串行时限阶段在连续两轮全量 CI 中都通过，且同一检出上两个用例单独串行各 5 次全部通过。
4. “生产 Agent Host 全局并发 ≤ 4、Runtime Worker 的 guard 为 4 个进程”是部署前提，写入部署说明，由部署 doctor 核对。生产并发要提高时，必须先在对应并发下重新测量本门槛。
5. 两个用例在全量并行阶段照常运行、照常记录；在那里失败时登记为负载敏感（合并基线 B 类），作为观察信号保留，不删除测试，也不作为 NX-049 是否达成的依据。

**后果。** 门槛不再证明“在远超部署并发的拥挤负载下也能在 2 s 内完成”，只证明“在部署并发下能完成”。这一前提由第 4 条的部署要求与 doctor 校验保证。
