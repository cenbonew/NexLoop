# ADR-028｜效应工具调用路径：收尾复查范围与超时后的同意图查询

状态：**采用**（Accepted）。决策人：负责人，2026-10-12，原话“按推荐，批准 ADR-028”。实现在分支 `effect-tool-path`（自 main 25312f7），临时迁移 0173。

关联：AGENTS.md“只有受治理的 EIOS Action 改变正式业务对象或产生外部效应”“未知外部结果先查询/对账，不盲目重试”“派发时按当前权限复查”；ADR-022 §4（guard 单次调用 2 s 时限）；ADR-027（inspect 授权的复查范围）；迁移 0040（效应意图）、0085（同 Run 工具调用锁）。

## 1. 背景

本机 1000 客户模板（main + ADR-027）在历史回复阶段：0 传输超时、0 死信、0 激活拒绝，但 36 个 Run 失败，全部是效应工具 `nexloop.service.request` / `nexloop.service.find` 报 `runtime_tool_unavailable`，每次 3–4 s 后放弃。

一次效应工具调用的组成（代码：`runtime_activation._effect_tool`；Host：`runtime-effect-tools.ts`）：

| 段 | 内容 | 200 客户实测（pg_stat_statements，本机 load≈9–14，偏悲观） |
|---|---|---|
| Host 授权 | Host 先对 `tool` 做一次完整 guard 授权 | 每次完整授权平均 37 ms（ADR-027 之后） |
| resolve | 激活链 resolve | 同上量级 |
| 同 Run 锁 | `nexloop-role-effect:<run>` advisory 锁 | 平均等待 15 ms |
| guard_before | 完整授权（含约 46 个读证明、上下文/角色/关系信封，信封由 Python 现场构建） | 平均 37 ms |
| intent | `nexloop_effect_intent_command`：提交或查询意图 | 平均 83 ms，最大 177 ms |
| guard_after | 再做一次完整授权（同一事务，意图写入之后） | 平均 37 ms |

即一次效应调用在 guard 侧约有 3 次完整授权加一次意图命令，Host 侧另有 1 次。1000 客户、本机满载时每次完整授权 p50 约 0.5 s、p95 约 1.4 s，于是整段越过 Host 效应客户端的 2 s 时限（`AbortSignal.timeout(2000)`），Host 报 `runtime_effect_unavailable`，工具失败，Run 失败。

效应意图在 0040 中按（客户、目标、步骤、槽位、动作）唯一：相同载荷重复提交返回已存意图（不新建、不重复预留额度），不同载荷报 `intent_payload_conflict`。

## 2. 决定

1. **guard_after 只做核心复查。** 同一事务内 guard_before 已完成完整授权（含全部上下文读证明）；意图写入后的收尾复查，用激活核心（ADR-027 的同一组复查：派发方凭据与队列授权、Run 凭据与 Run 证明、来源权威、租约与 fencing、Run 绑定、not_after）确认在可能的锁等待之后 Run 仍然有效，不再重复校验上下文信封。guard_before 不变，Host 侧对 `tool` 的授权不变。
   实现时保留一项直接的上下文检查：收尾时这个 Run 绑定的上下文工件（0052）必须仍可用、未被改动、仍在保留期内，否则拒绝并回滚整个事务。这样“写意图期间上下文工件过期即回滚”（`test_real_effect_intent_tail_artifact_expiry_rolls_back_every_write`）保持不变，而不必重建全部读证明。收尾复查只接受已有执行标记的 Run，拒绝任何上下文信封或模型数据，应答不带上下文。
2. **超时后的同意图查询。** Host 效应客户端在 `submit` 得到有歧义的结果（超时、连接错误、503）时，在 Run 自身的时限与预算内，用**完全相同的载荷**再提交一次。依据 0040 的唯一约束，这只能返回同一个意图（或冲突），不可能产生第二个效应或第二次额度预留，属于“先查询”。仍有歧义才报 `runtime_effect_unavailable`。`find` 本身是查询，同样最多再查一次。每次调用仍守 2 s 时限，ADR-022 §4 不变。
3. 不放宽任何时限，不改变效应语义、意图唯一性、额度预留或派发控制。

## 3. 理由

- 收尾复查要防的是“写意图期间租约丢失、Run 被作废或来源权威变化”，这些全在核心复查之内；上下文读证明在同一事务内刚刚完整验证过。去掉第二次上下文复查约省一次完整授权（约三分之一的 guard 侧成本）。
- 同意图再提交在语义上是查询：意图键由服务端从 Run 上下文推导，载荷相同即同一业务意图。比起让 Run 失败、交给回复保障兜底（再起一个 Run），它产生的外部动作更少。

## 4. 后果与验证

- 测试须覆盖：收尾复查在租约丢失、Run 凭据撤销、来源权威变化后仍拒绝并回滚意图与额度；上下文读证明在 guard_before 失效时仍拒绝；同载荷再提交返回同一意图且额度只预留一次；不同载荷仍报冲突；`find` 再查不改变状态。
- 200 客户模板对比每次效应调用的语句数与耗时；1000 客户模板对比失败码分布。
- 被拒绝：直接把效应客户端时限放宽到超过 2 s（违反 ADR-022 §4，且掩盖成本问题）；对 `submit` 做无界重试。
