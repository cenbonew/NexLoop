# ADR-020｜Message READ 派生、Agent 外发消息持久化、服务 Action 授权与合并标准

状态：**采用**（负责人 2026-10-09 确认）。
关联：ADR-019；迁移 0062（Message READ）；NX-018、NX-019、NX-020、NX-021；新增 NX-047、NX-048。

## 1. Source 对 Message 的 READ 由受治理事实派生（方案 B）

**背景。** 0062 要求 Source 主体在生成 Context 时对每条 `Message/<id>` 持有当前 READ。授权事实只由可信配置写入（0050），没有任何生产机制在消息被受理时发布对应的 resource graph 与 grant。测试通过可信配置手动写入 READ，因此 CI 曾经通过，但真实部署中 Message→Context 链路完全不可用。Codex 交接后的首次全量 CI 暴露出 21 个相关回归（Mac 与 CI 测试机均复现）。

**决定。** 不采用“只改测试夹具”的方案。新增迁移，使 Source 对 Message 的 READ 从受治理事实派生：

- 只覆盖该 Source 主体已受理（或由其会话/outbox 绑定产生）的消息，范围不超出这些消息。
- 租户、world 必须一致；派生同时要求 Source 主体当前授权有效。
- Source 撤权、消息删除或会话解除绑定时，派生的 READ 立即失效，不靠缓存。
- 只有本意就是测试可信配置的用例继续使用可信配置写入 READ。

**负向要求。** 他租户、他 world、未受理、已撤权、已删除的消息一律拒绝。

## 2. Agent 外发消息持久化为 Message

**决定。** Agent（含企业一侧的自动回复）发出的消息与顾客消息一样持久化为 Message 对象，带发送方身份（Agent/Role/人类接管者）、与外发 Action receipt 的关联和投递状态，但“已持久化”不等于“已送达”。

**理由。** 企业一方的承诺（`commitment` Claim）只能从企业发出的消息中提取；不持久化就无法追踪承诺与履约（M18），也无法让提取与审计覆盖完整对话。

**约束。** 草稿、未经 Action 核准的内容不得显示为已发送；第 1 节的 READ 派生规则同样适用于 Agent 发出的消息。

## 3. 服务 Action 与队列授权由调度员经可信配置授予

**决定。** 负责人授权调度员为 NexLoop 自身服务主体配置运行所需的 Action 与队列授权，例如 `eios:action:nexloop.claim.extract:1`、`eios:action:nexloop.claim.match:1`、`NexLoop.queue.claim-extraction`，以及后续同类服务授权。

**方式。** 授权写入必须走部署时的可信配置脚本（显式清单、可审计、可重放），不得直写授权表、不得使用超级用户运行时连接；清单随代码版本化。

**边界。** 该授权仅限 NexLoop 服务主体运行所需的最小 Action/队列权限，不包括人类主体权限、审核权限（`ontology.schema.review`）、真实外发渠道开通和 `REAL_DISPATCH_ENABLED`；这些仍需负责人本人确认。

## 4. 合并标准：相对基线不新增失败

**背景。** 在第 1 节修复落地前，main 的全量 CI 不可能全绿。

**决定。** 调度员审查通过、推送前扫描通过，且全量 CI 的失败集合相对当前已登记基线没有新增，即可合并 main。基线失败清单与分类（真实回归 / CI 测试机时限 / 并行负载抖动）随每次合并更新并保存。新增失败一律阻止合并；基线中的失败不得被重新归类来放行。

**退出条件。** 21 个回归修复后，标准恢复为“全量 CI 通过”；仅剩 CI 测试机时限类失败时单独评估时限设计，不靠放宽时限掩盖。

## 5. Embedding 维度

`EMBEDDING_DIMENSION=1024`（负责人已写入私有 `.env`）。方舟多模态端点只接受 1024 或 2048；pgvector `vector` 类型的 ANN 索引上限为 2000 维，1024 可直接建索引。维度一旦固定，索引不得静默变更。
