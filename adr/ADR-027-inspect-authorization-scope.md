# ADR-027｜inspect 授权的复查范围

状态：**提议**（草稿，待负责人裁定；调度员 2026-10-12 推荐方案 A 并给出约束）。实现在分支 `inspect-authz-scope`，未合入。

关联：AGENTS.md“派发时按当前权限复查”；ADR-022 §4（guard 单次调用 2 s 时限）；ADR-024（runtime guard 多进程）；迁移 0037–0039（激活核心）、0052 起各层（上下文工件、目录、角色、角色时限、正式数据、关系、角色策略、v6 绑定、模型请求、回复兜底）；临时迁移 0360。

## 1. 背景

NX-031 的 1000 客户模板在历史回复阶段停滞。排查结论：

- 每次 guard 授权在 200 客户时约 7100 条嵌套 SQL、约 60 ms CPU，其中约 46 次读证明、约 8 次动作证明复查。每次授权的调用次数在 25 和 200 客户时基本相同，问题不是“随数据量变慢”，而是“每次都很贵、次数多”。
- 次数最多的是 `inspect`：派发方在 Run 运行期间轮询 Run 状态，每次轮询都经过 Host 做一次完整授权，包括重新校验这个 Run 的全部上下文、关系和角色信封。
- 授权在 CPU 上排队，把 Host 请求推过派发方的时限，任务被放回队列而 Run 仍在 Host 上运行，随后这个 Run 的授权因租约失效被拒。

## 2. 决定（提议）

`inspect` 只读取 Run 在 Host 上的状态，返回 outcome 与回执 ID，不产生任何效应，也不携带上下文。它的 guard resolve 与授权只由激活核心（0037–0039）回答，**每次仍复查**：

1. 派发方服务凭据的身份、有效期与撤销，以及它对队列的动作授权；
2. Run 凭据的身份与 Run 证明：凭据撤销、过期或被控制作废，以及来源权威的任何变化（Run 凭据绑定来源目录摘要，租户权威修订变化即作废，0034）；租户状态包含在目录摘要内；
3. 任务租约与 fencing；
4. Run 绑定（命令与输入摘要）；
5. `not_after`。

0052 以后叠加的各层（上下文工件、目录、角色、角色时限、正式数据、关系、角色策略、v6 绑定、模型请求、回复兜底）**不再对 inspect 执行**，对 start、resume、cancel、model、tool、每一次效应调用以及这些操作的 resolve 一律照旧。

保护措施：

- SQL（0360）：inspect 的授权载荷如果带有任何上下文信封、模型请求或模型结果，拒绝；核心的回答如果带有上下文工件，拒绝。
- guard（runtime_control）：inspect 的应答如果带有上下文工件，以 503 拒绝。
- Host：inspect 的应答带有上下文工件即视为无效；inspect 不更新 Run 的上下文证明。
- Python 端：inspect 不构造任何上下文信封。

## 3. 理由

“派发时按当前权限复查”保护的是**效应与数据**：每一次可能产生效应或读取业务数据的调用，都要按当前权限重新授权。inspect 不产生效应，返回体不含任何来自上下文或关系的数据，复查这些读证明不能阻止任何效应或泄露。真正决定 Run 能否继续的复查（凭据、租约、绑定、时限、来源权威）对 inspect 仍然每次执行。上下文读权限被撤销后，下一次 model、tool、start、resume 会立即被拒，Run 无法再推进，inspect 只能看到它的终局状态。

## 4. 后果

- 200 客户模板实测（pg_stat_statements，历史回复阶段）：每次授权的平均嵌套语句从约 7100 降到约 4100，平均耗时从约 60 ms 降到约 35 ms（含 inspect 与其他操作的混合）。
- 上下文读权限被撤销、工件被删除、过期或篡改时，Run 状态仍可查询，但不会再有任何执行或效应；测试见 `tests/test_inspect_authz_scope_pg.py`。
- inspect 的复查范围比其他操作窄，这是有意的例外，后续任何新增的 Run 操作默认走完整复查；若要把其他操作纳入窄范围，须另立 ADR。
- 如果将来 inspect 的返回体要携带业务数据，必须先撤销本 ADR 的例外。
