# 工作台使用说明（负责人）：世界模型、数据、知识审核、运营人设与外联

- **适用**：v0.1.0 之后第一至第七批新增的工作台页面与负责人操作（第七批 `935aaf62`）。
- **写法**：只用角色名；不含截图、凭据或地址。
- **页面文字**：引号中的文字就是页面上显示的原文。
- **术语**：按 [工作台术语表](../design/workbench-glossary.md)：实体名用 EIOS 英文（Object Type、Object、Property、Link、Function、Action、Object Set、Artifact、Claim），状态显示中文标签，原始码只在悬停提示或详情里出现。
- **角色**：
  - **负责人**：工作台的 owner 角色；
  - **运营**：operator 角色；
  - **审核员**：reviewer 角色。

  角色清单见 `deploy/authorization/workbench-roles.v1.json`。

## 1. 世界模型、数据与知识审核

导航分组“模型与资产”下有：企业世界模型（可展开）、数据资产、数据健康、知识工作台。“管理”分组下有能力目录。

### 1.1 企业世界模型

- **导航**：点“展开 / 收起”打开“企业世界模型”这一组。子项依次是 **Object Type、Object、Property、Link、Function、Action、Object Set**，每个子项都有自己的页面和可以直接分享的地址。“企业世界模型”这一项本身是摘要页。
- **权限**：负责人和运营都可以打开。逐个 Object 的读取权限按角色计算；你没有读取权限的 Object 只计数，显示为“本页不可见 N 个”。
- **怎么修改模型**：这几个页面都只读。模型变更要经知识工作台审核（§1.5），再以可信配置发布。

**Object Type**
- 列出已发布的 Object Type，每个都有版本和 Property 契约。
- 页内的视图切换是 **Table / Graph**。Graph 显示“Object Type 关系图：N 个 Object Type，M 条 Link”；可以点某个 Object Type 聚焦到它。

**Object**
- 先选一个 Object Type，再翻页（“上一页 / 下一页”）。点开某个 Object，会显示它的标识、Schema Version、更新时间、**你有权读取的 Property 值**，以及它的“邻域图”，即直接关联的 Object。
- **被限制的 Property**：负责人限制的属性组里的 Property 只显示名称，值的位置显示“受限”标签（原始码 `withheld`）。页面上会提示“N 个 Property 属于负责人限制的属性组，只显示名称”。
- **读取会写审计**：每打开一个 Object 的详情，写一行读取审计，并按当前权限重新核对这个 Object 和每一个被请求的 Property。所以不要用这个页面做大批量浏览。
- 正在删除的客户，其相关 Object 不可读。

**Property、Link、Function、Action**：这些页面只读地列出各自的定义。Action 页列的是 Action 的定义；运行中的执行记录在“Action / 异常”页。

**Object Set**（ADR-036）
- **是什么**：负责人发布的一组“条件 + 排序 + 显示哪些 Property”的定义，例如“过去 30 天有未履行承诺的客户”。
- **怎么求值**：每次打开页面时，在数据库里按当时的数据求值，**不保存成员快照**；每个成员都按你的读取权限核对并写审计，所以你看到的成员**永远不会超过你本来就能读的范围**。
- **页面上能看到什么**：
  - 列表：版本、Object Type、条件（没有条件时显示“全部 Object”）、发布时间；
  - 预览：条件、排序（默认“按标识”）、显示的 Property、发布原因，以及“符合条件 N 个 · 本页显示 M 个 · 本页不可见 K 个”；
  - 每页 25 个，最多翻到第 1000 个。
- **特殊情况**：投影中你不能读的 Property 显示“受限”；发布后条件或排序所用的 Property 被限制了，这个 Object Set 显示“这个 Object Set 暂不可预览”；还没有任何 Object Set 时显示“暂无 Object Set”。
- **谁能发布**：只有负责人，经受治理 Action `nexloop.object_set.publish`。**页面本身不能发布**，只能查看和预览；所有成员都能查看。

### 1.2 能力目录

- **能看到什么**：系统能做什么、能触达到哪里，全部只读：“受治理能力”（能力、操作、谁可以执行、来源任务、登记时间）、Action（版本、状态、效应类别、副作用、效应清单）、来信渠道与交付路由、真实派发三层开关的当前状态。
- **权限**：负责人和运营。
- **常见问题**：这里不能开关真实派发，开关“只能由负责人在 设置与治理 中开启或关闭”；页面提示“真实派发开关暂不可读”，表示后端暂时读不到状态，不代表开关已打开。

### 1.3 数据资产

- **能看到什么**：只有计数和时间，不含消息原文：Claim 与提取、召回索引与回填记录、Embedding 预算、合并配置，以及 **Artifact** 的元数据（用途、类型、大小、创建时间、保留期限、所属客户）。每列出一条 Artifact 都写入读取审计。
- **权限**：Artifact 只有负责人和运营能看。
- **常见问题**：某项显示“后端尚未提供这一项；这不表示数量为零”，表示这项指标还没有实现；“Embedding 预算”目前一直显示“不可用”。

### 1.4 数据健康

页面讲的是 NexLoop 自己的数据流是否健康，只读，不含消息原文。顶部有快照时间，以及“共 N 项需关注”或“各项正常”。每张卡片显示“正常”或“需关注（n）”；超过阈值时，同时会触发对应的告警，告警页上有同样的处理提示。

| 卡片 | 各项的意思 | 异常时怎么办 |
|---|---|---|
| Claim 提取 | 待入队消息、最久等待、死信、24 小时失败率、队列中各状态的任务数 | 有死信或失败率超过阈值（例如 24 小时失败率超过 20%）时，先看“运行状态”页的提取队列与服务是否在运行；死信的原因码在任务详情里 |
| 召回索引与回填 | 启用的 embedding profile、索引条目、缺少 embedding 的条目、覆盖率、旧 profile 的向量、最近一次回填 | 缺少 embedding 时运行一次回填；profile 变更后仍有旧向量，说明回填或清理还没完成 |
| 审核重流 | 待重流、等待授权、最久等待 | 到知识工作台看审核重流的状态；“等待授权”需要补授权后才会重流 |
| 接入 | 发件箱待投递、24 小时商业事件、拒收率、迟到事件、最大接收延迟 | 发件箱积压（例如超过 50 条）时看投递服务；签名被拒偏多时，核对连接器的签名密钥是否轮换 |
| Artifact | 孤儿（没有引用超过 1 天）、超过保留期、删除卡住 | 核对孤儿 Artifact 是否应当清理；删除卡住时看 Artifact 清理服务 |
| 删除传播 | 未完成的删除、最久未完成、等待未知结果、重试 3 次以上的清理项、带保留的完成 | 看删除流程卡在哪个阶段；“等待未知结果”要先把相关外部动作对账清楚；重试多次的清理项看失败原因码 |

对应的告警规则（规则集 v6）：`extraction_dead_letters`、`extraction_backlog`、`recall_missing_embeddings`、`recall_profile_drift`、`reflow_stale`、`signature_rejections`、`artifact_orphans`、`artifacts_stuck_deleting`、`erasure_stalled`、`purge_retrying`。告警页上显示的是它们的中文名称。

### 1.5 知识工作台：负责人可以直接审核

- **负责人 2026-10-20 的决定**：现在这个租户只有负责人一个成员，没有单独的审核员，所以负责人也持有审核 Action（`ontology.schema.review`），可以直接审核候选。
- **怎么审核**：在“待审核候选”中打开一个候选，查看“审核证据”，然后在“审核决定”中选择**通过、并入已有定义或拒绝**。**理由必填**，决定以负责人的身份写入审计；如果候选在你审核期间被别人改过，提交会因为版本冲突被拒，刷新后重来。
- **以后怎么分工**：审核员角色没有变化。有了审核员之后，可以把审核员角色重新授予这个人，把审核职责分出去。运营既不能审核，也不能读取知识工作台。

## 2. 运营人设与联系偏好

页面：“管理”分组下的“运营人设”。有四个标签页：“人设与版本”“分配”“AI 身份披露”“外联控制”（外联控制见 §3）。

### 2.1 设置人设

1. **建立或发布一个版本**（在“人设与版本”标签页）。要填的字段：人设标识、名字、署名、自我介绍、语气、价值观、单条消息字数上限、表情、用词与称呼、禁用说法、语言、适用场景与不适用场景、“表明 AI 身份时的话术”“被问到是否 AI 时的回避话术”，以及发布原因。
   - 版本一经发布**不能修改**，要改就发布一个新版本。
   - 旧版本可以“停用”或“重新启用”。
   - Agent 不能修改人设。
2. **分配**（在“分配”标签页）。优先级从高到低是：单个客户指定 → 分群规则 → 租户默认。
3. **权限**：发布、分配、发布分群规则、设置 AI 身份披露，都只能由负责人执行，每次修改都有记录。其他成员只能只读查看人设配置。

### 2.2 AI 身份披露（负责人已定的规则）

- **默认不主动表明**是 AI：“主动表明”的默认值是“不主动表明”。可选的还有“首次接触时表明一次”和“每次会话开始时表明”。
- **被直接问到是否是 AI 时**（“被直接询问是否 AI 时”）：默认“用人设里的回避话术回答（话术为空时转人工）”，也可以设为直接“转人工”。
- **能不能自称是人类**：由租户开关“拦截‘自称人类’的说法”决定，默认关闭。打开后，系统会拦截消息里自称人类的说法。
- 还可以选择是否在消息上加“AI 生成”标识。
- 页面上的提示：是否让消费者知道是 AI 由使用方决定；不同法域对 AI 生成内容的标识有不同要求，合规责任由使用方承担。

### 2.3 联系偏好

- **来源**：只来自客户本人的表达，例如客户说“晚上别联系我”。负责人**不能替客户新增偏好**，只能对某条偏好选择“不采纳”。
- **作用**：
  - 时段、频率、渠道、主题四类偏好在**派发时**强制执行，只会让规则比租户规则更严，不会更松；
  - 语气偏好只供对话参考。
- **权限**：只有负责人能查看，也只有负责人能“不采纳”。

## 3. 外联

页面：“运营人设”的“外联控制”标签页，只有负责人能看到。修改都经负责人专属的受治理 Action，页面上会显示修订号和“外联控制修改记录”。

> **目前不会真实外发。** 外发 Action 已经存在，但工作台**没有外发按钮**；真实派发开关**默认关闭**，并且外联只有一个回环（测试）渠道。打开真实派发属于负责人的 B 类决定，要另行确认，并在“设置与治理”中操作。页面上的提示仍是“目前还没有外发功能，这些设置先用于派发预演”。

### 3.1 控制项

| 控制项 | 说明 |
|---|---|
| 时区 | 勿扰时段和频率按这个时区计算 |
| 勿扰时段 | 先勾选“设置勿扰时段”，再填起止时间；可以跨午夜，例如 22:00–08:00 |
| 频率上限 | “每位客户 24 小时最多”与“7 天最多”各一个上限 |
| 开启营销 | 默认关闭；页面显示“已开启 / 已关闭” |
| 营销同意模式 | “默认可发，客户表示不同意即停（opt-out）”或“只发给明确同意的客户（opt-in）”。**打开营销时必须勾选确认**：“我确认营销同意模式为「…」，并知悉合规责任由使用方承担” |
| 营销额度 | “7 天最多”，不能超过上面的 7 天上限 |
| 退订话术 | 追加在每条营销消息的末尾，最多 200 字 |
| 发送方标识 | 可选，最多 40 字 |
| 原因 | 每次修改都必须填写 |

修改后点“保存外联控制”。

### 3.2 外联目的

- 目的说明一次外联“为什么联系”。目前的清单（可信配置 `deploy/configuration/outreach-purposes.v1.json`）有四种：承诺跟进、服务回访、计划目的、营销。
- “外联目的”表格中每行有状态（“已启用 / 已停用”）和审批（“需要 / 不需要”）两列。负责人用每行的“启用 / 停用”按钮切换，经受治理 Action `nexloop.outreach_purposes.set`。没有启用的目的，在派发时会被“目的”这道闸门拦下。
- 要新增一种目的，要发布新版本的目的清单，这不在工作台里操作。

### 3.3 外发 Action

- 外联的发送经受治理 Action（`outreach.send`），只授予负责人；另外，计划复评 Run 也可以经同一条路径请求发送（Agent 发起的请求同样要过全部闸门）。
- **受理不等于发送**：每次请求都要依次通过全部闸门，**联系限制最先**；当前真实派发开关关闭，只有回环渠道，所以不会触达任何真实客户。
- 工作台目前没有发送按钮，也没有发送记录页。发送状态目前只有原始码（例如 `pending_approval`、`accepted`、`refused`）；中文标签见术语表，会随 UI 整理批次接入。

### 3.4 可选审批

- 某个目的设为“需要审批”时，这个目的的发送请求先进入待审批，**审批时限 24 小时**。**当前清单里没有任何目的需要审批**，所以“待审批外联”通常是空的，显示“没有待审批的外联”。
- “待审批外联”表格的列是：外联、目的、发起时间、截止、发起人。负责人点“批准”或“拒绝”，经受治理 Action `nexloop.outreach.approve`。
- **审批人不能是请求人**：页面提示“发起人不能审批自己的请求”。
- **批准不是豁免**：批准后派发时仍要通过全部闸门（联系限制最先），真实派发开关仍然关闭；拒绝或超时即终止，不能再批。

### 3.5 派发预演

- **作用**：列出外联候选，并对每个候选逐道闸门给出结论，回答“如果现在发，会不会被放行、卡在哪一道”。它只读，不发送任何东西。
- **闸门**，按检查顺序：暂停、联系限制、目的、人设排除、勿扰时段、频率、客户联系偏好、真实派发（目前一定关闭）、预算。营销消息还要经过“营销已退订”“缺少营销同意”的检查（见 §4.2）。
- **怎么看**：工作台还没有预演页面，只有负责人专属的只读接口 `GET /api/v1/workbench/outreach-candidates`，需要负责人的工作台会话。

## 4. 退订、同意与拒绝规则

### 4.1 拒绝规则 v2（ADR-023 §4，负责人 2026-10-20 选方案 B）

- **营销之后的“退订”只停营销**：如果客户最近收到的一条已派发的主动消息是**营销**，并且在 **30 天内**，客户回复“退订”“取消订阅”“unsubscribe”，或者整句只有“TD”或“stop”，就**只停营销**，其他联系照常。
- **“怎么退订”“如何退订”这类问句**也按只停营销处理。
- **其他情况一律全停**：
  - 超出 30 天，或者最近一条主动消息不是营销，上面这些说法也会停止**所有**主动联系；
  - 其他任何拒绝说法（例如“别联系我”“不要再发了”），以及系统判断不确定的说法，一律全停；
  - “拉黑”“屏蔽你们”“删除我的号码”这类说法总是全停；
  - 一条消息里同时有两类说法，例如“退订，别再联系我”，按全停处理。
- **客户想全部停掉**：再说一次任何全停的说法即可，例如“别联系我”。全停之后**只有负责人能解除**（“联系限制”页）。
- 规则从 v1 切换到 v2 的记录保存在数据库中，可以审计。

### 4.2 营销同意与恢复营销

- **退订记录**：客户按 §4.1 只停营销时，系统记一条“已退订”，证据包括那条消息、命中的规则版本与条目、匹配到的文字，以及它回复的那条营销消息。之后的营销请求会被“营销已退订”拦下。
- **同意记录**：同意模式为 opt-in 时，只有明确同意的客户才能收到营销，否则会被“缺少营销同意”拦下。同意或撤回同意的来源只有两种：
  - 客户本人的来信（必须是这位客户发来的消息）；
  - 线下证据（填写证据引用）。

  两种都要填写理由（1–500 字）。
- **恢复营销**：只有在客户已退订时才能恢复，而且**不会自动恢复**，必须由负责人记录。
- **怎么记录**：经负责人专属的受治理 Action `nexloop.marketing_consent.record`，种类有“同意”“撤回同意”和“恢复营销”。**工作台目前还没有这个操作的页面**，要等后续的 UI 批次补上。

## 5. 模拟世界

> 模拟世界只用合成或结构生成的数据，效应只经 Action 替身执行，**不会触达任何真实客户或真实 provider**；真实派发开关对模拟世界恒为关闭。总体说明见 [NX-041 总说明](../implementation/NX-041-overview.md)。

负责人用到四个 Action，都只有负责人能执行，每次都要写原因：

| Action | 做什么 | 配置文件里的字段 |
|---|---|---|
| `nexloop.sim_world.create` | 建立一个模拟世界（`sim:`）或影子世界（`shadow:`）；同一请求重试得到同一个世界；时钟建立时是暂停的 | `kind`（`simulation` 或 `shadow`）、`purpose`（目的）、`expires_in_days`（1–30，默认 30） |
| `nexloop.sim_world.generate` | 在 `sim:` 世界中生成数据：合成（按分组）或结构生成（按已发布定义）；同一（类型、种子）只生成一次，每个世界最多 10 次 | `world`、`kind`（`synthetic` 或 `structural`）、`seed`、`consumers`（1–2000）、`events_per_consumer`（`min`、`max`，0–50）、`segments`（合成时填，否则为空）、`max_objects`（结构生成时填，0–10000，否则为空） |
| `nexloop.sim_clock.control` | 推进、暂停、恢复时钟或设置速率 | `world`、`action`（`advance`、`pause`、`resume`、`set_rate`）、`seconds`（推进时填）、`rate`（设置速率时填）、`reason` |
| `nexloop.sim_world.delete` | 整体删除一个世界：分批清除，可以中断后继续；只保留 30 天摘要（计数与 digest），然后彻底删除 | `world`、`reason` |

**用法：配置文件加一条命令**（与“确认未送达”等负责人工具同一形态）：

1. 在私有目录写一个配置文件（权限 0600，不进 git），内容是上表中对应 Action 的字段，外加一个稳定的请求 ID（重试时保持不变）。
2. 执行一条命令，工作台口令从钥匙串经管道输入；先加 `--dry-run` 预查，结果无误后去掉 `--dry-run` 正式执行。
3. 命令输出只含世界 ID、状态与原因码，不含口令或数据内容。

> **当前状态（`935aaf62`）**：这四个 Action 已经在工作台的写入口上（`create_sim_world`、`generate_sim_world_data`、`control_sim_clock`、`delete_sim_world`），但**工作台还没有页面，负责人用的命令行工具也还没有实现**。在工具合入之前，不要用其他方式代替；需要建立模拟世界时，请先让开发线补上这个工具。

**数量与期限**（负责人 2026-10-21 定）：每个租户最多同时有 20 个 active 的模拟世界；每个世界默认 30 天到期，最长 30 天，到期后自动整体删除，不需要再执行删除。需要更久的实验，到期前另建一个世界，用同样的种子重新生成。

**常见问题**
- **生成时报 `quota_exceeded`**：这个世界已经生成过 10 次，换一个新世界。
- **同一种子再生成一次没有变化**：同一（类型、种子）只生成一次，这是有意的，保证可以复现。
- **删除后还能看到这个世界**：删除分批进行，状态会依次显示删除中、已删除；之后 30 天内只剩摘要。
- **建立时被拒，提示数量已满**：已经有 20 个 active 的世界，先删除不用的世界。
- **模拟世界的费用**：每个世界的模型预算是 100 元，按租户每月合计不超过 100 元；超出时新的模型调用被拒绝。
