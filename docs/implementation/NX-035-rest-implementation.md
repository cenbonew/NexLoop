# NX-035 本地剩余项：实现说明

分支 `nx035-rest`，从 `dispatch/integration-s5c` `a90634d` 切出。迁移 `0250_nx035_journal_retention.sql`（临时号）。依据：`NX-035-design.md`（D1–D8 已定）、`NX-035-local-implementation.md` §7 的剩余项，以及 0140 头注释中记下的集成点。

## 1. 删除记录清扫不越过已导出的恢复日志；恢复日志的保留（正确性）

- **导出序号**：`runtime.nexloop_journal_exported_seq()` 取已校验的日志导出（`runtime.nexloop_backup_manifests` 中 kind 为 `journal` 的记录）里最大的 `journal_seq`。从未导出过时为 null。
- **records 清扫**：0140 的 `runtime.nexloop_retention_sweep_records` 函数体重命名保留为 `…_before_journal_v0250`，其他类别仍交给它处理；`records` 类别由新函数处理：
  - 一条删除记录只有同时满足两个条件才删除：保留期已满；承载它的恢复日志条目的序号不大于已导出序号（日志条目已被清理，说明它早已导出）。
  - 从未导出过时一条也不删（fail closed）。
  - tombstone 不进恢复日志，仍按自己的天数清理。
  - 恢复重放进行中时什么都不删（与 0140 相同）。
- **恢复日志的保留**（在同一次清扫中进行）：
  - 该租户、该 world 的日志条目，在 `deletion_ledger_days`（records 设置，365 天，长于 35 天的备份保留期，NX-029 §9）之后、并且已导出时才删除；
  - 日志表是只追加的，删除通过登记过的删除范围进行（0129 的机制），与删除记录相同。
- **为什么不会丢**：恢复时，重放的输入是已导出的日志段，加上恢复出的数据库自身仍保存的日志。已导出段只覆盖到导出序号，而清扫只删除导出序号以内的条目，所以两部分首尾相接，既不缺也不重。
- **清扫结果**的计数增加 `journal`（日志删除条数）和 `journal_exported`（是否有过导出）。
- **对部署的影响**：没有启用日志导出（`nexloop-backup journal`）的部署，删除记录会一直保留。这是有意的：删除记录必须在被导出之后才能离开数据库。

## 2. 各渠道“按时间查询”的读取器（`nexloop_eios/restore_evidence.py`）

- **作用**：读取器从渠道自己在数据库之外的持久记录中，列出时间窗口内的外部引用，生成恢复窗口对账所需的证据条目（`{tenant_id, world, action_type, time_queryable, external_intent_ids}`），交给 `runtime.nexloop_restore_reconcile`。
- **`local_json_evidence`**（本地 JSON 投递，NX-016）：
  - 依据：每个已投递的意图有一份不可变、fsync 过、原子发布的 manifest，它的修改时间就是发布时间；
  - 窗口内发布的每个 manifest 都是一个引用；
  - 以下情况都把渠道判为不能按时间查询，由对账保持暂停：条目不是本人所有的私有普通文件；manifest 里的意图不是文件名对应的意图；store 根目录不是私有目录或不存在。
- **`incentive_ledger_evidence`**（AT-043 的优惠回环账本）：
  - 依据：每个已发放的意图一份 fsync 过的 JSON 记录，以意图 ID 的 sha256 命名、原子替换；
  - 未完成的 `.tmp` 不算已发放；
  - 记录名与内容不符，或出现其他异常条目，就判为不能按时间查询。
- **`not_queryable`**：不能按时间查询的渠道使用的条目。没有引用，对账时会暂停对应的 action type，等负责人处理（规则不变）。
- **读取器不做的事**：不猜测，也不修复渠道的记录。
- **“出站记录服务”尚待确认**：NX-047 的出站记录器把记录写在数据库里，恢复后会随数据库一起回退，不能作为窗口证据；`message_provider_facts` 也在数据库里。本次实现了两个有库外落盘记录的回环渠道：本地 JSON 投递和优惠回环账本。“出站记录服务”具体指哪个库外记录，待调度员确认后再补。

## 3. 工作台“备份”块（只读，apps/web）

- **数据来源**：运行状态页的“备份”块显示 M12 备份块（`runtime.nexloop_backup_metrics`），只包含数字和状态：
  - 最近一次已校验的数据库备份、最近一次完整备份、最近一次 WAL 归档、恢复日志导出延迟、最近一次文件快照、距上次通过的恢复演练、最近一次演练的 RPO / RTO；
  - 最近一次备份校验（通过或失败）、WAL 归档（正常或出现失败）、各仓库最近一次备份的时间。
- **按 AT-045 处理缺失**：
  - 没有观测的指标显示“无”，从不显示为 0；
  - 一次数据库备份都没有记录时，整块显示“没有任何已记录的数据库备份：未加载，不代表没有备份。”
- **严格解析**：非数字、负数、未知状态都按无效响应处理。
- **测试**：`apps/web/test/workbench-observability.test.ts` 新增一条，覆盖各项数值、“无”、校验与归档状态和严格解析；原有的“不可用”用例改用新文案。

## 4. 意图重建（切片三，Q2）：只有设计，未实现

**背景**：恢复到时刻 T 后，窗口 [T, 恢复开始] 内外部渠道已经执行、但数据库里没有对应意图的引用（对账中的“无法核实”），现在一律保持暂停，由负责人人工处理。切片三要把其中能核实的部分重建为意图，使渠道可以恢复，而且不会重复执行。

1. **前提**：
   - 只针对能按时间查询、并且能按引用查询到完整、确定参数的渠道，即本地 JSON 投递（manifest 带有冻结参数和 payload digest）和优惠回环账本（记录带有金额、币种、目录代码、客户引用）；
   - 其他渠道仍然保持暂停。
2. **重建的对象**：为每个“无法核实”的引用重建一个已终态的意图（fulfilled），带上外部回执，并记为 `origin='restore_reconstructed'`。
   - 不重建 Run、计划步骤或模型调用；
   - 不重建 Commitment 或业务对象的变更；业务对象的结果另由负责人复核；
   - 预算按回执补记消耗，并标注来源为恢复重建，不重复预留。
3. **授权**：重建是负责人在 verified_readonly 状态下执行的受治理人类 Action（`restore.reconstruct_intents`，owner 专属，经 0124 注册表），逐个渠道确认。
   - SQL 会重新核对：引用确实在窗口内、渠道记录的哈希与提交的证据一致、该引用在库中没有任何意图。
4. **幂等与不重发**：
   - 重建的意图直接写为终态，从不进入派发；
   - 以外部引用为业务键，同一引用只能重建一次；
   - 重建之后，该渠道的“无法核实”计数归零，负责人才可以恢复该渠道的 action_type scope。
5. **删除传播**：
   - 重建前先核对删除日志：引用所属的 Consumer 如果已被删除（重放后），就不重建，只计入一个 tombstone 计数；
   - 重建出来的记录同样受 NX-029 删除与保留规则约束。
6. **需要定的事项**：
   - 业务对象副作用（例如服务交付后应更新的对象状态）是否也要重建，建议否，由负责人复核；
   - 重建是否需要第二人确认，建议否，与 `open_scope` 相同，只需 owner。
7. **验收**：
   - 恢复演练中，构造窗口内已执行、库中缺失的投递和优惠发放；
   - 重建后，每个引用正好对应一个终态意图，不会重复执行；
   - 渠道恢复后，新的工作照常派发；
   - 已删除 Consumer 的引用不会被重建。

## 5. 测试

- `tests/test_journal_retention_pg.py`（3 个，干净 catalog，以 owner 身份调用清扫函数）：
  - 从未导出时什么都不删；
  - 只导出一部分时，只删除已导出的部分；未导出的条目即使超期也保留；
  - 年轻的条目保留；
  - 已导出段与库内剩余日志首尾相接、不缺不重，内容不变；
  - 不会清理其他租户的条目；
  - 重放进行中时不清扫。
- `tests/test_restore_evidence.py`（4 个）：
  - 本地 JSON：窗口内的投递被列出，窗口外的不列出；权限不对、名不副实、根目录不私有、目录不存在时，判为不能按时间查询；非法窗口被拒绝；
  - 优惠账本：窗口内的发放被列出；未完成的写入不算；记录名与内容不符时，判为不能按时间查询。
- `tests/test_retention_expiry_pg.py` 的两个用例：在清扫前记录一次日志导出（`tests/support/journal_export.py`），并断言导出前删除记录不会离开。
- `apps/web/test/workbench-observability.test.ts`：见 §3。
