# NX-054 P1：正式关系类型的定义与发布

依据：ADR-038（负责人 2026-10-22 采用，7 个拍板点全部按推荐）与设计稿 `docs/design/relation-types-design.md` §3、§7 P1（两份文件在分支 `l5/relation-types-adr`，ce40a327）。迁移 `0318_relation_types_p1.sql`（临时编号，由调度员合批重编号）。

**P1 只做定义**：不派生（触发器在 P2）、不回填（P3）、不切读（P4）。上线后 `ontology.relations` 仍为 0 行，任何读方的行为都不变。

## 1. 内容

| 部分 | 位置 | 说明 |
| --- | --- | --- |
| 首批关系类型 | `nexloop_eios/relation_catalog.py` 的 `FIRST_BATCH` | 26 个，全部 many_to_one。其中 14 个带 Consumer 归属标记：12 个 `target`，2 个 `transitive`（`message_in`、`assessment_evidence`）。另有 12 个普通关联。不在首批中的：RelationshipAssessment 的 source/target、id 数组、`ceiling_ref`、`fulfillment_basis`（见 ADR-038 §3） |
| 链长 | `ownership_chains()`；SQL 发布时重新计算 | 由类型图计算：要求无环、每条归属链都走到 Consumer、每个源类型最多一个归属关系。首批最长链 L = 3（RelationshipAssessment → Message → Conversation → Consumer）。manifest 声明的 L 必须等于计算值 |
| 发布 | `control.nexloop_publish_relation_types(tenant, manifest)`；`python -m nexloop_eios.relation_catalog --tenant <TENANT_ID> --database-url-file <configurator DSN 文件> [--dry-run]` | 只接受 `nexloop_configurator`，与告警规则相同。`ontology.relation_type_versions.definition` 保持与 `RelationTypeDefinition` 的输出完全一致（0016 的 link 会逐字节比较），所以 NexLoop 自己的 `source_property` 与 `consumer_ownership` 放在 `control.nexloop_relation_type_profiles`，目录版本与 L 放在 `control.nexloop_relation_catalogs`。完全相同的内容重放时接受，同一版本换了内容则拒绝（40001） |
| world 隔离 | 触发器 `ontology.nexloop_relation_world_guard` | 关系的两个端点必须在同一 tenant、同一 world；它补上了 0001 中不含 world 的端点外键 |
| 写权限 | 迁移第 4 部分 | 只有 owner 能写 `ontology.relations`、`relation_type_versions`、profiles、catalogs；0001 对 `nex_eios_app`（如果这个角色存在）的条件授权在本迁移中撤销 |
| 受治理 unlink | `authz.nexloop_unlink_relation_action`；`GovernedRelationUnlinker` | 与 0016 的 link 同一套模式：签名命令、capability `ontology.relation.unlink`、关系 Action 绑定、关系的 delete 权限（`authz.nexloop_assert_relation_delete_authority`，由 0034 的 create 检查改为 delete）、两端的 edit 证明、Action claim 幂等。关系已经不存在时视为成功，什么都不做 |
| 按关系解析归属 | `runtime.nexloop_relation_object_consumers` | 沿归属关系走，最多 L 跳。**P1 没有任何调用方**，P4 再接入读守卫 |

## 2. 测试（本地 PG）

- `tests/test_relation_types_p1_pg.py`：
  - 首批发布：26 个、L = 3、全部 many_to_one；重放；
  - 拒绝的情况：非 configurator、声明的 L 错误、环、链走不到 Consumer、一个类型有两个归属关系、带属性的定义、同一版本换内容；
  - **结构测试（C-1）**：对每个带归属标记的类型，按它的归属路径建一条完整的链（合成对象和关系），断言解析结果是那个 Consumer、跳数等于计算值、最长链等于已发布的 L。以后新增一个带标记的类型而链走不通时，这个测试会失败；
  - world 隔离；
  - **写权限结构测试（S-1）**：枚举 pg_roles 中所有非超级用户、非 owner 的角色，都没有这四张表的 INSERT、UPDATE、DELETE 权限。
- `tests/test_relation_unlink_pg.py`：
  - unlink 删除关系，同一意图重放、关系已不存在时都视为成功；
  - link Action 不能用来 unlink；
  - 没有 delete 权限、端点权限被撤销时，什么都不删；
  - 伪造签名被拒。

## 3. 发布到 stage 之前（只读，调度员执行）

1. 设计稿 §2 的计数 SQL，用来核对首批每个引用字段的实际形态（id 是否都是 64 位 hex、目标是否存在、是否跨 world）。
2. RelationshipAssessment 中已有的 relation_name 是否与首批重名（设计稿 §8）：

```sql
select properties->>'relation_name' as name, properties->>'relation_version' as version, count(*)
from ontology.objects where type_name = 'RelationshipAssessment' group by 1, 2 order by 1, 2;
```

   首批的 26 个名字见 `FIRST_BATCH`。有重名时先改名，再发布。
3. 用 `--dry-run` 看 manifest 摘要（26 个、L = 3、digest），然后由 configurator 在登录窗口内正式发布。

## 4. P2 之前的性能基线（测量方案）

P2 的派生触发器在每次对象写入提交时执行，所以要在**没有触发器**的当前版本上先测一组基线，P2 再用同样的方法测一次，比较两者。

| 场景 | 驱动 | 测什么 | 规模 |
| --- | --- | --- | --- |
| sim 数据生成（NX-041 S2） | `tests/test_nx041_sim_generation_pg.py` 的生成路径，或 stage 上的 `sim-setup` 一次生成 | 生成 N 个合成 Consumer 及其 Goal、PlanStep、Conversation、Message、MessageAssignment 的总耗时；每个对象写入的提交耗时（p50、p95）；WAL 字节数（`pg_current_wal_lsn` 的差值） | N = 200 和 N = 1000 |
| 擦除批量假名化（0305–0307） | 对一个拥有 M 个对象的合成 Consumer 执行完整擦除（`tests/test_erasure_whole_database_pg.py` 的建数方式），由 keeper 跑到完成 | 每个阶段（references、identity residue）的耗时；属性更新的行数 | M = 50 和 M = 500 |
| 普通 real 对话 | `tests/test_relay_multi_consumer_pg.py` 的一轮入站消息 | 从消息被接受到回复写入的耗时（p50、p95） | 100 轮 |

- **测量方法**：
  - 每个场景跑 3 次，取中位数；
  - 测量期间记录负载（loadgate 低于 12），本地 PG 与 stage 各测一组，数字记入证据；
  - 只读的 `pg_stat_statements`（stage 上如果已开启）补充每条语句的耗时。
- **P2 的验收门槛（建议）**：sim 生成和擦除批量假名化的总耗时增加不超过 25%；real 对话的 p95 增加不超过 10 ms。超出时先优化派生函数，例如关系类型随会话缓存、按类型预先筛选，再考虑上线。

## 5. 不在 P1 中

- 由 objects 触发器派生关系（P2）；
- 删除对象前先删关系的 BEFORE DELETE 触发器（P2，设计稿 N-1）；
- 回填与 revert（P3）；
- 读守卫、`object_fields`、purge、世界模型邻居切到关系（P4）。
