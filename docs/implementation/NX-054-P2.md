# NX-054 P2：关系随对象写入派生

依据：ADR-038 拍板点 5 方案 a（负责人 2026-10-22 按推荐）；设计稿 §4.1 与 L6 复核的 N-1、N-2、N-3。迁移 `0319_relation_types_p2.sql`（临时编号，由调度员重编号），基于 P1（`0318`）。

**P2 只派生**：不回填存量对象（P3），不切换读方（P4）。读守卫、`object_fields`、擦除 purge 仍按 0315 的属性规则解析归属；“关系存在时用关系、不存在时用属性”的并存规则在 P4 接入。stage 上在 P1 的关系类型发布之前，这个触发器什么都不做（找不到任何关系类型）。

## 1. 内容

| 部分 | 说明 |
| --- | --- |
| `ontology.nexloop_relation_derive` | `ontology.objects` 上的 **DEFERRABLE INITIALLY DEFERRED 约束触发器**（after insert or update of properties，逐行）。它在**提交时**执行，并且读取对象当时的最终属性，所以同一事务中后写入的目标也能被看到（N-2），同一事务内多次修改时以最终值为准。对该对象类型的每个已发布关系类型（取每个名字的最新版本，并且必须有 `source_property`）：<br>- 属性是 64 位 hex、并且目标类型的对象在同一 tenant、同一 world 中存在：put 这条关系（relation_id 与 0016 相同，幂等），同时 drop 这个对象同名的其他关系；<br>- 属性为空、被改掉、或者指向不存在的对象（例如擦除写入的假名）：drop 同名关系。指向不存在的对象时，计入 `runtime.nexloop_relation_derivation_dangling`。 |
| 基数 | one_to_one、one_to_many 类型在目标已经有其他源时**拒绝提交**（42501 `relation cardinality conflict`），不跳过。首批关系类型全部是 many_to_one，一个源对象的一个属性只有一个值，所以不会冲突（N-3）。 |
| `ontology.nexloop_relation_endpoint_delete` | `ontology.objects` 上的 BEFORE DELETE 触发器：先删除以该对象为任一端的关系，再删对象（N-1）。不知道关系存在的删除路径（0129 的 CommercialRecord 保留期清理、sim/shadow world 整体删除、擦除）都不会再被端点外键挡住。 |
| `runtime.nexloop_relation_dangling(tenant)` | 只读：派生时遇到的悬空引用，按 world 和关系类型计数。 |
| 不派生的情况 | 以 `session_replication_role=replica` 写入的对象（恢复、测试种子数据）不派生；这部分由 P3 的回填覆盖。 |

两个触发器都是 security definer，执行时先设置 `eios.tenant_id`。`ontology.objects` 与 `ontology.relations` 都启用了强制 RLS，不设置就什么都看不到。我第一次实现时漏了这一点，测试抓到了：删除触发器删不到关系，对象删除因外键失败。

## 2. 验收（本地 PG）

`tests/test_relation_types_p2_pg.py`，7 项：

- **派生跟随属性**：put，改指向，清空，假名化（drop 并计入悬空），指向不存在的对象（计入悬空），PlanStep 同时得到 `plan_step_of` 与 `step_in_goal`，`control_id` 悬空。
- **提交时可见（N-2）**：同一事务中先写 Goal、后写它的 Consumer，提交后关系存在，悬空为 0；同一事务中建了又改指向的 Goal，只留下最终那条关系。
- **基数冲突**：为测试另发布一个 one_to_one 类型，第二个源在提交时被拒，对象本身也没有写入。
- **删任一端**：删目标 Consumer、删源 Goal，都会带走关系，不被外键挡住。
- **sim world 整体删除（N-1）**：world 内派生出关系后，`nexloop_sim_world_purge` 完成删除，对象与关系都为 0。
- **0129 财务保留期清理（N-1）**：沿用 `test_retention_pg` 的 keeper 与商务配置，过期的 CommercialRecord 带着一条指向其 Consumer 的关系，keeper 照常删除，`incomplete=0`，关系随之消失。
- **生产写入路径的悬空为 0**：`message_runtime_fixture` 经受治理的 Action 写入 Consumer、Goal、PlanStep、EffectControl、ConsumerOwnership、Conversation、Message。在它发布系统目录之后，立即发布这些类型能闭合的关系类型子集。断言：每个能解析到目标的引用属性都恰好有一条关系，至少包括 `conversation_of`、`owned_by`；`relation_dangling` 为空。

## 3. 性能（与 P1 基线对比）

`tests/test_relation_derive_perf_pg.py`：同一份数据，三种模式：

- P1：派生触发器禁用；
- 空闲：有触发器，但没有发布关系类型；
- 派生：已发布首批关系类型。

本地 PG（开发机，loadgate 通过，负载约 3.7），N = 1000 个 Goal 加 1000 个 PlanStep，一个事务内生成，再用一条语句把引用全部假名化。连跑 3 次：

| 场景 | P1 | 空闲 | 派生 |
| --- | --- | --- | --- |
| 生成（2000 个对象，3000 条关系） | 0.119–0.131 s | 0.144–0.151 s | 0.311–0.353 s |
| 批量假名化（2000 行） | 0.107–0.108 s | 0.134–0.153 s | 0.219–0.230 s |

判读：

- 只有对象写入的微基准中，派生让生成慢约 2.5 倍（每个对象多约 0.1 ms），假名化慢约 2 倍；只有触发器、没有发布类型时多出 15%–40%。
- **这超过了 P1 文档中为整体场景建议的 25% 门槛**。不过微基准只包含对象写入本身；真实的 sim 生成和擦除每个对象还有大量其他写入（事件、runtime 表、审计），派生在其中的占比更低。是否达标，要按 P1 §4 的方案在 stage 上测整体场景后判断。
- 如果整体场景仍然超标，可以做的优化：
  - 按 (tenant, 类型) 在事务内缓存关系类型清单，省掉每行的目录查询；
  - 对没有关系类型的对象类型提前返回；
  - 把同一事务内同一对象的多次触发合并成一次。
- 测试只设了一个宽松的上限（生成不超过 P1 的 4 倍加 1 秒，假名化不超过 6 倍加 1 秒），用来发现退化成平方级的情况，不代表验收门槛。

## 4. 不在 P2 中

- 存量回填（P3：受治理的回填 Action，带来源标记的 revert）；
- 读方切换（P4）；
- 删除属性后备（P5）。
