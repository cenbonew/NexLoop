# NX-054 P2：关系随对象写入派生

依据：ADR-038 拍板点 5 方案 a（负责人 2026-10-22 按推荐）；设计稿 §4.1 与 L6 复核的 N-1、N-2、N-3；L6 对 321948ad 的复核（I-1 到 I-5、P-0 到 P-2），已在修订中处理。迁移 `0321_relation_types_p2.sql`（临时编号，由调度员重编号），基于 P1（`0319`）。

**P2 只派生**：不回填存量对象（P3），不切换读方（P4）。读守卫、`object_fields`、擦除 purge 仍按 0315 的属性规则解析归属；“关系存在时用关系、不存在时用属性”的并存规则在 P4 接入。stage 上在 P1 的关系类型发布之前，这个触发器什么都不做（找不到任何关系类型）。

## 1. 内容

| 部分 | 说明 |
| --- | --- |
| 派生映射 `control.nexloop_relation_derivations` | 每个 tenant、每个关系名一行，只记**最新**发布版本的源类型、目标类型、`source_property` 和基数（I-1）：新版本去掉 `source_property` 后就停止派生，不会回退到旧版本。由 profiles 表上的触发器随 P1 的发布维护，迁移时按已发布内容填充一次。按 `(tenant_id, source_type)` 建了索引，触发器查找一个类型只需一次索引探测（P-0）。 |
| `ontology.nexloop_relation_derive` | `ontology.objects` 上的两个 **DEFERRABLE INITIALLY DEFERRED 约束触发器**：after insert；after update of properties，并且带 `WHEN (old.properties IS DISTINCT FROM new.properties)`，属性没变的更新不排队（P-1）。在**提交时**执行，读对象当时的最终属性（N-2）。<br>- 没有派生关系类型的对象类型（Message、事件类等）：一次索引探测后直接返回（P-0）。<br>- 属性是 64 位 hex、并且目标类型的对象在同一 tenant、同一 world 中存在：put 这条关系，metadata 为 `{"derived": true}`（relation_id 与 0016 相同，幂等）。<br>- **只在 update 时** drop 不再匹配的派生关系（P-2：新插入的对象没有旧关系）。<br>- 指向不存在的对象：计入 `runtime.nexloop_relation_derivation_dangling`；擦除写入的假名（`pseudonym:` 前缀）只 drop、不计数（I-5）。<br>- 最新版本没有 `source_property`：drop 这个对象同名的派生关系（I-1）。 |
| 派生与受治理 link/unlink 的分工（I-2） | 派生**只删除标记为 derived 的关系**。经 0016 link 入口写入的同名关系不会被派生删除。经 unlink 删掉的派生关系，会在该属性下一次变化时、仍指向目标的情况下重新派生出来，因为属性才是事实来源。 |
| 基数 | one_to_one、one_to_many 类型在目标已经有其他源时**拒绝提交**（42501 `relation cardinality conflict`），不跳过。首批全部是 many_to_one，不会冲突（N-3）。<br>**隔离级别（I-4）**：冲突检查依赖 READ COMMITTED：先加咨询锁，然后每条语句取新的快照。在 REPEATABLE READ 或 SERIALIZABLE 事务中，可能看不到并发提交的另一个源。<br>**提交时报错（I-3、I-4）**：基数冲突，以及事务 A 派生出指向 T 的关系时 B 并发删除了 T（端点外键报 23503），都发生在 COMMIT。Action 内部的拒绝映射捕获不到，调用方只会看到“提交失败”。API 和 worker 必须把 COMMIT 上的错误当作未成功（可重试或对账），不能当作 Action 已经成功。发布第一个 one_to_one 类型之前，要在 API 层把 COMMIT 上的 42501 映射成受治理的拒绝，并补一条经 Action 的测试。 |
| `ontology.nexloop_relation_endpoint_delete` | BEFORE DELETE：先删除以该对象为任一端的关系，再删对象（N-1）。 |
| `runtime.nexloop_relation_dangling(tenant)` | 只读：派生遇到的悬空引用，按 world 和关系类型计数。没有 grant 给任何角色；以后要 grant 时，tenant 必须来自服务端上下文，不能来自参数。 |
| 不派生的情况 | 以 `session_replication_role=replica` 写入的对象（恢复、测试种子数据）不派生；由 P3 的回填覆盖。 |

两个触发器函数都是 security definer，执行时先设置 `eios.tenant_id`（`ontology.objects` 与 `ontology.relations` 都启用了强制 RLS）。

## 2. 验收（本地 PG）

`tests/test_relation_types_p2_pg.py`，9 项：

- **派生跟随属性**：put，改指向，清空，假名化（drop 并计入悬空），指向不存在的对象（计入悬空），PlanStep 同时得到 `plan_step_of` 与 `step_in_goal`，`control_id` 悬空。
- **提交时可见（N-2）**：同一事务中先写 Goal、后写它的 Consumer，提交后关系存在，悬空为 0；同一事务中建了又改指向的 Goal，只留下最终那条关系。
- **基数冲突**：为测试另发布一个 one_to_one 类型，第二个源在提交时被拒，对象本身也没有写入。
- **删任一端**：删目标 Consumer、删源 Goal，都会带走关系，不被外键挡住。
- **sim world 整体删除（N-1）**：world 内派生出关系后，`nexloop_sim_world_purge` 完成删除，对象与关系都为 0。
- **0129 财务保留期清理（N-1）**：沿用 `test_retention_pg` 的 keeper 与商务配置，过期的 CommercialRecord 带着一条指向其 Consumer 的关系，keeper 照常删除，`incomplete=0`，关系随之消失。
- **新版本去掉 source_property（I-1）**：发布 goal_of v2（没有 source_property）后，派生映射指向 v2；属性下一次变化时派生关系被删除，新对象也不再派生。
- **派生的边界（I-2 等）**：派生关系带 `{"derived": true}`；同名的非派生关系（代表经 link 写入的）在属性被清空后仍然保留；同一事务内插入后又删除的对象什么都不留下（S-7）；replica 写入不派生；目标在另一个 world 时不派生，并计入该 world 的悬空。
- **生产写入路径的悬空为 0**：`message_runtime_fixture` 经受治理的 Action 写入 Consumer、Goal、PlanStep、EffectControl、ConsumerOwnership、Conversation、Message。在它发布系统目录之后，立即发布这些类型能闭合的关系类型子集。断言：每个能解析到目标的引用属性都恰好有一条关系，至少包括 `conversation_of`、`owned_by`；`relation_dangling` 为空。

## 3. 性能（与 P1 基线对比）

`tests/test_relation_derive_perf_pg.py`：同一份数据，三种模式：

- P1：两个派生触发器都禁用；
- 空闲：有触发器，但没有发布关系类型；
- 派生：已发布首批关系类型。

本地 PG（开发机，loadgate 通过，负载约 4.5），N = 1000 个 Goal 加 1000 个 PlanStep，一个事务内生成，再用一条语句把引用全部假名化。修订后连跑 3 次：

| 场景 | P1 | 空闲 | 派生 |
| --- | --- | --- | --- |
| 生成（2000 个对象，3000 条关系） | 0.121–0.141 s | 0.129–0.139 s | 0.297–0.299 s |
| 批量假名化（2000 行） | 0.109–0.111 s | 0.122–0.124 s | 0.205–0.210 s |

判读：

- **空闲开销**：从修订前的 +15%–40% 降到约 0%–10%（P-0、P-1）。对于没有派生关系类型的对象类型（Message、事件类），以及属性没有变化的更新，额外开销接近于零。
- **有派生的类型**：生成约慢 2.3 倍，假名化约慢 1.9 倍（修订前分别是 2.5 倍和 2 倍）。剩下的开销主要来自每条关系一次 insert（同时触发 P1 的 world 守卫和两个端点外键检查）与目标存在性检查，与派生的规模成正比，没有出现平方级增长。
- 这个微基准只包含对象写入；真实的 sim 生成和擦除每个对象还有大量其他写入，派生在其中的占比更低。**是否满足 25% 的门槛，要按 P1 §4 在 stage 上测整体场景后判断**。如果仍然超标，下一步按 L6 复核的顺序：
  - P-3：事务内缓存派生映射；
  - P-4：集合化，由语句级触发器写入候选队列，提交时一次性处理。
- 测试只设了一个宽松的上限，用来发现退化成平方级的情况，不代表验收门槛。

## 4. 不在 P2 中

- 存量回填（P3：受治理的回填 Action，带来源标记的 revert）；
- 读方切换（P4）；
- 删除属性后备（P5）。
