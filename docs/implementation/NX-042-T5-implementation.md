## 校准方法

- **数据**：只用 T4 的 real 聚合（real 世界、real 人设、每组至少 30 个消费者，只有计数和比率）。
- **窗口**：最多 3 个**互不重叠**的校准窗口 `[split_at, split_at+span)`，span 为 28、56 或 84 天。
  - **排除范围**：一个窗口排除的消费者，从“它自己的参考窗口起点”和“本次第一个窗口的起点”两者中较早的那个算起。所以同一份报告里，一个消费者最多只在一个窗口中计数，窗口之间有间隔或 span 不同时也一样（L6 复核 1.2）。
  - **不得复用**：与同一版本以往任何一份报告（不论结论）用过的窗口有重叠，就拒绝（`window_used`）。这样就不能用同一批数据反复校准直到通过（L6 复核 1.3）。
- **报告中的小计数**：每个窗口的排除计数（`non_real_persona`、`erasing`、`in_reference_window`）和 `reference_consumers_excluded`，小于 30 的一律写成 `"<30"`，不写具体数字，避免拿多份报告做差分（L6 复核 3.2、3.3）。

### 单元的口径

- 一个单元是一个（行为，窗口，分组）组合：
  - 行为：孪生里有真实聚合数据可对照的行为，只有 `reply_within_24h`（接触后 24 小时内回复）和 `refuse_contact`（接触后被记录拒绝联系），记 B ∈ {1, 2}；
  - 窗口：本次校准用到的某一个窗口；
  - 分组：该窗口输出的分组。
- T4 的分组只有三种结果：
  - 四个 UTC 时段都满 30 人，输出四个时段；
  - 有时段被抑制，只输出 `all`；
  - `all` 不足 30 人，什么都不输出。
- 所以每个窗口贡献 B × {0, 1, 4} 个单元。1–3 个窗口能凑出的单元数：

| B | 1 个窗口 | 2 个窗口 | 3 个窗口 |
|---|---|---|---|
| 2 | 0, 2, 8 | 0, 2, 4, 8, 10, **16** | 0, 2, 4, 6, 8, 10, 12, 16, 18, 24 |
| 1 | 0, 1, 4 | 0, 1, 2, 4, 5, 8 | 0, 1, 2, 3, 4, 5, 6, 8, 9, 12 |

### 门槛的选择

- **方法**：通过条件是被覆盖的单元数 k 落在 ⌈0.7n⌉ ≤ k ≤ ⌊0.9n⌋（D3，不改）。假设单元相互独立，k 服从 Binomial(n, 0.8)，下表是真实覆盖率为 80% 的孪生被误判为 failed 的概率：

| n | 通过区间 | 误判概率 |
|---|---|---|
| 8 | 6–7 | 37.1% |
| 10 | 7–9 | 22.8% |
| 12 | 9–10 | 48.0% |
| **16** | **12–14** | **34.2%** |
| 18 | 13–16 | 23.2% |
| 24 | 17–21 | 20.4% |

- **条件一：两个窗口必须能达到。** B=2 时，两个窗口最多 16 个单元，所以门槛只能是 ≤ 16 中可能出现的值。
- **条件二：误判最低。** 门槛 T 之上会下结论的单元数，是表中 ≥ T 的那些可达值，取其中最坏的误判率：
  - T=16 时，n 只会是 16、18 或 24，最坏 34.2%；
  - T=10 或 T=8 时，还会出现 n=12，最坏 48.0%；
  - T ≤ 4 时更差，例如 n=4 的误判率是 59.0%。
  - 所以选 **T = 16**：两个完整窗口就能下结论；三个窗口时 n 为 16、18 或 24，误判率不超过 34.2%。
- **只有一种行为的孪生**（B=1）：每个窗口最多 4 个单元，三个窗口最多 12 个，永远达不到 16。这类孪生明确判为 `not_calibratable`，原因写进报告：“a single calibratable behaviour gives at most 4 cells a window (12 over three windows), below the 16 cells for a verdict”。之所以不为它单设更低的门槛：n 为 8 和 12 时误判率分别是 37.1% 和 48.0%，比 B=2 时更差。
- **局限**：同一批消费者产生的单元并不独立，所以实际误判率可能高于上表；“不合格的孪生被判 passed”的概率仍然没有计算。

### 结论

| 结论 | 条件 | 是否写事件 |
|---|---|---|
| passed | 单元数 ≥ 16，且 \|覆盖率 − 名义值\| ≤ 0.10（80% 区间即 70%–90%，D3） | 是 |
| failed | 单元数 ≥ 16，其余情况；报告写明是区间过宽还是覆盖不足 | 是 |
| insufficient_sample | 单元数 < 16 | 否 |
| not_calibratable | 孪生含没有真实聚合数据的行为，或只有一种可校准行为（D4） | 否 |

- **Brier**：以区间中点作预测，由计数计算；只作参考，不参与判定。

### 反复校准：K = 3

- 报告记录尝试序号（本版本有结论的报告数，包括这一份）和最近 3 次结论（`attempts.recent_verdicts`，最新的在前）。
- `runtime.nexloop_consumer_twin_calibration` 是在 T1 定义上直接重写的，已在复制件守护里登记。重写后，只有最新一次是 passed、并且最近 3 次里没有 failed，才算 calibrated。`selectable`（T1）沿用这个状态。
- **K 取 3 的理由**：
  - 一个版本只要 failed 过，就要连续三次 passed 才能重新可选用。
  - 每次尝试至少要两个从未用过的 28 天窗口，所以想“碰运气碰到通过”，至少要再等 3 × 56 = 168 天，并且连过三次。
  - 代价：一个合格的孪生（16 个单元时单次通过率 65.8%）在一次误判之后，接下来三次都通过的概率只有 0.658³ ≈ 28%。K=2 时约为 43%。我优先防止“反复试到通过”，所以选 3；如需放宽，改成 2 即可。

## 定案与限制

1. **单元数**：门槛 16，计算过程见上（调度员 2026-10-21，L6 复核 1.1）；D3 不改。
2. **等待期**：每个窗口都必须在版本发布之后开始，并且已经结束。所以新版本至少要等 2 × 28 = 56 天，凑满两个完整窗口才能下结论。一个版本 failed 之后，还要再等至少 168 天（见 K = 3）。独立性优先。
3. **可校准的行为**：只有回复率和拒绝联系率。含其他行为的孪生，或者只有一种可校准行为的孪生，都判为 `not_calibratable`（D4）。
4. **命令行工具**：`scripts/deploy/twin_calibrate.py`，配置示例为 `deploy/examples/twin-calibrate.example.json`。
   - 先用 `twin_calibrate.py --config F --dry-run` 预演：只检查配置、显示请求，不读口令，也不发送。
   - 正式执行：`security find-generic-password … -w | twin_calibrate.py --config F --origin https://<APP_HOST_NAME>:<PORT> --username-file F --password-stdin`。
   - 窗口先按时间排序，再计算幂等键，所以窗口顺序不同的同一份配置算同一个请求（L6 复核 4）。重跑时返回受治理的原结果。
