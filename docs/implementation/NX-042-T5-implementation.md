# NX-042 T5 实现说明：校准运行与报告

- **依据**：设计稿 §3.2、§3.3；负责人 D2、D3、D4、D7（2026-10-20）；调度员 2026-10-21 关于单元数、等待期、可校准行为和命令行工具的定案。
- **迁移**：0281（T4 聚合读取）、0282（校准报告、评估、受治理 Action），都是临时编号，合并时统一编号。
- **契约**：`twin-calibration-report.schema.json`（`nexloop-twin-calibration-report/1`）。

## 做了什么

| 部分 | 内容 |
|---|---|
| 报告表 | `control.nexloop_twin_calibration_reports`，写入后不可修改（不能 update、delete 或 truncate）；引用为 `twin-calibration:<报告 digest>` |
| 评估 | `runtime.nexloop_twin_calibration_evaluate(定义, 各窗口聚合)`，纯函数 |
| 触发 | 负责人受治理 Action `nexloop.consumer_twin.calibrate:1`（operation `calibrate_consumer_twin`，只能在 real 世界发起，同一请求幂等）；命令行 `scripts/deploy/twin_calibrate.py` |
| 事件 | 结论为 passed 时追加 `passed`，版本变为 calibrated，NX-043 可选用；failed 时追加 `failed`；insufficient_sample、not_calibratable 不追加。触发器要求事件对应一份同版本、结论相同、定义 digest 一致的报告 |

## 校准方法

- **数据**：只用 T4 的 real 聚合（real 世界、real 人设、每组至少 30 个消费者，只有计数和比率）。
- **窗口**：最多 3 个**互不重叠**的校准窗口 `[split_at, split_at+span)`，span 为 28、56 或 84 天。每个窗口的参考窗口是它前面同样长的一段；参考窗口里出现过的消费者从这个校准窗口中排除，所以按消费者分组，不按消息。连续的几个窗口里，前一个窗口的消费者会因此自动从后一个窗口中排除。
- **单元**：（行为，窗口，分组）。行为只有 `reply_within_24h`（接触后 24 小时内回复）和 `refuse_contact`（接触后被记录拒绝联系）。分组是四个 UTC 时段；有时段被抑制时，只用 `all`。一个窗口最多贡献 8 个单元，报告里列出每个窗口贡献的单元数。
- **覆盖率** = 区间覆盖住观察比率的单元数 ÷ 单元总数。
- **结论**：

| 结论 | 条件 | 是否写事件 |
|---|---|---|
| passed | 单元数 ≥ **20**，且 \|覆盖率 − 名义值\| ≤ 0.10（80% 区间即 70%–90%，D3） | 是 |
| failed | 单元数 ≥ 20，其余情况；报告写明是区间过宽还是覆盖不足 | 是 |
| insufficient_sample | 单元数 < 20 | 否 |
| not_calibratable | 孪生含没有真实聚合数据的行为（D4） | 否 |

- **Brier**：以区间中点 p 作预测，由计数计算：`r(1−p)² + (1−r)p²`；报告给出每个单元的值和按人数加权的总值。只作参考，不参与判定。

## 真实覆盖率为 80% 的孪生被误判为 failed 的概率

假设各单元相互独立，被覆盖的单元数服从 Binomial(n, 0.8)。通过区间是 ⌈0.7n⌉ ≤ k ≤ ⌊0.9n⌋：

| 单元数 n | 通过需覆盖的单元数 | 误判为 failed 的概率 |
|---|---|---|
| 8（旧规则，单窗口） | 6–7 | 37.1% |
| 16 | 12–14 | 34.2% |
| **20（新的下限）** | **14–18** | **15.6%** |
| 21 | 15–18 | 28.7% |
| 22 | 16–19 | 28.7% |
| 23 | 17–20 | 29.3% |
| 24（3 个完整窗口） | 17–21 | 20.4% |

- 按调度员定案，合并后至少 20 个单元才下结论。
- **n = 20 时误判概率为 15.6%。**
- 三个窗口都满（24 个单元）时反而是 20.4%：区间端点必须取整数个单元，n 不同，可通过的整数范围也不同，所以误判率不是随 n 单调下降的。
- 两条额外说明：
  - 同一消费者在不同时段或不同行为的单元之间并不独立（回复和拒绝联系来自同一批人），所以实际误判率可能高于上表。
  - 上表只计算“合格孪生被判 failed”，没有计算“不合格孪生被判 passed”的概率。

## 定案与限制

1. **单元数**：最多合并 3 个互不重叠、都在版本发布之后的窗口，合并后至少 20 个单元（调度员 2026-10-21）。不改动负责人的 D3 门槛。
2. **等待期**：每个校准窗口都必须在版本发布之后开始，并且已经结束。所以新版本至少要等 28 天才能校准，凑满 20 个单元则至少要等 3 × 28 = 84 天。这是有意为之：独立性优先，参数不可能见过校准数据（调度员 2026-10-21 维持现状）。
3. **可校准的行为**：只有回复率和拒绝联系率。含其他行为（例如 `payment_intent`）的孪生一律判为 `not_calibratable`，不会被标为已校准（D4，调度员维持现状）。
4. **命令行工具**：`scripts/deploy/twin_calibrate.py`，配置示例为 `deploy/examples/twin-calibrate.example.json`。
   - 先用 `twin_calibrate.py --config F --dry-run` 预演：只检查配置、显示请求，不读口令，也不发送。
   - 正式执行：`security find-generic-password … -w | twin_calibrate.py --config F --origin https://<APP_HOST_NAME>:<PORT> --username-file F --password-stdin`。
   - 用同一份配置重跑时，返回的是受治理的原结果（`outcome_id`、`replayed`），不会写第二份报告。
