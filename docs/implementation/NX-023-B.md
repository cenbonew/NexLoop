## 2. 逐来源复核规则（`authz.nexloop_context_v6_source`）

所有条目先查：10 个键齐全、`content_hash = sha256(规范 JSON(content))`、`access_decision_ref` 指向本次签名信封中某个当前 READ 证明（`decision:` + 该证明规范 JSON 的 sha256，证明本身逐个经 `nexloop_assert_read_authority` 复核）。然后按来源类型：

| ref | 允许的段 | 证明 | 由源行重算并比较 | 要求的 tags |
|---|---|---|---|---|
| `claim:<id>`（陈述） | 只能 `evidence`，`subsection=claim_evidence` | `eios:object:Conversation/<本 Run 会话>` | 原文、Message 引用、span、说话人、kind、resolution_state、modality、condition（**不含结构化 value**）；revision=extractor_version；kind 由说话人决定 | `negation`（否定）、`contact_limit`（constraint） |
| `claim:<id>`（hypothesis） | 无（真实世界一律拒绝） | — | — | — |
| `nexloop:intent:<uuid>` | `open_work/intents` | `eios:object:Consumer/<本 Run 消费者>` | action、state、since；只收 accepted/dispatching/unknown | `unconfirmed` |
| `nexloop:outbound:<uuid>` | `open_work/outbound` | 同上 | delivery_state、since、固定说明；渠道已接受的不在此 | persisted/dispatching/unknown → `unconfirmed` |
| `eios:object:Consumer/<id>` | `constraints`、`consumer_state` | 对象 READ + 每个展示属性的属性 READ | 每个属性等于当前对象值；revision=当前 revision | 无 |
| 其他 | 拒绝 | | | |

被裁剪条目同样复核，且不得带任何钉住标签；`budget_report.omitted` 与提交的被裁剪条目一一对应。钉住来源完整性：本会话中仍在审核态、带原文、否定或 constraint 的 Claim，本消费者 accepted/dispatching/unknown 意图与 persisted/dispatching/unknown 外发，必须全部在包内，除非 `insufficient` 显式声明该段 `required_source_unreadable`。

重放：同一消息已绑定后再次调用（丢失 ACK 的重试），包必须逐字相同；此时不再逐项复核（当时的读取证明已过期），只复核核心、Artifact 与 claim。

## 3. 模型请求记录（AT-027）

- Host 计算 `request_text = 规范 JSON({model:{api,id,provider}, context, settings})`（去掉 apiKey/headers/signal 等）；`request_digest = sha256(request_text)`；`tool_manifest_digest` 为 `[context.tools, 每条 system 消息的 {added, removed}]`（Pi 把工具声明放在转录的 system 消息里）的规范 hash；`settings_digest` 为 settings 的规范 hash。
- SQL 复算三个 digest；请求中必须有一条 user 消息的内容等于已绑定的 v6 包；provider 由 Run 命令的 `runtime_profile` 固定（deterministic-test→faux，deepseek-flash→deepseek）；`call_sequence` 稠密（0089 触发器）；同号同请求的重试幂等，同号不同请求拒绝；预算取自包所引用策略。
- 请求原文存于新表 `runtime.nexloop_model_request_prompts`（FORCE RLS、只追加、应用角色无权限）；`prompt_artifact_id` 由 (run, call_sequence) 派生。
- **与设计稿的差异（调度员 2026-10-09 决定，v0.1 接受）**：设计稿 §4 要求请求原文进私有 Artifact、PG 只存 hash 与受权引用；本实现把原文存在 PG 私有表，单次上限 192 KiB（guard 请求体 256 KiB）。接受条件：表 FORCE RLS、只有 owner 可读、应用角色无任何权限、原文不进日志（guard 与 Host 只记录 digest）。
- **交给 NX-029**：`runtime.nexloop_model_request_prompts` 与 `runtime.nexloop_model_requests` 纳入保留期、删除传播（含消费者删除/更正）与导出范围；请求原文含顾客原文与证据文本，保留期不应长于对应 Message；当前表只追加，删除需由 NX-029 的受治理删除路径实现（不得直接 SQL 删除）。
- `runtime.nexloop_context_manifest(run_id, call_sequence)`：按 `context-manifest.schema.json` 组装单次调用的 Manifest（仅 owner 可用的审计投影）。

## 6. guard 耗时前后对比

方法：pytest 插件包裹进程内 guard 的 `RuntimeActivationPort.authorize` 与 `_effect_tool` 计时；基线为 `ce111f6` 的独立 worktree（同一 venv、同一 Node），与改动版**交替**各跑 4 轮（同一时段，消除机器负载差异）。下表为 4 轮中位数的中位数（p90 / 最大值）。

| 用例 | 操作 | 基线 ce111f6 | 本分支 |
|---|---|---|---|
| v4[complete] | guard model | 700 ms（1066 / 1196） | 691 ms（1076 / 1198） |
| v4[complete] | guard tool | 700（767 / 907） | 713（790 / 892） |
| v4[complete] | tool submit | 1117（1250 / 1333） | 1109（1210 / 1258） |
| 两 Pi | guard model | 980（1076 / 1235） | 945（1035 / 1177） |
| 两 Pi | guard tool | 951（997 / 1370） | 932（984 / 1046） |
| 两 Pi | tool submit | 1329（1462 / 1518） | 1324（1486 / 1530） |

v2–v5 Run 不携带快照，只多一层外包函数，差异在噪声内。v6 真实 Pi 用例（3 次）：带快照的 guard model 中位数 258–293 ms，同一 Run 不带快照的 235–328 ms，快照写入约增加 20–30 ms；工具请求 2 s 时限内余量与 v2 相同。早先非交替测量曾显示改动版慢 15–25%，同时段系统负载 10–13（其他线在并行跑回归），交替重测后消失。
