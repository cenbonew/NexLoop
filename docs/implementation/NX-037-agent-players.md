# NX-037 代理扮演客户：执行说明（10/17 校准，10/18–19 交互）

> **客户为模拟、系统为真实。** 消费者由负责人操作的 AI 代理（Claude Code / Codex 驱动浏览器）扮演。部署、网关、DeepSeek 真实模型、企业端点和 WebChat 都是真实的。负责人是唯一的员工。

本文给负责人和代理使用。命令与开跑清单见 [OPERATIONS.md](../OPERATIONS.md) §9.4、§9.4a；计划见 `deploy/configuration/nx037-interaction-plan.v3.json`（36 次）。

## 1. 分工

| 谁 | 做什么 |
|---|---|
| 负责人 | 准备授权书与参与者登记（§6），开三层开关，在终端运行 `run_interactions.py --driver real …`；在校准后的暂停和异常时做决策。 |
| 客户代理（每个消费者账号一个浏览器会话） | 按运行入口的提示，在 WebChat 页面以对应账号发消息、读回复；一次交互的消息全部发完后创建完成标记。 |
| 员工侧代理（可选，也可以由负责人本人做） | 只用于 `human_takeover` 类：在工作台接管、回复、交还；`takeover_after_delivery` 变体中在参考端点员工页面标记工单。使用负责人唯一的工作台账号。 |
| 运行入口（`run_interactions.py`） | 发出提示，等待完成标记，观测本次交互的全部来信与 Run，按规则判定、暂停或停止。它自己不发任何消息。 |

## 2. 同步点：提示与完成标记

- **提示**：运行入口每发出一次交互，就在 `<试运行目录>/prompts.jsonl` 追加一行，同时在终端打印同样的内容。例如：

  ```json
  {"seq": 7, "interaction_id": "<uuid>", "kind": "restricted_after_refusal", "variant": "repeated_refusal",
   "consumer": "consumer:<id>", "done_file": "<试运行目录>/operator-done/7", "deadline_seconds": 900}
  ```

- **代理的循环**：
  1. 读取 `prompts.jsonl` 里尚未处理的最新一行；
  2. 按 §3 的模板，用 `consumer` 指定的账号扮演；
  3. 全部消息发完、最后一条回复已经出现在页面上之后，创建 `done_file`（空文件即可）。

- **完成标记之后**：运行入口开始观测。本次交互的每一条来信都了结后才判定：Run 已终结且效应已了结；在接管期间发的来信，则以员工回复为准。判定后才会出现下一行提示。
- **超时**：在 `deadline_seconds` 内没有创建完成标记，或者某条来信始终没有了结，这次交互按 `interaction_timeout` 暂停。
- **不要提前创建完成标记**：标记之后再发的消息会算到下一次交互里。

## 3. 扮演指令模板（按类型和变体）

通用要求：

- 用自然的中文，像普通客户一样说话；不要提到"测试""代理""NexLoop"；不要编造真实的个人信息（姓名、电话、地址都用"合成"字样或省略）。
- 不写任何真实公司名或品牌名：需要称呼商家时用"你们""贵店"，人设用通用说法（例如"一位想预约上门检查的住户"）。试运行租户的真实名字只记在负责人的私有文件里；本文、模板和示例一律写作 `<TENANT_DISPLAY_NAME>`，负责人也不要把真实名字写进给代理的指令。
- 每发一条，就等 Agent 的回复出现在页面上，再发下一条；单条消息不超过 200 字。

| 类型 | 变体 | 该说什么 | 什么时候停（然后创建完成标记） |
|---|---|---|---|
| ordinary_reply | single_question | 一个与服务相关的普通问题（营业时间、服务内容、价格范围等）。 | 收到一条回复后。 |
| | long_conversation | 围绕同一个话题进行 6–10 轮：追问细节、比较选项、表示考虑一下。 | 第 6–10 条回复出现后。 |
| | vague_need | 先说一个模糊的需求（例如"最近家里设备有点问题"），等 Agent 澄清时再补充具体情况。 | Agent 给出明确建议或回答后。 |
| real_delivery | direct_order | 明确提出要购买或预约目录里的服务（企业交付）。 | 回复确认已受理后。交付工单由企业端点生成，不用等工单被处理。 |
| | vague_then_order | 先模糊描述需求，澄清后明确提出交付请求。 | 同上。 |
| restricted_after_refusal（只用 REFUSAL 账号） | single_refusal | 明确拒绝联系，例如"以后不要再联系我了"。 | 收到这条消息的回复后（受限期间仍允许一条绑定回复）。 |
| | repeated_refusal | 先拒绝联系；之后再来信说一句话，并再次明确拒绝。 | 第二次拒绝的回复出现后。 |
| | refusal_then_question | 先拒绝联系；之后再来信问一个普通问题。 | 这个问题的回复出现后（核对 Agent 只回复这条来信，不主动联系）。 |
| human_takeover | takeover_reply | 客户代理：发一条需要人工处理的消息（例如投诉或特殊要求），收到 Agent 回复后再发一条"能找人工吗"。员工侧：看到第一条回复后在工作台接管，回复第二条，然后交还。 | 员工回复出现在客户页面、并已交还后（由员工侧通知客户代理）。 |
| | takeover_after_delivery | 客户代理：先明确提出交付请求，收到受理回复后要求人工。员工侧：接管，在参考端点员工页面把这张工单标记为"已处理"，回复客户后交还。 | 同上。 |
| unknown_reconciliation | post_delayed | 负责人先在端点主机执行演练 `drill --delay-next-posts 1`；客户代理随后明确提出交付请求。 | 回复出现后。交付结果是否已经对账由运行入口观测，不用代理确认。 |
| | get_unavailable | 负责人先执行 `drill --get-unavailable-seconds 60`；客户代理随后提出交付请求。 | 同上。 |

演练命令只由负责人执行（§5），代理不执行。

## 4. 账号分组

- 计划里的 `consumer:<CUSTOMER_1..4>` 用于普通回复、交付、接管、结果未知；`consumer:<REFUSAL_1..2>` **只用于拒收类**。
- 拒收之后这个账号会被限制联系，再用它做交付会在派发时被拒。运行入口会拒绝违反分组的计划（`account groups`）。
- 一个浏览器会话只登录一个消费者账号；换账号时先退出，不要在同一个会话里切换。

## 5. 暂停与停止

- **运行入口结束**（终端退出码 1 表示暂停，2 表示停止，3 表示拒绝；`<试运行目录>/state.json` 的 `status` 为 `paused` 或 `stopped`）：代理立即停下，不再发任何消息，等负责人决策。
- **负责人在场的时点**：
  - 校准后的暂停（第 3 次之后）：核对单次费用，然后用 `--resume <确认引用>` 恢复；
  - 异常：停止，或校准以外的暂停（错误率、费用、未了结的不明效应、交互超时、critical 告警）。

  其余时间由代理按计划执行。
- **恢复之后**：代理从 `prompts.jsonl` 里新出现的那一行继续。已经记录过的交互不会重复。

## 6. 准备（负责人）

1. **授权书**：以 `deploy/examples/nx037/operator-authorization.example.txt` 为模板写自己的授权书，保存为私有文件（0600），不放进仓库。在试运行配置的 `operator_authorization.authorization_sha256` 里登记它的 sha256，运行时用 `--operator-authorization-file` 给出。
2. **参与者**：每个消费者账号登记为 `kind: agent`，写明工具名、不写凭据；负责人本人登记为 `{"kind": "human", "role": "staff"}`。示例见 `deploy/examples/nx037/trial-participants.example.json`。
3. **计划**：复制 v3 计划，把占位符换成真实的消费者账号。

## 7. 代理绝对不能做的事

- 不碰任何服务器、终端里的服务进程或数据库；不执行部署、迁移、演练命令。
- 不改任何开关（三层真实派发开关、租户或 Action 开关），不打开或点击任何真实派发开关。
- 不填写、不查看、不复制任何凭据（密码、令牌、API Key、DSN）。登录由负责人事先在浏览器里完成，代理只使用已登录的会话。
- 只在两个页面上操作：WebChat 客户页面，以及参考端点的员工页面。员工页面上只能做"标记工单"；工作台只做接管、回复、交还。
- 不修改试运行目录里除完成标记以外的任何文件，不删除证据。
- 不在消息里写真实的个人信息，不冒充真实的人或组织。
