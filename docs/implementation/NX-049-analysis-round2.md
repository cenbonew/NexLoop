# NX-049 部署主机时限分析（第二轮：JIT A/B 与并发）

依据：
- 调度员在部署主机上运行 `scripts/perf/nx049_profile.sh`，main `fb61852`，`deploy-jit-on` / `deploy-jit-off` 各 3 轮。用的是 v1 钩子，所以没有按请求的 PG 函数增量；交回的目录里也没有 `host-*.jsonl` 和 `pglog-*.log`。
- 本轮用 report v2（本分支）重新汇总这两组数据，并从 `proc-*.json` 中直接读取每个请求的分层和墙钟。
- Mac 对照用同一脚本的 `mac-baseline`（v1 钩子，可比）。
- 原始输出不入库。

## 0. 结论先行

1. **JIT 不是原因，CPU 调频也不是。** 两组之间看不出差别：
   - 服务端 `runtime_activation_command` 每次调用的均值：jit-on 137 / 138 / 161 ms，jit-off 160 / 160 / 178 ms。均值大小取决于这一轮跑到了哪一步，与 JIT 开关无关。
   - 单独请求的耗时两组相同（见 §1）。
   - jit-off 那组 v4 有几轮越过了 authorize、在 effect submit 才超时，这不是 JIT 关闭带来的改善：jit-on 第 3 轮也是这样（墙钟 33.3 s）。原因见第 3 条。
2. **O3 解析缓存在部署主机上生效（手段 3 排除）。**
   - misses 是常数：v4 每轮 409 次（两个进程分别为 371 和 38），两 Pi 每轮 751 次。这些是各进程首次解析时的必然未命中。
   - 跑得越久，hits 越多：v4 从 5971 增至 8003 再到 10549，misses 不变。也就是说，稳定阶段的命中率是 100%。
   - 汇总里的整体命中率是 0.914–0.963，低于 Mac 的 0.98，只是因为部署主机的运行在中途超时、总请求少，首次未命中占的比例就大了。
   - 缓存这一层（`PostgresAuthorityUnitOfWork._load`，即 `authz:load_fact`）每请求 552 次，合计约 16 ms，已经很便宜。
   - 但 cProfile 显示，EIOS 核心拿到缓存实例后，会立即对它做一次完整重校验并重算规范摘要。这部分记在 `resolve_facts` 自身耗时里，O3 省不掉，是手段 8 的主要对象（§6）。
3. **超时只发生在同一进程内 2–3 个 guard 请求重叠的时候。** 单独请求在部署主机上稳定低于 2 s；一旦重叠，就会越过 2 s。
   - 单独请求的耗时：v4 1.12 s，两 Pi 1.31 s，各轮之间几乎没有波动（见 §1）。
   - 重叠请求的耗时：v4 1.6–2.2 s，两 Pi 2.0–2.43 s。
   - 第一轮报告的“个别层被放大 4–35 倍”（例如 `batch_resolve` 自身耗时 279 ms 对 32 ms），**不是这些层本身变慢了**。这是重叠时等待 Python GIL 的时间，被记到了等待发生时所在的那一层（§2）。
   - v4 是否在 authorize 失败，取决于第一次重叠落在 1.70–2.19 s 的哪一侧：6 轮中有 2 轮超过 2 s，4 轮擦线通过，随后在下一次重叠时失败（effect submit 2.10–2.17 s，或之后的 authorize）。这是边缘上的抛硬币，与 JIT 无关。
4. **部署主机与 Mac 的差距是均匀的约 2.5 倍，Python 与 SQL 两部分都一样。** 单独请求中，v4 Python 部分 708 对 281 ms，SQL 往返 410 对 157 ms；两 Pi 是 964 对 392 ms、343 对 133 ms。没有哪一层被异常放大，这正是单线程 CPU 速度差的特征。
   - JIT 和调频已经排除。剩下唯一的环境因素是这台机器本身的单线程性能（以及笔记本的电源或散热策略），§5 列了一个只读核对办法。
5. **手段 4、5 合起来不够。**（更正：手段 6，即 O5b 级别 1，已经以迁移 0096 进入 main，这两轮部署数据本来就包含它，不能再计入收益，见 §4。）按 §3 的模型估算，4a、4b、5 全做之后：
   - v4 重叠请求约 1.2–1.85 s；
   - 两 Pi 重叠请求仍有约 1.8–2.3 s，上沿依旧超过时限。

   原因是两 Pi 每个请求的 Python 计算约 0.96 s，其中 `resolve_facts` 自身就占 0.77 s。两个请求重叠时，Python 部分在 GIL 下串行，单这一项就到 1.9 s。手段 4/5/6 主要减少的是 SQL 往返和服务端计算，砍不到这一块。

   所以需要新增**手段 8：削减 `AuthorizationFactsResolver.resolve` 的纯 Python 开销**，它对重叠请求的收益是按重叠请求数成倍计算的（§4）。

## 1. 单独请求与重叠请求（每轮中位数，毫秒；Python = 请求时间减去 `sql:*` 往返）

重叠的判定：同一进程内两个受时限约束的请求，时间区间的重叠超过其中较短者的 30%。

| 用例 | 主机 | 单独：总 (Python + SQL) | 重叠：总 (Python + SQL) |
|---|---|---|---|
| v4[complete] | 部署 jit-on | 1116–1122（703–708 + 410–411） | 1622–1778（878–1118 + 660–744） |
| v4[complete] | 部署 jit-off | 1117–1125（702–707 + 410–413） | 1605–1665（867–876 + 739–764） |
| v4[complete] | Mac | 430–451（276–285 + 154–159） | 641–658（377–398 + 262–268） |
| 两 Pi | 部署 jit-on | 1306–1307（962–964 + 341–347） | 2022–2201（1402–1671 + 520–621） |
| 两 Pi | 部署 jit-off | 1307–1309（963–967 + 341–345） | 2136–2290（1573–1733 + 492–508） |
| 两 Pi | Mac | 525–529（390–394 + 132–134） | 827–837（598–602 + 224–229） |

重叠的分布：
- 两 Pi 每轮只有一次重叠，3 个请求，窗口约 2.6 s，最慢的一个 2.19–2.43 s。
- v4 第一次重叠在第 6–8 次 authorize，3 个请求，窗口约 2.3 s，最慢的一个 1.69–2.19 s。之后还有多次 2–6 个请求的重叠，最慢的一个 1.6–2.47 s。

每个请求的工作量在重叠前后完全相同：
- v4：SQL 往返 246 次，`load_fact` 552 次，判定 46 次（全部不同）；
- 两 Pi：SQL 往返 132 次。

## 2. 为什么重叠就会超时：同一个 guard 进程，GIL 串行

1. **guard 由测试进程内的线程处理。** 所有 authorize 事件都来自同一个 pid、不同的线程，Python 部分要轮流持有 GIL。
2. **重叠窗口约等于各请求 Python 部分之和。** 以两 Pi jit-on 第 1 轮为例：
   - 3 个请求的窗口是 20.9 s 到 23.5 s，约 2.6 s；
   - 3 个请求单独时的 Python 部分合计 2.9 s，SQL 部分合计约 1.0 s；
   - 也就是说，窗口内基本是一个核在串行跑 Python。机器有 16 个线程，PG 的活动采样在这些窗口里平均只有 1.0 个活动后端，`CPU` 占绝大多数，没有锁等待。
3. **服务端没有变慢。** 包含重叠请求在内，整轮 `runtime_activation_command` 每次调用的服务端均值是 137 ms，与单独请求时客户端测得的约 132 ms 一致。重叠请求里客户端测到的 `sql:` 时间却从 410 ms 涨到 660–1020 ms：
   - 结果早已返回，线程在等 GIL 才能继续，这段等待被记在 `sql:` 上；
   - 每个请求有 246 次往返，每次往返结束都要重新拿一次 GIL。重叠时平均每次多等约 1–1.5 ms：事实快照 121 次多了 86–213 ms，身份快照 29 次多了 34–97 ms，角色核验 37 次多了 23–58 ms。
4. **`batch_resolve` 的 279 ms 对 32 ms 也是这个原因。** 它的自身耗时单独时稳定在 20–24 ms（v4）或 48 ms（两 Pi）；重叠时变成 37–336 ms（v4）或 618 ms（两 Pi）。多出来的时间是这个线程在批量结果返回后等 GIL 的时间，取决于当时另一个线程正在跑什么，所以波动很大。
5. **Mac 上同样有重叠，只是还有余量。** Mac 上重叠请求是 0.64–0.84 s，单独请求是 0.43–0.53 s，倍率与部署主机相同（约 1.5–1.7 倍）。部署主机每单位工作慢 2.5 倍，重叠后就越过了 2 s。

所以真正要压的是：
- 每个请求的 Python 计算 P：重叠时按重叠请求数成倍累加；
- SQL 往返次数：每次都多付一次重新拿 GIL 的代价；
- 服务端时间 D：不占 GIL，只算一次。

## 3. 估算模型

重叠中最慢那个请求的时长 ≈ k × P + D + 往返次数 × g。

- k：同时处理的请求数，取实际观测到的 2（3 个请求的窗口里，最慢的那个和另一个几乎完全重叠，第三个只部分重叠）。
- P：单独请求的 Python 部分。
- D：单独请求的 SQL 部分。
- g：重叠时每次往返多等的 GIL 时间，约 1–1.5 ms。

用部署主机的数据校验：
- v4：2 × 708 + 410 + 246 × 1.2 ≈ 2.12 s（观测 1.69–2.19 s）；
- 两 Pi：2 × 964 + 343 + 132 × 1.2 ≈ 2.43 s（观测 2.02–2.43 s）。

两个都在观测范围的上沿，可以用来估算上限。

## 4. 手段 4、5、6（以及新增的 8）在部署主机上的收益

部署主机上每个请求的估算，单位毫秒。“重叠”指按 §3 模型估算的最慢请求的降幅。

| # | 手段 | 去掉什么 | v4 单独 | v4 重叠 | 两 Pi 单独 | 两 Pi 重叠 |
|---|---|---|---|---|---|---|
| 4a | 单请求共用一个连接，事务仍按现有边界分开；`BEGIN ISOLATION LEVEL …` 合进同一条语句 | 连接借出 37→1，角色核验 37→1，隔离级别设置 24→0（约 −96 次往返） | −20~30 | −120~170 | −10~20 | −60~100 |
| 4b | 在 4a 基础上，把一个请求内的只读判定合并成一个 RR 只读事务 | 再去掉身份快照 29→1、取时间 24→1（约 −51 次往返） | 再 −15~20 | 再 −60~100 | 再 −10~15 | 再 −40~70 |
| 5 | 逐事实快照加载并入 O2b 批量 | 事实快照 121→约 4 次（两 Pi 46→约 8 次） | −35~45 | −150~220 | −10~15 | −40~60 |
| 6 | O5b 级别 1：激活 SQL 内的读断言去重 | **已在 main（迁移 0096），部署数据已包含，不计入** | 0 | 0 | 0 | 0 |
| 8 | 削减 `resolve` 的纯 Python 开销（目标 −40%） | v4 P 中的 `resolve_facts` 约 450–530 ms，两 Pi 约 770 ms | −180~210 | −360~420 | −300 | −600 |

| 组合 | v4 重叠 | 两 Pi 重叠 | 判断 |
|---|---|---|---|

- 4a、4b、5 主要减少往返次数。它们在单独请求上收益很小，在重叠请求上却有 3–5 倍的收益，因为每少一次往返，就少一次重新拿 GIL。
- 6（O5b 级别 1）已在 main 中（迁移 0096），第一、二轮部署数据都已包含它的效果，所以不计入。本文初版把它算作待做项，是我的错误，已由调度员指出更正。
- 8a + 8b 已在 `nx049-resolve` 实现，本机实测 `resolve_facts` 自身耗时降 31–40%，见 `NX-049-resolve.md`。
- 8 是唯一能按重叠请求数成倍见效的一项。具体做法要看 §6 的 cProfile 结果。
- 以上都只估算 authorize。effect submit（`runtime_effect_tool`）走的是同一套授权与激活路径，降幅相近。

## 5. 环境：还剩一项可以只读核对

JIT 与调频已经排除。剩下的 2.5 倍是均匀的，大概率就是这台 ThinkPad 的单线程性能。是否已经被电源或散热策略压低，可以在部署主机上只读核对一次（不改任何设置）：

```bash
lscpu | grep -E 'Model name|MHz'; cat /sys/firmware/acpi/platform_profile 2>/dev/null; cat /sys/devices/system/cpu/cpu0/cpufreq/energy_performance_preference 2>/dev/null
```

```bash
.venv/bin/python -m timeit -n 5 -r 5 "sum(i*i for i in range(1_000_000))"
```

在 Mac 上执行同一条 `timeit`。如果两者的比值明显小于 2.5，或者 `platform_profile` 是 `low-power`、EPP 是 `power`/`balance_power`，就说明还有一部分是电源策略造成的，可以由运维调整，不用改代码。

即使电源策略能调好，GIL 串行的结构问题依然存在，生产环境中多个 Role 并发时同样会出现，所以 §4 的工作仍然需要做。

## 6. `resolve` 的 Python 开销分解（Mac，cProfile）

命令：`NEXLOOP_PERF_CPROFILE=1 NEXLOOP_PERF_PGFUNC=0 scripts/perf/nx049_profile.sh mac-cprof 1`，然后 `scripts/perf/cprof_report.py scripts/perf/out/mac-cprof`。

覆盖范围：
- 共剖析了 4575 次 `resolve` / `resolve_in_unit_of_work`；另有 1250 次因为与正在剖析的那次重叠而跳过。
- 剖析开销很大。两 Pi 这一轮因此超时（rc=1），v4 通过。
- 下面的数字只看分布。cProfile 会放大调用次数多、单次很短的函数，所以百分比是上限。

| 热点 | 调用次数 | 占 resolve 的比例（含子调用） | 是什么 |
|---|---|---|---|
| `_fact_resolver._load_fact` → `_exact_model` → `model_validate(value, strict=True)` | 6.7 万次（每次 resolve 约 15 次） | 约 42% | 对**已经是该类型的事实实例**再做一次完整校验。`_StrictFrozenModel` 配置了 `revalidate_instances="always"`，所以每次都会重跑全部校验器，包括 `_seal_snapshot` |
| `facts._canonical_digest` / `_canonical_value` | 17 万 / 1558 万次 | 约 40–50% | `_seal_snapshot` 每次都把整个事实 `model_dump` 后递归规范化，再算 sha256。其中有 1.46 亿次 `isinstance` |
| `applications.ResourceRestriction._validate_resource_id` | 58.7 万次 | 约 19% | 嵌套限制项的校验器：每次重新校验资源 id，并对限制项重算规范摘要 |
| `_fact_resolver.project` → `convert` | 5620 / 615 万次 | 约 27% | 每次 resolve 把整张权限图投影成只读视图，相同的事实对象也会重新投影 |
| `json.dumps` / `iterencode` | 154 万次 | 约 13% | 规范化排序与摘要编码 |

结论：
- **O3 只省掉了 JSON 解析，没有省掉校验。** 缓存交回的是同一个冻结实例，但 EIOS 核心的 `_load_fact` 随即对它做一次完整重校验，重算整份事实的规范摘要。部署主机上每个请求 552 次 `load_fact`，主要就是这部分开销。
- 这些都是对同一个不可变对象、同样的输入重复做同样的纯计算。去掉重复不会改变判定结果，也不会改变摘要。

手段 8 的具体形态（不改变任何判定、摘要或证明，只去掉对同一不可变对象的重复计算）：
- **8a**：`_exact_model` 对“本进程内由受信解析路径构造、且已通过校验的冻结实例”跳过重校验。
  - 用一个只在构造路径登记的 `WeakSet`（或按 id 登记，并持有引用）来识别这类实例；
  - 不在登记里的实例仍然完整校验；
  - 登记只在 O3 缓存与 `_seal_*` 的构造路径中写入。
- **8b**：`_typed_resource_id` / `_validate_resource_id` 是纯函数，按输入做有界的 LRU 记忆化。
- **8c**：`project` 的投影结果按“冻结实例 → 只读视图”跨次复用。目前的 memo 只在单次投影内有效。
- **8d**（可选）：`_canonical_value` 的快路径，先判断 `str`/`int`/`None`，再走 `isinstance` 链。

预期：8a 与 8b 去掉 resolve 中约一半的计算。保守按 −40% 估算 §4 的收益，实施后用 §8 的方法实测。

需要注意的是：
- 这些代码在 vendored 的 EIOS 核心（`packages/eios-core/src/eios/authz/`）中，改动属于对上游的有意分叉，要在 provenance 中记录；
- `revalidate_instances="always"` 是上游的防御性设计。8a 只对本进程受信路径构造的实例生效，需要 L1 确认这一边界。进程内能改写冻结实例的代码，本来就已经越过了这条防线。
