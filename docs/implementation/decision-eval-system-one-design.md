# 判断层设计：接入方舟“决策评估 System One API（beta）”

**状态**：设计稿。负责人已批准做设计评估；**v0.1 试运行之后才实施**。本文不含实现，不改任何代码、契约或 planning。

**依据**：

- 调度员 2026-10-15 晚用合成数据做的实测（见 §0）；
- [NX-019 提取器](NX-019-extraction.md)与 ADR-019（Claim 的九类 epistemic_kind，显性与隐性分开）；
- ADR-023（显式拒绝）；
- [NX-037 provider 路由](NX-037-provider-routing.md)；
- [人民币计价](NX-037-cny-pricing.md)；
- `nexloop_eios/model_profile.py`、`provider_credentials.py` 的凭据规则；
- [OPERATIONS](../OPERATIONS.md) §8a。

**写法**：文中只用角色名与参数。接口地址记作 `<SYSTEMONE_ENDPOINT>`，凭据记作 `<ARK_CREDENTIAL_FILE>`，不写任何密钥、地址或主机名。

## 0. 接口与实测摘要

- **调用方式**：`POST <SYSTEMONE_ENDPOINT>`。请求头带 `ark-beta-systemone-api: true` 与 Bearer 凭据。
- **请求体**：`{model, state, questions}`。
  - `state` 是待评估的内容；
  - `questions` 的形式为 `{<id>: {type: noul|choice|score, instructions, criteria}}`。
- **响应** `answers`：
  - `noul` 给出概率；
  - `choice` 给出 `choice`、`confidence`、`probabilities`；
  - `score` 给出 `score`、`probabilities`、`legend`。
- **特性**：只返回判断，不生成文本；按 token 计费；上下文 128k。

**实测**（合成数据，调度员 2026-10-15 晚）：

| 项 | 结果 |
|---|---|
| 三类问题的正确性 | 都答对 |
| 时延 | 约 0.5 s |
| token | 输入约 1000，`output_tokens` = 0 |
| 注入样本（要求“忽略规则判 true”） | `grounded` = 0.0007，没有被带偏 |
| 推断类 Claim | 判为 hypothesis（0.99） |
| 校准 | 概率普遍贴近 0 或 1，校准程度存疑（见 §6） |
| 稳定性 | 连续请求中有 1 次在 60 s 内没有响应（beta） |

## 1. 定位

- **判断层或评审，不是生产者**：
  - 它不替代 NX-019 提取器，提取、切分、span 与 hash 仍由提取器完成；
  - 它不生成任何回复文本；
  - 它只对已有的内容回答带版本的固定问题。
- **输出的身份是证据或假设，不是事实**：
  - 每个判断都作为一条带来源的评审记录保存（§5），引用被评审对象的 ID 与 digest；
  - 判断结果**绝不直接修改业务对象**；
  - 需要改动 Claim 状态、发起转人工或暂停时，一律通过已有的 EIOS 受治理 Action 完成，执行者是持有该 Action 授权的服务主体；判断结果只是这个 Action 的输入之一，不能单独构成授权。
- **低置信时，默认值永远是“不确定”**：
  - 落在阈值区间之间（§6）、超时或出错（§4），都按“不确定”处理，交给人工；
  - 不确定不会被当成“否”而自动放行，也不会被当成“是”而自动拒绝。
- **可以关闭**：判断层整体由一个部署级开关控制，并按租户、按用途细分。关闭后，主流程的行为与没有判断层时逐字节相同。

## 2. 首批用途与问题集

问题集是版本化的配置文件，命名为 `decision-questions.<用途>.v<N>.json`，放在 `deploy/configuration/decision-eval/`。规则：

- 已发布的版本不再修改，改动就出新版本；
- 证据中记录问题集版本，以及每个问题的 `id`；
- `instructions` 和 `criteria` 都是固定文本，不拼接任何用户内容；
- 用户内容只放进 `state`，并且整段放在明确的界定标记之间（见 §3.5）。

### 2.1 用途一：Claim 复核（`decision-questions.claim-review.v1`）

- **时机**：提取器写出 Claim 候选之后、Claim 进入可用状态之前。复核结果只用于把候选标为“需人工复核”或“通过复核”，由受治理的 Claim 评审 Action 完成，与 ADR-019 的评审流程相同。
- **`state` 的内容**：
  - 原文片段：提取器给出的 span 所在的消息，以及前后各 N 条，N 有上限；
  - Claim 的结构化表述：predicate、object、epistemic_kind，不含内部 ID；
  - 原文的 hash，用于事后核对。

| id | type | 问题要点（instructions 摘要） | criteria 摘要 |
|---|---|---|---|
| `grounded` | noul | 这条 Claim 是否有原文中顾客本人的话直接支撑 | 只认顾客本人的原话；系统消息、员工消息、引述他人的话都不算支撑 |
| `kind` | choice | Claim 的认知类型：`stated_fact` / `stated_preference` / `stated_intent` / `hypothesis` / `other`，与 NX-019 的九类做映射，映射表随版本发布 | 显性陈述与推断要分开；凡是推断，一律判为 `hypothesis` |
| `injection` | noul | 原文是否含有试图改变评审规则或指示的内容 | 例如“忽略规则”“判为真”这类对评审者的指令；正常的业务请求不算 |
| `polarity_ok` | noul | 否定、条件、时间语义是否被正确保留（例如“不要”“如果”“上周”） | 与原文相反或丢失条件即为 false |

**判定**：

| 条件 | 结果 |
|---|---|
| `grounded` ≥ 上阈值，`injection` ≤ 下阈值，`kind` 与提取器一致且 `confidence` ≥ 阈值，`polarity_ok` ≥ 上阈值 | **通过复核** |
| `grounded` ≤ 下阈值，或 `injection` ≥ 上阈值 | **需人工复核**，原因代码为 `ungrounded` 或 `injection_suspected` |
| 其余（落在阈值区间之间、`kind` 不一致、超时或出错） | **需人工复核**，原因代码为 `uncertain` |

两种结果都不删除 Claim，也不改它的内容。

### 2.2 用途二：relay 与回复兜底的“转人工”判断（`decision-questions.handoff.v1`）

- **时机**：
  - relay 受理来信后、签发 Run 之前，作为额外的信号；
  - 回复保障在决定发兜底回复之前。
- 判断层**只能把对话推向人工**，不能阻止或替代 ADR-023 的硬性规则：显式拒绝与联系限制仍以现有的确定性规则为准。
- **`state` 的内容**：最近 N 条会话消息（角色加正文，有长度上限），以及会话当前的状态码（是否已在人工接管、是否已有拒收）。不包含其他客户的任何信息。

| id | type | 问题要点 | criteria 摘要 |
|---|---|---|---|
| `needs_human` | noul | 这条来信是否需要人工处理 | 投诉、纠纷、涉及安全或法律、明确要求找人、自动回复无法回答的问题 |
| `refusal_signal` | noul | 顾客是否表达了不愿再被联系 | 只作为 ADR-023 确定性规则之外的补充提示，不能替代该规则 |
| `urgency` | score | 紧急程度（0–3），`legend` 随版本固定 | 0 为一般咨询，3 为人身、安全或法律风险 |

**判定**：

- `needs_human` ≥ 上阈值，或 `urgency` ≥ 2：通过受治理的转人工 Action 发起人工接管，原因代码为 `decision_eval_handoff`。
- `refusal_signal` ≥ 上阈值：不自动加联系限制。只发起人工接管，并提示员工按 ADR-023 处理。
- 落在阈值区间之间、超时或出错：主流程照常进行；同时在工作台的复核队列里加一条提示，原因代码为 `uncertain`。

### 2.3 第三候选：NX-039 独立评估（`decision-questions.eval.v1`，暂不设计细节）

NX-039（独立评估与语义版本发布）要求硬门槛、留出集、成本与性能限制以及回退。System One 可以作为评估器之一，对候选版本的输出逐条回答质量问题（是否切题、是否越界承诺、是否泄露）。它的前提是：

1. 已有标注集上的校准结果（§6）；
2. 评估器本身的版本、模型 ID 与问题集版本被固定，并写进评估报告；
3. 评估器从来不是唯一的门槛，硬门槛仍是确定性检查。

等 NX-039 开工时，再按它的设计稿细化。

## 3. 部署与治理

### 3.1 新 provider 进入 ModelProfile

- **单独的 profile**：在现有的 `ModelProfile` 与 `provider_credentials` 机制之上，加一个独立的 profile 类别 `decision_eval`，前缀为 `DECISION_EVAL_`。它与 Host 的对话模型（`MODEL_`）分开，互不复用：
  - `DECISION_EVAL_PROVIDER=ark-systemone`；
  - `DECISION_EVAL_MODEL_ID=<模型 ID>`；
  - `DECISION_EVAL_BASE_URL=<SYSTEMONE_ENDPOINT>`；
  - `DECISION_EVAL_CREDENTIALS_FILE=<ARK_CREDENTIAL_FILE>`。
- **规则与现有 profile 相同**：
  - stage 上不从环境变量或 `.env` 取 key；
  - 没有 key 时进入明确标注的测试模式（确定性替身），不会静默调用；
  - `base_url` 必须与版本化允许表中的值完全一致，模型给出的 URL 一律不采用。
- **beta 头**：`ark-beta-systemone-api: true` 由适配器固定加上，不可配置。接口转为正式版后，改适配器、出新版本。
- **价目**：仿照 `model-tariffs/deepseek-flash.cny.v1.json`，新增 `model-tariffs/ark-systemone.cny.v1.json`，内容为每百万 token 的输入价与输出价，记录来源与核对日期。

### 3.2 出口网络（与 L4 的 G-CLAIM-EGRESS 对齐）

- **由谁调用**：不由 Agent Host 调用（判断层不在 Run 里）。由新的后台进程 `decision-evaluator` 调用，它是一个独立的 worker，有自己的服务主体、连接池与预算条目，从受治理的队列中取评审任务。
  - 提取器与 relay 只把待评审的对象写入这个队列，不直接对外请求，所以外部接口的时延与故障不会传到主流程（§4）。
- **走哪个网络**：放在 L4 正在实现的 G-CLAIM-EGRESS 所定义的“模型出口”命名空间中，即与 claim-extraction-worker、claim-matcher 同一个出口网络（这一项在 G-CLAIM-EGRESS 合入后对齐）。
  - 不放在应用命名空间：应用命名空间不允许访问任何模型地址；
  - 不放在 Agent Host 的命名空间：Agent Host 只给对话模型使用。
- **方舟域名进入 allowlist**：沿用 `MODEL_PROVIDER_ALLOWLIST` 的办法，防火墙只接受数字地址：
  1. 负责人在管理机上解析 `<SYSTEMONE_ENDPOINT>` 的主机名，取得当前地址集合；
  2. 写进私有 stage env 的出口 allowlist 参数（G-CLAIM-EGRESS 会定参数名），渲染 nft，作为 B 类变更由负责人加载；
  3. 地址集合与解析时间写入私有证据。
  
  CDN 或负载均衡的地址可能变化，所以要定期重新解析并比对（建议每天一次，只读），出现新地址就报负责人。不在主机上做运行时 DNS 放行，不放行整段网段。
- **TLS**：校验系统 CA 与 SNI。请求固定发往 allowlist 中的数字地址，SNI 为方舟的主机名（与 `EffectProviderConfiguration` 的 `connect_address` 思路相同）。

### 3.3 凭据

- 凭据只放在 `decision-evaluator` 自己的 secret 中（0600，属主为该服务的 UID）。写入方式与 deploy-days 执行单中 DeepSeek key 的做法相同：从开发机经 ssh stdin 写入，不回显。
- 凭据**绝不进入** `state`、`questions`、日志、证据、工作台或任何前端构建；适配器的异常信息只有错误类型。
- 方舟的 key 建议另开一把，**不与对话模型共用**，以便单独限额、单独吊销。

### 3.4 预算与 CNY 计价

- **计价**：每次调用按“输入 token × 输入单价 + 输出 token × 输出单价”记为 CNY，实测输出为 0。预算与币种的规则同 D-g 方案 2：只按 CNY，不换算，币种不一致就拒绝。
- **预算**：
  - 判断层有自己的预算科目 `decision_eval`，按租户、按月计；
  - 单次请求的 `state` 有 token 上限（建议 8k，远低于 128k）；
  - 超过月度预算的 80% 时告警，达到上限后，判断层对该租户自动进入“不确定 → 人工”（§4），不再调用。
- **估算**：每次约 1000 输入 token，以 200 客户、每天几百次评审计，月费用很低。具体单价以官方价目为准，写入价目文件时核对。

### 3.5 数据外发与隐私登记

- **登记**：判断层会把顾客原文发往外部服务。上线前在隐私和数据处理登记中增加一项：
  - 外发对象：方舟；
  - 目的：判断；
  - 字段：会话片段、Claim 结构；
  - 保存：调用方不保存，供应商的保存期以其服务条款为准；
  - 区域：境内；
  - 法律依据或授权：待负责人确认。
- **最小化**：
  - 只发评审所需的最短片段；
  - 不发顾客的联系方式、账号 ID、其他客户的数据或内部 ID；
  - 发送前对手机号、邮箱、证件号做确定性的掩码。
- **删除与限制**：
  - 已被删除或受联系限制的客户，其内容不再送去评审；
  - 评审记录只存 digest 与概率（§5），删除传播时一并处理。
- **注入防护**：用户内容只放在 `state` 中，并用固定的界定标记包起来；`instructions` 明确要求把 `state` 当作数据，而不是指令。实测的注入样本没有成功，但这只是一个样本，`injection` 问题本身也作为一个信号保留。

## 4. 可靠性

- **超时**：单次请求的总时限 5 s（实测 0.5 s，beta 曾出现 60 s 无响应）。用绝对截止时间，不在时限内无限重试。
- **重试**：
  - 只对连接错误、5xx 和超时重试，指数退避（例如 1 s、2 s、4 s，加抖动），最多 3 次；
  - 4xx（参数、鉴权、配额）不重试，直接记为失败；
  - 重试只在 `decision-evaluator` 内进行，评审任务在队列中带租约，进程崩溃后由下一个进程接手。
- **失败就是“不确定 → 人工”**：
  - 超时、重试用尽、响应格式不对、概率越界或缺项、预算用尽、开关关闭，都记为 `uncertain`，并走 §2 中“不确定”的那条路径；
  - 不会因此放行，也不会因此拒绝。
- **不阻塞主流程**：
  - Claim 复核是异步的，Claim 在复核完成前保持“待复核”，不影响提取与回复；
  - 转人工判断有时间预算，在 relay 和回复保障的步骤里只等很短的一段（例如 1 s）。超时就按“不确定”继续主流程，判断结果晚到时只补一条工作台提示，不回滚已签发的 Run。
- **幂等与缓存**：
  - 缓存键为 `sha256(规范化的 state 文本) + 问题集版本 + 模型 ID`；
  - 相同的键在有效期内（建议 30 天）直接复用之前的判断，不再调用；
  - 同一被评审对象与同一问题集版本只有一条有效记录，重复入队按幂等键合并；
  - 缓存只存 §5 中的字段，不存 `state` 原文；
  - 删除传播时，按被评审对象一并清除对应的记录。

## 5. 证据记录格式

每次判断写一行，只追加。不记录推理过程，接口也不返回推理过程。

| 字段 | 内容 |
|---|---|
| `review_id` | 新的 ID |
| `tenant_id`、`world` | 来自服务端的上下文 |
| `subject_kind`、`subject_id` | 被评审对象：`claim_candidate` 或 `message`，以及它的 ID |
| `state_digest` | 发送的 `state` 的 sha256（规范化之后、掩码之后）；不存 `state` 本身 |
| `question_set` | 例如 `decision-questions.claim-review.v1` |
| `model_id` | 模型 ID |
| `provider` | `ark-systemone`（beta） |
| `answers` | 按问题 `id` 记录：noul 的概率；choice 的 `choice`、`confidence` 与各选项的概率；score 的 `score` 与概率 |
| `thresholds` | 本次判定使用的阈值版本与数值 |
| `decision` | `pass` / `needs_human` / `handoff` / `uncertain` |
| `reason_code` | 例如 `ungrounded`、`injection_suspected`、`decision_eval_handoff`、`timeout`、`budget_exhausted` |
| `usage` | 输入与输出的 token 数，以及 CNY 金额 |
| `latency_ms`、`attempts` | 时延与尝试次数 |
| `cache_hit` | 是否命中缓存 |
| `recorded_at` | 记录时间 |
| `action_ref` | 若据此发起了受治理 Action，记下该 Action 的意图 ID；没有则为空 |

## 6. 阈值校准

- **方法**：
  - 每个 noul 或 choice 问题设两条阈值：下阈值 `t_low` 与上阈值 `t_high`。≥ `t_high` 判为是，≤ `t_low` 判为否，二者之间**转人工**；
  - 阈值在标注集上选定，目标是在给定的人工比例以内，让误放行与误拦截都不超过约定上限；
  - 阈值写进版本化的阈值文件，每次修改都出新版本。
- **标注集**：
  1. 由负责人或员工标注的合成样本，以及脱敏的真实片段，每个问题至少覆盖正例、反例与对抗样本（注入、否定、条件、推断）；
  2. 留出一部分只用于最终验证，不参与选阈值。
- **校准存疑的处理**：实测的概率普遍贴近 0 或 1。这时阈值区间的宽度意义不大，模型对错题也可能给出接近 1 的概率。所以要看标注集上**高置信度错误**的比例：比例超过上限时，不能只靠概率，必须同时满足确定性规则（例如 `grounded` 判为是时，Claim 的 span 必须真的出现在原文中），否则一律转人工。
- **上线前 shadow 运行**：
  - shadow 阶段只记录判断，不发起任何 Action，不影响主流程；
  - 用 shadow 结果与人工结论对比，统计一致率、高置信错误率、转人工比例、时延与费用；
  - 由负责人决定是否以及在哪个用途上转为实际生效。
- **用 36 次交互语料做离线 shadow 的计划**：
  - **语料**：v0.1 受控交互（30 次计划，加上校准和补充，共 36 次）的会话与 Claim 记录，客户为模拟，系统为真实；
  - **做法**：试运行结束后，离线逐条对用途一和用途二提问，结果写进一个独立的 shadow 证据集（§5 的格式，`decision` 字段记为 `shadow:<结论>`），不写回业务数据；
  - **对照**：用途一对照提取器的输出与人工复核；用途二对照交互中实际发生的人工接管、拒收后受限回复这几类场景；
  - **外发**：语料只含测试人设，外发前仍做掩码，并在隐私登记中写明这是一次性离线评估；
  - **产出**：每个问题的混淆矩阵、建议阈值、费用与时延。用来决定是否进入在线 shadow。

## 7. 风险与待负责人决定的事项

| # | 事项 | 说明 | 建议 |
|---|---|---|---|
| D1 | 是否在 beta 接口上建立依赖 | 接口为 beta，实测中出现过 60 s 无响应；接口与计费可能变化 | 只用于不阻塞主流程、失败即转人工的场景；适配器固定 beta 头与版本，接口变化时出新版本 |
| D2 | 数据外发的授权与登记 | 顾客原文发往外部服务，需要隐私登记与对应的授权依据 | 上线前完成登记；先只用离线 shadow（模拟客户语料） |
| D3 | 由哪个进程调用、走哪个出口网络 | 本稿建议新的 `decision-evaluator` worker，与 claim worker 共用 G-CLAIM-EGRESS 的出口 | 等 G-CLAIM-EGRESS 合入后确认参数名与网络 |
| D4 | 预算科目与上限 | 判断层单独记账，按 CNY 计 | 先设很低的月度上限，超过即进入“不确定 → 人工” |
| D5 | 校准不足时是否允许自动生效 | 概率贴近 0 或 1，高置信错误的风险 | 只有在标注集上高置信错误率低于约定上限时，才让某个问题自动生效；否则永远只是转人工的信号 |
| D6 | 是否另开方舟 key | 与对话模型分开限额与吊销 | 另开一把，单独限额 |
| D7 | 用途二是否进入 relay 的同步路径 | 会增加时延（实测 0.5 s，上限 1 s） | 先只在回复保障与工作台提示中使用；relay 同步路径等在线 shadow 结果后再决定 |
| D8 | 问题集与阈值的发布流程 | 版本化文件，由谁批准发布 | 与服务授权、告警规则一样，由负责人批准，经受信配置发布 |
| R1 | 供应商侧的数据保存与再训练 | 以其服务条款为准 | 在隐私登记中写明；条款不明确时，只用离线 shadow |
| R2 | 判断被当作事实使用 | 下游误把概率当结论 | 证据格式中 `decision` 与 `answers` 分开；业务对象只经受治理 Action 改动，判断只作为输入 |
| R3 | 注入与对抗样本 | 只测过一个注入样本 | 标注集中加入对抗样本；`injection` 判为是时一律转人工 |
| R4 | 费用失控 | 重复调用或循环 | 缓存键、幂等键、单次 token 上限、月度上限 |

## 8. 不在本稿范围内

- 任何代码、迁移、契约或 planning 改动；
- 对方舟接口的进一步调用（本稿只用了调度员已有的实测结果）；
- 把判断层用于生成回复，或用它替代 ADR-023 的硬规则。
