## 3. 切片 1 的设计

**SQL**：`runtime.nexloop_outreach_candidates(tenant, world, at)`，只读。
- 每个候选包含：`consumer_id`、`purpose`（`commitment_followup` / `service_followup`）、`origin_ref`、`dedupe_key`、`due_at` 或 `observed_at`，以及 `gates` 数组。
- `gates` 里每一项给出闸门名称、结论（`pass` / `refuse` / `not_wired`）、原因码和必要的细节。
- 汇总结论 `would_dispatch`：只有每道已接入的闸门都通过、且没有 `not_wired` 时才为 true。v1 因为外发 Action 尚未发布，这个值总是 false，会在细节里说明原因。

**候选来源**：
- **承诺跟进**：
  - 条件：Commitment 状态为 `open` 或 `in_progress`；
  - 时间窗：`due_at - lead_seconds` 已到点、`due_at` 未过，`lead_seconds` 取当前承诺设置，即 `commitments.v1` 的 3600 秒；
  - 去重键：`commitment_id + 'due_soon'`。
- **服务回访**：
  - 条件：服务类意图（非回复）在最近 24 小时内变为 `fulfilled`、`confirmed` 或 `failed`；
  - 去重键：`intent_id + 状态`。

**闸门预演**：按外联稿 §3.2 的顺序。

| # | 闸门 | 切片 1 的处理 |
|---|---|---|
| 1 | 控制面暂停 | 读 `control.nexloop_control_scopes`：租户 `*` 或该消费者被暂停 |
| 2 | 联系限制 | `control.nexloop_contact_restrictions` 生效即拒绝（NXC05 语义） |
| 3 | 目的与审批 | `not_wired`（切片 3、6） |
| 4 | 营销接收资格 | 不适用：切片 1 没有营销候选 |
| 5 | 测试人设 | `runtime.nexloop_consumer_persona≠real` 时拒绝（`persona_excluded`） |
| 6 | 租户勿扰 | 默认 21:00–09:00（O1：北京时间） |
| 7 | 租户频率 | 默认 24 小时 1 条、7 天 2 条，计数口径按 O2 |
| 8 | 消费者沟通偏好 | `runtime.nexloop_contact_preference_refusal`（人设链），channel 为原生 WebChat，topic 为目的 |
| 9 | 真实派发开关 | `control.nexloop_real_dispatch_closed_layer` 对 `nexloop.outreach.send:1` 的结论：该 Action 尚未发布，结论为关闭 |
| 10 | 预算 | `not_wired`（切片 4） |

**默认值**：`runtime.nexloop_outreach_defaults()` 返回勿扰时段、频率上限和时区，并在返回值里标明“默认值，切片 2 起由租户配置覆盖”。

**读取**：工作台 observe 动词 `outreach_candidates`，只对 owner 开放；路由为 `GET /api/v1/workbench/outreach-candidates`。只返回 ID、目的、时间和闸门结论，不返回消息正文或姓名。

**不做**：不写表、不建意图、不发送、不调用模型，不新增业务 Action，不改 `packages/contracts/`。

## 4. 切片 4 的落地方式

**路径**：沿用激励发放（AT-043）已有的受治理效应模式：自有意图台账、受理时取控制快照、执行端口在派发时准入、只有回环 provider。没有新增派发路径，也没有新凭据。

**受理**：负责人通过受治理入口提交 `outreach.send` / `send_outreach`（只限人类负责人）。
- 参数：`consumer_id`、`purpose`、`origin_ref`、`body`、`channel`（固定为 `native.webchat`），以及可选的 `conversation_id`。
- 服务端从当前目的清单冻结 `topic`、`purpose_version`、`frequency_class`。
- 业务意图 ID = `outreach:sha256(租户, 消费者, 目的, origin_ref, 租户时区的日期)`。同一天的重试或重复请求返回原意图；正文不同则拒绝（`intent_exists`）。
- 受理不发送，也不预留任何额度。

**派发**：执行端口 `nexloop.outreach.execute:1` 只授予领域 worker 服务。它在意图行锁和消费者级锁内依次检查：
1. 消费者不在删除中；
2. **联系限制最先检查**；
3. 请求人当前仍是有效成员，且角色仍含该 Action；
4. 负责人控制快照（NXC01/02/04）；
5. 闸门：目的（需要审批的目的在切片 6 之前一律拒绝）、营销资格、测试人设、租户勿扰、租户频率（含营销额度）、消费者偏好（主题前缀匹配）、三层真实派发开关（受理后开关有变更也算关闭）、模型预算。

任何一项拒绝都是终态，记录拒绝码和闸门结果，provider 收到的请求为零。结果未知时，先按意图 ID 查询，不重发。

**开关**：`nexloop.outreach.send:1` 的 Action 开关默认没有记录，即关闭。本片不打开开关。

**留给后续**：
- 执行服务主体及其授权、后台 worker 接入，属于打开真实外发的前置工作，须负责人作 B 类决定；
- 真实 WebChat 投递，以及物化为 Message、写入 `nexloop_outbound_messages`（P1 的 `origin_kind` 列，随投递一起做）；
- 拒绝写入统一的派发拒绝表（该表以效应意图为键；本片的拒绝留在台账和审计事件里）；
- 复评 Run 入口（切片 5）、审批（切片 6）、退订与同意记录（切片 7）。

## 附录 A：退订词表 v1（已审定，负责人 2026-10-20）

用途：外联稿 §4.4。只在**最近一条主动消息是营销目的**、且时间在窗口内（默认 30 天）时使用。命中后写入营销主题拒绝（`marketing`）；如果最近一条主动消息不是营销，按联系限制兜底。一般性的“别联系我”由现有拒绝规则（`contact-refusal-rules`）处理，这里不重复收录。

**发布**：可信配置 `deploy/configuration/unsubscribe-rules.v1.json`，格式与 `contact-refusal-rules` 相同：版本化、确定性匹配（PostgreSQL ARE，不区分大小写）、不调用模型、只增补不删减。整句匹配（`exact`）的词条写成 `^…$`，包含匹配（`contains`）的词条按字面转义。测试见 `tests/test_unsubscribe_rules.py`。入库与入站检查在切片 7 实现。

**审定结论**：收录 TD（按整句匹配）；保留第 8 条“别给我推”；恢复接收营销的说法另起一张表，在切片 7 起草；排除项“退款”维持，同时含退款和退订意思的消息交给正常回复链路。

**与现有拒绝规则的重叠（切片 7 之前需要负责人决定）**：现有的 `contact-refusal-rules.v1` 已经把“退订”“取消订阅”“unsubscribe”和整句“TD / stop”列为拒绝（规则 `unsubscribe`、`sms-stop-keyword`）。入站时拒绝规则先执行，命中后直接写入**联系限制**。所以客户在营销消息之后回复“退订”，今天得到的是全部主动触达停止，而不是外联稿 §4.4 设计的“只停营销”。要实现“只停营销”，需要发布拒绝规则 v2，在“最近一条主动消息是营销”时把这几条交给退订词表处理。这会放宽一条保护性规则，属于 ADR-023 范围内的变更，必须由负责人拍板。在此之前保持现状：更严，也更安全。

**匹配方式**（与拒绝规则一致）：
- 先做文本规范化：去掉首尾空白和标点，全角转半角，英文转小写；
- `exact`：整条消息规范化后与词条完全相同；
- `contains`：消息中包含该词条；
- 排除项先于命中项判断：消息含排除词时，不算退订。

**待负责人确认的问题**：
1. `TD` 是否收录。WebChat 用户可能不熟悉这个短信习惯，但收录后误伤的可能很小。
2. 第 8 条“别给我推”覆盖面较广，例如“别给我推荐了”也会命中。推荐保留：在营销消息之后，这类回复通常就是不想再收。
3. 恢复接收营销的说法（外联稿 §4.4，例如“以后可以给我发活动”）另起一张小表，在切片 7 起草，不放在退订词表里。
