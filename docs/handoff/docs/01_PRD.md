# NexLoop 产品需求文档（PRD）

版本 1.0｜状态：开发基线｜日期：2026-10-07。

## 1. 产品愿景与问题

NexLoop 探索在“关系持续连接”的长期目标下，企业怎样持续交付消费者愿意付费的价值。它不是群发营销工具、固定流程编排器或个人助理。它把运营负责人的目标、消费者真实状态、本体约束和历史证据组织成 Agent 的行动依据，让每一次行动产生可核验结果，再用于下一次对齐。

关系持续不等于持续打扰。用户拒绝联系、暂时沉默、结束付费或者没有合适的下一步，都可以是正确结果。模型能力不是衡量成功的唯一尺度；交付是否兑现、动作是否可靠、客户权益是否尊重和真实经营结果同样重要。

## 2. 冻结的用户决策

| 项目 | 决策 |
|---|---|
| 名称 | NexLoop |
| 形态 | 企业级开源项目，暂不绑定行业 |
| 顺序 | 真实运营及动作可靠性优先；模拟实验和策略选优后置 |
| 目标机制 | 人设长期/阶段 O、KR；Agent 自主分解并周期/事件对齐 |
| 自主边界 | 不默认逐动作人工批准；执行范围由 EIOS Action/Policy 强制限制 |
| 长期状态 | Goal、Ontology、Consumer、Relationship、Memory、Commitment 持久化 |
| Agent 组织 | N:M 角色关系，有界执行池，稀疏事件触发的短生命周期 Run |
| 数据规模 | 首版约 1,000 个消费者；并发测试确定，不预设永久配比 |
| 内核 | Pi Durable 执行；项目内 NEX-EIOS 本体与 Action；EvoOntology 选择性吸收 |
| 存储与交付 | PostgreSQL 默认；本地双机服务；本地 CI；GitHub 同步/备份 |

## 3. 用户与权限角色

**运营负责人**制定目标、预算和边界，观察偏离并干预。**运营人员/客户成功人员**处理例外、查看关系和履行交付。**消费者**通过被支持的渠道表达需求、偏好并接收服务。**系统维护者**管理部署、集成、模型、Schema 与版本。**研究者**在受授权的脱敏数据上比较上下文和策略。角色可合并，但权限不可隐式混用。

## 4. 范围与版本

**v0.1：可运营的真实闭环。** 至少一个租户、一个价值目录、一种真实交互渠道、一组受治理 Action、目标/计划/记忆/本体实例更新、承诺、经营事件接入和最小工作台。必须可以在没有专有云存储、没有 GitHub 在线 CI 的情况下部署。测试和演示模型使用显式 deterministic provider；真实模型凭据由运维注入。

**v0.2：语义与 Schema 的受控自演进。** 基于真实轨迹诊断缺口、提出候选、离线对比和受治理发布。先允许概念描述、别名、映射和上下文形状改进，再开放兼容性 Schema 扩展。

**v0.3：消费者数字孪生与实验选优。** 构建独立模拟世界、真实数据校准、候选策略筛选、影子运行及小范围真实实验。

**非目标。** 第一版不建设 Kubernetes、多机分布式 Harness、完整 CRM/ERP/支付网关、不自训练大模型、不支持任意浏览器代操作和无界 Shell、不承诺自动提高收入或通用外部动作 exactly-once，不把所有 23 个模块拆为服务。

## 5. 核心用户旅程

### J01：从消费者问题到持续价值

负责人发布目标。消费者在 Web Chat 报告使用问题。入站消息先持久化，系统组织目标、权益、历史问题及承诺，Agent 选择先提供服务而非促销。Action 核验后交付，提取器把新问题、联系偏好和承诺形成变更集并写入 EIOS。到期由新 Run 检查问题是否解决。之后独立付款事件到来，商业状态更新，旧续费提醒被取消。工作台能看到目标、依据、交付、付费与成本，但不会把这次先后关系直接宣称为因果。

### J02：暂停与恢复

负责人暂停某策略或消费者触达。暂停版本进入控制状态并使待执行项失效；正在推理的 Run 可以结束分析，但提交 Action 时必须被拒绝。外部已受理动作进入核对。恢复不是回放全部旧任务，而是创建新的评估需求。

### J03：对话导致模型结构缺口

多轮提取发现“有条件的承诺”无法表达。系统先检查已有类型和检索问题，再形成 Schema 候选。只在隔离环境评估，确定性兼容/权限/迁移检查通过后由 EIOS 发布；原始对话与证据不会因为模型结构暂缺而丢失。

### J04：异常恢复

消息渠道已接收动作，但进程在记账前崩溃。重启通过稳定业务意图 ID 查出已有执行，先核对外部状态。结果不明保持 unknown 并进入专用处理，不产生盲目第二次发送。

### M01｜企业、身份与租户

**范围：v0.1。** 管理员建立企业空间与运行环境，复用 NEX-EIOS 的身份、membership 和授权语义；保存时区、语言、数据策略和模型预算配置。

**输入与产出：** 输入为已认证会话或服务身份；输出为服务端解析的 TenantContext。API、任务、检索、Artifact 和运行实例全程携带经过验证的租户上下文。

**关键规则：** 不信任浏览器或模型提供的 tenant_id/scopes；无租户、membership 失效或授权服务不可用时拒绝。公共 API 请求体不接受替调用者提权的身份字段。

**验收：** 至少两个测试租户验证对象、向量、日志、导出、事件和 Action 的交叉访问均被阻止；无账号共享超级密钥。

### M02｜运营角色与责任

**范围：v0.1。** 负责人定义长期运营职责、目标范围、消费者集合和资源上限；角色定义独立于执行进程。支持角色与消费者 N:M。

**输入与产出：** 角色输出 run 的职责配置与授权上限；同一执行池可服务多种角色。

**关键规则：** 角色权限不自动叠加；代表人类执行必须使用明确 delegation，不能并入服务身份权限。角色不会为每个消费者创建常驻 Agent。

**验收：** 同一消费者可关联两个角色，但重复事件不会触发两个冲突触达；角色禁用后新执行被拒绝。

### M03｜目标、OKR 与指标定义

**范围：v0.1。** 负责人设置长期 O、阶段 O、KR、周期、优先级、预算与约束；Agent 提出自己的子目标、KR 和计划，并关联父目标版本。

**输入与产出：** 目标、KR 定义、观察值与来源分离。目标版本发布后不可原位覆盖，修改产生新版本。

**关键规则：** Agent 不得修改上层目标、统计口径、周期和目标值来宣布完成；KR 从经过批准的指标定义计算，不执行模型生成的任意 SQL。

**验收：** 所有 Run 能追溯目标版本；修改父 KR 后旧计划失效或重新对齐，历史进度仍能解释。

### M04｜持续对齐、干预与矫正

**范围：v0.1。** 周期和事件触发检查目标偏离、证据变化、预算和关系风险，产出 continue/replan/pause/stop/escalate 的结构化决定。

**输入与产出：** 负责人修改目标、约束、预算或暂停策略；变更产生版本与影响事件。

**关键规则：** 暂停必须影响排队任务和未提交动作；已经被外部系统接受的动作先核对或补偿，不声称能够撤销历史。重要约束执行前重验。

**验收：** 在任务等待期间撤销权限、改变目标或停止活动，唤醒后不能继续旧动作。

### M05｜消费者身份与档案

**范围：v0.1。** 保存消费者 canonical ID、渠道身份映射、基本属性、使用和产品关系。支持人工纠正身份、候选合并与拆分。

**输入与产出：** 正式消费者对象由 EIOS 持有，界面档案是受权限限制的读取视图。

**关键规则：** 姓名、表达和向量相似不等于同一人。未确认身份只能保持候选关系；高风险合并必须有确定性证据或授权的人工决策。

**验收：** 同名不同人不合并；跨渠道已验证身份可关联；重复导入不会重复创建消费者。

### M06｜关系状态与生命周期

**范围：v0.1。** 表达消费者与企业的关系、未解决问题、未兑现承诺、当前使用与联系状态；支持稳定、弱化、未知等带证据判断。

**输入与产出：** 关系事实和模型推测分别保存，状态包含证据、更新时间和有效范围。

**关键规则：** 不将长期无消息自动判为流失，不默认用单一亲密度分数决定触达。结束商业关系、拒绝联系也是有效终态。

**验收：** 工作台能展示状态依据，证据更正后关系判断可重算；不因提高活跃率而忽视拒绝联系。

### M07｜价值、产品、服务与权益目录

**范围：v0.1。** 定义企业实际可交付的产品、服务、内容、权益、适用条件、成本和交付证明。

**输入与产出：** 向 Context Engine 提供经筛选的供给信息；与 Action 定义及承诺关联。

**关键规则：** Agent 不能承诺目录外的保证、折扣或能力。价格、权益和预算变更使用受治理的业务接口。

**验收：** 示例至少包含一项可完成、可记录证据的真实服务；不能只有促销消息。

### M08｜交易与商业状态

**范围：v0.1 薄切片。** 接入订单、付款、退款、权益、取消、复购与续费事件；使用通用商业事件而非只支持订阅制。

**输入与产出：** 外部系统记录与验证来源进入证据层，正式商业状态经 EIOS 更新；历史金额保留币种。

**关键规则：** 客户自述付款、Agent 声称退款与已验证交易事实严格分开。测试付款、模拟付款不得计入真实经营指标。

**验收：** 签名商业 webhook 去重并核对；已付款事件使不再适用的提醒失效。真实持续付费结论需真实商业数据。

### M09｜触点、对话与联系偏好

**范围：v0.1。** 首版提供消费者 Web Chat、运营工作台和通用签名 webhook；外部渠道由 Connector 扩展。记录消息、发送者、附件、回执与 Run。

**输入与产出：** 保留原始内容、规范化内容与消息顺序；对渠道重投幂等入库。

**关键规则：** 促销、服务通知和用户主动请求分别分类。停止联系、静默期与频率约束在执行层生效，不能仅存进摘要。

**验收：** 重复消息不重复响应；断线重连后能读取已提交消息；未获证实的草稿不会显示为已发送。

### M10｜对话清洗与结构化提取

**范围：v0.1。** 标准化渠道格式、顺序、引用和时间；提取消费者陈述、偏好、需求、问题、条件性意图、承诺及推测。

**输入与产出：** 输入原始消息、相关对话和现有本体；输出带 evidence span、置信等级、时效与对象候选的 Claim 和 Mutation Proposal。

**关键规则：** 不删除反复投诉的语义；保留否定、条件、说话人和时间歧义。消费者内容是证据，不是管理指令。

**验收：** 从“解决后再考虑续费”不能提取“承诺续费”；提取重跑不重复创建同一个承诺。

### M11｜本体实例、关系与证据变更

**范围：v0.1。** 对变更集进行身份解析、时效、冲突、引用和权限检查；通过 EIOS 创建或更正对象、属性和关系。

**输入与产出：** 实例变更有稳定 proposal ID、expected_version、证据和应用结果；可关联事实冲突与更正链。

**关键规则：** 事实更新依据证据，而非“让模型评分更高”。晚到旧消息不能无条件覆盖新状态；正式写入只走受治理 Action。

**验收：** 同一变更重复提交最多形成一次业务变化；版本冲突返回409并重新取证，不盲目覆盖。

### M12｜本体结构与语义模型演进

**范围：v0.2；v0.1 留契约。** 分离概念解释变化、正式对象类型/属性/关系定义变化；形成候选、兼容检查、评估和版本发布流程。

**输入与产出：** EvoOntology 辅助诊断和提出局部候选；正式 EIOS schema 发布及迁移保持独立治理。

**关键规则：** 新增 Term 不等于新增 EIOS 类型；Schema 演进不授予 Action 权限。低风险扩展可自动通过规则，破坏性变更按维护流程处理。

**验收：** 候选不覆盖 active；缺少迁移/回归证据不发布；回滚语义版本不自动倒退真实业务事实。

### M13｜长期记忆与知识管理

**范围：v0.1。** 管理事件性记忆、业务知识、关系历史和策略经验；索引是派生视图，原始证据和正式本体各有权威归属。

**输入与产出：** 支持来源、有效时间、得知时间、版本、访问标签、过期、更正和删除。

**关键规则：** 混合检索先限定租户、消费者、世界和属性权限；不能将推测或模拟结果升格成真实事实。

**验收：** 删除或更正同步传播至摘要、关键词、向量和可访问的运行上下文；旧索引不绕过最新约束。

### M14｜上下文构建与语义访问

**范围：v0.1。** 组织目标、当前事件、消费者状态、问题承诺、相关证据、Action 与约束；按需调用语义发现/解析。

**输入与产出：** 产出 Context Manifest、实际模型请求快照和检索来源，记录策略、模型及语义版本。

**关键规则：** 关键约束主动提供，其他语义按需读取；信息不足明确表达；预算裁剪优先保留当前输入与执行约束。

**验收：** 每次模型调用可核对实际发送内容；不同 Context 策略可用同一评估集合比较。

### M15｜运营策略、计划与重规划

**范围：v0.1。** Agent 根据目标自主生成阶段策略和短期行动计划，定义依赖、等待条件、停止条件和复评时间。

**输入与产出：** Strategy、Plan、Run 与 ActionIntent 分别建模；计划可被新版本 supersede。

**关键规则：** “暂不行动”和“需要补充信息”都是正常结果；长等待由 PostgreSQL 唤醒重新评估，不维持一个跨月推理循环。

**验收：** 客户已经续费或问题已解决后，旧计划不继续盲目执行；每个行动能关联目标和证据。

### M16｜事件、任务与唤醒

**范围：v0.1。** 接收入站消息、商业结果、目标变化、到期检查等事件；执行去重、合并、优先级、公平性、租约和死信处理。

**输入与产出：** PostgreSQL 持久队列是任务权威，Valkey 通知只是加速；使用服务器时区转换后的 UTC due_at。

**关键规则：** 同一事件不能无限反复触发自身；后台提取、复盘和演进不得抢占全部交互槽位。

**验收：** Valkey 丢失或进程重启不丢已接受任务；过期租约被安全回收，旧持有者不能继续写。

### M17｜Action 治理与可靠执行

**范围：v0.1。** 由 EIOS 核验主体、权限交集、参数、目标状态、预算、联系约束、版本和业务幂等键，再执行外部或内部动作。

**输入与产出：** 保留意图、授权、尝试、接收结果、业务生效证据和对账状态。

**关键规则：** 不承诺通用 exactly-once；使用至少一次投递＋业务去重＋结果查询。超时可能是 unknown，不能当作失败自动重发。

**验收：** 在外部已生效但本地未记结果时强制崩溃，恢复不能产生重复效应；撤权及暂停执行前重验。

### M18｜承诺与价值交付

**范围：v0.1。** 把承诺作为一等对象，保存对象、内容、责任方、截止时间、条件、状态和履行证据。

**输入与产出：** 跟踪请求创建、已交付、客户确认与问题解决，不把这些状态合并。

**关键规则：** “消息发送成功”不等于“问题解决”；不允许无能力和无预算的承诺。

**验收：** 承诺到期触发复评与异常；工作台能指出未完成事项及其证据。

### M19｜效果、商业结果与成本

**范围：v0.1。** 分别衡量执行成功、客户价值、关系状态、付款/退款及成本；计算 KR 并保留数据来源和观察窗口。

**输入与产出：** Token/模型、渠道、优惠、服务和人工成本分别记录；收入币种不自动混算。

**关键规则：** 相关不等于因果；不把最后一条消息自动归因为付款原因；延迟结果按成熟窗口统计。

**验收：** 测试数据不混入真实经营面板；unknown 动作不计为成功；成本上限能实际阻断新消耗。

### M20｜负责人工作台

**范围：v0.1。** 提供目标、消费者、对话、计划、动作、承诺、知识、本体和异常视图，支持目标/边界/预算干预。

**输入与产出：** 默认显示“当前状态＋证据＋可执行控制”，不是聊天记录堆叠。

**关键规则：** 每个状态有来源与时间；危险管理行为有明确范围和审计；业务 Action 不以逐条审批为默认。

**验收：** 暂停与恢复可端到端验证；界面不把候选 Schema 显示为正式 Schema，不把模拟显示为真实。

### M21｜消费者数字孪生

**范围：v0.3。** 基于授权的真实历史构建可校准行为模拟器，支持同一消费者的多个假设版本与群体抽样。

**输入与产出：** 输入经过脱敏的世界快照；输出带来源与不确定性的模拟行为，不要求每个消费者常驻。

**关键规则：** simulation 的对象、事件、预算、凭据和 Action 与 real 隔离；孪生不是事实数据库。

**验收：** 测试环境不能调用真实发送和付款；模拟预测必须以独立真实数据校准，不能包装成确定概率。

### M22｜实验与评估

**范围：v0.1 回归；v0.2/v0.3 完整。** 首版具备提取、授权、上下文和执行回归；后续比较语义、Prompt、模型、规划与模拟策略，支持影子与受控线上实验。

**输入与产出：** 实验冻结输入、模型/策略/代码版本、预算、评价方法与留出集。

**关键规则：** 回放不重放真实副作用；同一消费者/相关对话避免跨训练与验证泄漏；候选评估成功不直接证明收入因果。

**验收：** 一次数据集和版本能复现测评条件；发布硬门槛与评分分开，任一关键约束失败即拒绝。

### M23｜审计、可观测与运行追溯

**范围：v0.1。** 串联 Event、Run、Goal、Context、Model Call、Mutation、Action、Outcome 和版本；提供指标、结构化日志和审计导出。

**输入与产出：** 记录可审计的依据摘要、工具输入输出和必要快照，不要求或伪造模型隐藏思考。

**关键规则：** 日志默认脱敏，原文受授权访问；审计追加不等于无限保留个人信息，删除遵循数据策略。

**验收：** 按 run_id 能还原发生了什么、使用了什么输入、哪些结果仍未知；告警不能泄露跨租户原文。

## 7. 成功指标与统计口径

产品研究主指标由部署企业选择：订阅续费率、复购率或持续付费消费者数，均须声明观察窗口、有效消费者集合、退款处理和数据成熟度。首版不设虚构商业提升目标。

系统验收使用技术与行为指标：已接受事件无静默丢失；规定故障集合中不发生重复外部效应；未授权/跨租户/模拟污染测试全部拒绝；关键联系限制及时落到执行检查；每个 ActionIntent 有目标、身份、参数和结果证据；回归集达到冻结的指标门槛。

示例续费率定义为“在选定窗口内到期且可续费的订阅中，在其到期日前后预先规定宽限期内有验证付款的比例”。分母按到期队列冻结，未成熟窗口单独列出，退款追溯规则由 MetricDefinition 固定。不能每次报告变化时重选分母。

## 8. 非功能需求

**可靠性。** 接受成功之前持久化；任务至少一次交付；关键写入幂等和版本检查；unknown 单独处理。组件停止时明确降级，不假装成功。

**安全与隐私。** 租户、主体、世界及属性级边界贯穿全链；凭据不进入 Prompt 和前端；数据最小化、可更正、可删除；第三方模型数据发送需企业明确配置。

**性能。** 见测试文档的初始目标：平台层（不含外部 LLM）入站 ACK p95 ≤500ms，普通详情读取 p95 ≤500ms；空闲交互队列调度 p95 ≤2s。这些是待验证指标，不是硬件现状承诺。整体 Agent 延迟按模型与工具分别报告。

**可移植性。** Docker Compose、明确依赖锁、通用环境变量、单机公开快速启动和双机私有部署；无不可开源的强制组件。

**可维护性。** 类型契约、依赖方向、迁移、来源许可、测试、ADR、故障排查和恢复手册随代码维护。

## 9. 产品级发布门槛

v0.1 不以页面齐全为完成。必须用两台主机上的独立 NexLoop 环境跑通 J01/J02/J04，并出具环境指纹、构建 SHA、迁移版本、测试结果、运行证据及恢复演练。至少一次真实模型调用和一项受控真实交付需标为真实验证；测试 webhook 和 deterministic provider 的结果单独标为 test。

尚未验证真实商业付款时，产品可以完成“可靠运营技术试运行”，但不能宣称已经验证“持续付费增长”。上线权限、真实渠道凭据缺失时继续完成无副作用任务，并将剩余验证记录为 blocked，不伪造完成。

## 10. 依赖与进一步细化

首阶段需确认现有源码的授权写入口、最小迁移图和 Artifact 适配；服务器 OS/资源、登录方式、镜像可达性、模型及渠道凭据由部署预检补齐。部署预检可以澄清未知运行环境，但不得推翻已经确认的产品方向或要求负责人逐步指挥 Agent。
