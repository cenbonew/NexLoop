# 事故复盘：签名命令因跨主机时钟偏差被拒（2026-10-21）

- **环境**：stage（两机：APP_HOST 运行应用进程，DATA_HOST 运行 PostgreSQL）。只用角色名。
- **级别**：stage 上所有依赖签名命令的后台处理停止；没有数据丢失，没有错发或重复发送。
- **修复**：热修复 `38d1a073`，合并提交 `56d2eb22`，作为**发布 24.1** 部署，只换镜像，没有 SQL 改动。
- **时间**：本文时间一律用 UTC，括号内为北京时间。

## 1. 影响

- **从 2026-10-20 21:31:53Z（北京 10-21 05:31:53）起**，stage 上所有带签名的后台命令都被 SQL 拒绝，涉及队列领取与完成、效应执行、Run 激活等。
- **结果**：新的 Run 无法启动或推进，客户来信得不到回复，效应停止派发。
- **没有发生的**：
  - 没有未经授权的写入：被拒的命令什么都没做；
  - 没有重复或错误的外部效应：效应在派发之前就被拒绝，真实派发开关也照常生效；
  - 没有数据损坏：恢复之后，积压的工作按原有的重试与对账路径继续处理。
- **持续时间**：从开始到发布 24.1 部署完成。部署完成的时刻以调度员的部署记录为准，记为 `<恢复时间>`。

## 3. 根因

- **签名的有效期上限两边算法不一致**：
  - 客户端（APP_HOST 上的各进程）签名时，`expires_at` 取**自己的** `now + 25 秒`；
  - SQL 端（DATA_HOST）要求 `expires_at ≤ clock_timestamp() + 25 秒`，用的是**数据库主机**的时钟。
- 两边用的是同一个 25 秒，没有任何余量。所以**只要 APP_HOST 的时钟比 DATA_HOST 快，哪怕只快 0.03 秒，每一个签名都会被拒**。
- 两台主机分别同步**两个不同的公共 NTP 源**，两者之间有正常范围内的小偏差，方向和大小会随时间漂移。21:31:53 前后，偏差的方向从“APP_HOST 稍慢”变为“APP_HOST 稍快”，签名从此全部越界。

## 4. 为什么以前没有暴露

- 在此之前，APP_HOST 的时钟一直与 DATA_HOST 相同或稍慢，客户端算出的 `expires_at` 总在 SQL 上限之内。
- 开发机和 CI 的测试，客户端与数据库在**同一台机器**上，用同一个时钟，偏差为 0，所以“恰好等于上限”的写法从来没有失败过。
- 没有测试覆盖“客户端时钟比数据库快”的情况，也没有检查跨主机的时钟偏差。

## 5. 修复（发布 24.1）

- 新增常量 `SIGNED_COMMAND_TTL = 20 秒`（`nexloop_eios.signing`）。32 个模块中的 40 处签名有效期都改为使用它，客户端与 SQL 上限之间留出 **5 秒余量**。
- **不改的**：
  - SQL 的 25 秒上限不变；
  - 效应执行中的 Action 领取租约 `lease_expires_at` 不变，因为它是租约，不是签名有效期。
- **没有迁移**：部署只换镜像。
- **测试** `tests/test_signing_clock_skew_pg.py`：
  - 客户端时钟快 3 秒时，队列与效应执行的签名被接受；
  - 快 6 秒时被拒：这是对 SQL 上限不变的阳性对照；
  - 每个签名模块都使用 `SIGNED_COMMAND_TTL`，不再有写死的 25 秒签名上限（参数化检查）。

## 7. 遗留

- **NTP 源不改**（负责人决定）：两台主机仍然同步两个不同的公共 NTP 源。5 秒余量足以覆盖正常的偏差；偏差的监测由上面的部署后检查承担。
- **余量的上限**：如果两台主机的偏差超过 5 秒（例如某一台的时间同步失效），签名会再次全部被拒。部署后检查的告警阈值应当低于 5 秒。
- **“恰好等于上限”的同类写法**：本次只处理了签名有效期。其他客户端与 SQL 使用同一个时间上限、没有余量的地方，留待代码评审时逐项排查。
- `<恢复时间>` 与积压的消化情况，由调度员按部署记录补上。
