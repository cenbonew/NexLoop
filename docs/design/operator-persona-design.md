## 0. 借鉴什么

OpenClaw/Muse 一类文件式 Agent 把“我是谁、怎么说话、主动联系的偏好”写成几份可读文件，例如 `SOUL.md`、`IDENTITY.md`、`PROACTIVE_PREFERENCES.md`。Agent 每次启动时读入，人可以直接编辑。值得借鉴的有三点：

- **身份与说话方式是独立、可读、可版本化的工件**，不散落在提示词里；
- **偏好是一份持续存在的“事实”**，每次行动前都要读；
- **编辑权在人**。

NexLoop 不照搬“Agent 读写本地文件”。原因有两个：运行时没有数据库凭据，也不能自改配置；业务事实只存在 PostgreSQL。具体对应如下：

| 文件式 Agent | NexLoop |
|---|---|
| `SOUL.md` + `IDENTITY.md` | **运营人设**：受治理的版本化配置，负责人批准发布（§2） |
| Agent 自己改文件 | Agent 只能**提候选**，走候选与审核流程（§2.4） |
| `PROACTIVE_PREFERENCES.md` | **沟通偏好**：来源是消费者自己的陈述（Claim），在**派发时强制执行**（§4） |
| 启动时读文件 | 每次 Run 把“人设@版本”和适用偏好放进上下文包，并记入轨迹（§3.4） |

## 2. 运营人设

### 2.1 内容

一份人设回答四个问题：“我是谁”“怎么说话”“坚持什么”“什么时候用”。

| 部分 | 字段 | 说明 |
|---|---|---|
| 身份（IDENTITY） | `display_name`、`signature`、`self_intro` | 消费者看到的名字、消息署名、首次自我介绍。必须是运营身份，不能冒充某个真实员工，见 §5 |
| 语气（SOUL） | `tone`（例如亲切、专业、简洁）、`values`（三到五条，例如“先解决问题再解释”“不确定就说不确定”） | 用自然语言写，进入上下文 |
| 表达规则 | `length`（单条消息字数上限、分段方式）、`vocabulary`（偏好用词、称呼方式）、`emoji`（不用、少用、可用）、`forbidden_phrases`（禁用说法列表）、`language` | 可以机器检查的部分（长度、禁用说法、表情）在出站前检查，见 §3.5 |
| 适用场景 | `scenarios`（例如售后、续费提醒、首次接待）、`not_for`（不适用场景） | 供分配规则和 Agent 判断使用 |
| AI 身份话术 | `ai_disclosure`（按租户配置填写的话术，见 §6） | 默认为空，表示不主动表明 |

人设**不包含**任何价格、折扣、权益、服务范围或承诺能力。这些仍由供给、商业规则和受治理 Action 决定，见 §5。

### 2.2 治理

- **形态**：受治理的可信配置。每份人设是 `operator-persona` 文档，标识为 `persona_id@version`，每个版本不可变。草稿、发布、停用状态和每次变更都留证。
- **发布**：只能由负责人经新 Action `nexloop.operator_persona.publish:1` 发布。发布时做结构校验（字段、长度、禁用说法格式）和底线校验（§5）；不通过就拒绝。
- **停用**：已分配给消费者的人设被停用时，这些消费者按分配规则回落到默认人设，回落记录原因 `persona_retired`，见 §3.3。
- **Agent 不能自改**：运行时没有任何写人设的工具。Agent 认为某个说法效果不好时，只能**提候选**（§2.4）。

### 2.3 存储位置

| 方案 | 说明 |
|---|---|
| (a) 正式对象 `OperatorPersona`（EIOS 本体，版本由对象修订表达） | 可以复用对象读取和审计；但人设是“配置”而不是“业务事实”，并且需要“版本不可变、按版本引用” |
| (b) 控制面配置表（与上下文策略同一模式：`control.nexloop_operator_personas`，以 `persona_id` 加 `version` 为主键，内容不可变，发布 Action 写入） | 与 `context-strategy:<id>@<ver>` 同构，引用简单，天然支持“按版本复现” |

推荐 **(b)**，见 D2。

### 2.4 Agent 提候选

- 新工具 `propose_persona_change`，只在复评 Run 和审核类角色中提供。参数包括：目标人设、建议修改的字段、理由，以及证据（会话或消息 ID、指标）。
- 候选写入现有候选与审核队列（NX-045/046）的一个新类别 `operator_persona`。负责人在工作台看到差异和证据：采纳就生成新的草稿版本，再走发布流程；拒绝则记录原因，并有冷却期。
- 候选**永远不会**直接改变正在使用的人设。

## 3. 千人千面的分配

### 3.1 分配层级（优先级从高到低）

1. **负责人对单个消费者的指定**：`assign_operator_persona(consumer, persona_id)`，需要写原因。
2. **分群规则**：规则引用消费者的正式属性或分群标签，例如会员等级、渠道、语言、所属角色。规则按顺序匹配，第一条命中的生效。规则本身也是版本化的可信配置 `persona-assignment-rules.v<N>`，由负责人发布。
3. **租户默认人设**。

分配的结果只有一个：`persona_id`，**版本跟随该人设当前的发布版本**。消费者“用的是哪一个人设”是稳定的；人设内部的措辞迭代则通过新版本统一生效，不需要逐个重新分配。

### 3.2 消费者偏好的微调

- 消费者明确说出的沟通偏好，例如“说简单点”“别发表情”“叫我王先生就行”“用英文”，按 `epistemic_kind=preference`、`speaker=consumer` 提取为 Claim，与 §4 的沟通偏好同源。
- 这些 Claim **只在人设允许的范围内微调表达**：长度更短、不用表情、称呼方式、语言。它们**不能**改变人设的身份、价值观、禁用说法和底线。
- 出现冲突时，以消费者偏好为准，只要它没有越过人设的硬规则。例如消费者要求“随便点，可以骂人”，这条偏好不生效，并在上下文中标注“偏好未采纳：越过表达规则”。

### 3.3 稳定性与更换

- 同一消费者的人设在没有更换事件时不变。任何更换都写一条 `persona_assignment_event`，内容包括原人设、新人设、来源、原因和执行人。来源取以下之一：

| 来源 | 含义 |
|---|---|
| `owner_assign` | 负责人指定 |
| `rule_change` | 规则新版本命中了不同的人设 |
| `persona_retired` | 原人设被停用 |
| `experiment_arm` | S7 实验分组 |

- **规则变更的影响**：分群规则发布新版本时，先给出“影响预览”，列出多少消费者会更换、从哪个人设换到哪个人设。负责人确认后才生效；生效时为每位受影响的消费者写一条事件。
- **会话内不切换**：一次进行中的会话（最近 N 小时内有往来）沿用会话开始时的人设版本，下一次会话再切换，避免同一段对话里口吻突变。
- 消费者被设为联系限制后，人设分配保留，但不再有任何主动触达。

### 3.4 进入上下文与轨迹

- 上下文包 v6 新增一节 `operator_persona`，属于固定必含项，不参与裁剪。内容包括：
  - `persona_ref`：`operator-persona:<id>@<version>`；
  - 人设正文：身份、语气、表达规则、适用场景；
  - 本次生效的偏好微调，每条都指向其 Claim ID；
  - 未采纳的偏好及原因；
  - AI 身份配置（§6）。
- Context Manifest 记录 `persona_ref`、分配来源以及分配事件 ID。轨迹中的每次 Run 都能查到“用了哪个人设的哪个版本、为什么是它”。
- **S7 实验**：实验以 `experiment_arm` 为来源写分配事件；指标（回复率、满意度、拒绝联系率、转人工率）按 `persona_ref` 聚合。`persona_ref` 进入 Run 结果的维度，便于离线对比与线上 holdout。

### 3.5 出站前的机器检查

模型生成的回复或主动消息在提交外发 Action 之前，由确定性检查器按人设的可检查规则逐条检查：

- 单条长度上限；
- 禁用说法（精确匹配或正则）；
- 表情策略；
- 是否声称自己是真人（§6）。

不通过的处理：交回 Run 修改一次；仍不通过，则按回复保证的兜底路径处理，或者转人工。检查结果写入轨迹。

人设里的语气与价值观无法用规则检查，只进入上下文，不做拦截。

## 4. 消费者沟通偏好

### 4.1 内容与来源

| 维度 | 例子 | 强制方式 |
|---|---|---|
| 时段 | “工作日晚上别找我”“只在周末联系” | 派发时检查：落在消费者偏好的禁止时段内，主动外发被拒（`preference_quiet_window`） |
| 频率 | “一周最多一次” | 派发时检查：与租户频率上限取更严者（`preference_frequency`） |
| 渠道 | “只在微信里说”“别打电话” | 派发时检查：渠道不在允许范围内即拒绝（`preference_channel`） |
| 主题 | “别给我推活动”“续费的事可以提醒我” | 派发时检查：外联目的属于消费者拒绝的主题时拒绝（`preference_topic`），目的与主题的映射写在外联稿的目的清单中 |
| 语气 | “说简单点”“正式一点” | 进入上下文，参与 §3.2 的微调；出站前长度规则按偏好收紧 |

- **唯一来源是消费者自己的陈述**：`speaker=consumer`，`epistemic_kind ∈ {preference, constraint}`，`modality ∈ {asserted, requested}`。Agent 的推测（`hypothesis`）不能成为可强制执行的偏好；它只能出现在上下文的假设区，不参与派发检查。
- **从 Claim 到偏好**：新增一个确定性的投影，可以由 SQL 实现，也可以是一个受治理的物化步骤。它从已解析（resolved）的偏好类 Claim 生成 `consumer_contact_preferences`，每行包括：维度、规则（结构化值）、来源 Claim ID 和生效时间。
  - 无法结构化的陈述，例如“晚点再说”，不生成可强制执行的规则，只进入上下文；
  - 时间类偏好使用 Claim 的 `valid_time` 归一结果；结果为 `ambiguous` 或 `unresolved` 时不生成规则。
- **更正与撤回**：消费者更正（`correction`）或说出相反的偏好时，新的 Claim 取代旧的（`superseded`），投影随之更新。消费者删除请求（NX-029）会清除这些偏好。
- **可见与可改**：工作台的消费者详情页显示当前生效的偏好及来源原话（按 ADR-025 记录成员读取）。负责人可以把某条偏好标为“不采纳”，需要写原因，但不能凭空新增偏好；偏好只能来自消费者本人。

### 4.2 与联系限制、拒绝的关系

强弱顺序固定，越靠前越硬：

1. **联系限制 / 明确拒绝**（ADR-023）：消费者说“别联系我”时，写入联系限制，一切主动触达停止，只有负责人能解除。偏好**不能**放宽它；“客户要求的提醒”也不例外，见外联稿 P6。
2. **租户控制**：暂停、勿扰时段、频率上限、真实派发开关、预算。
3. **消费者沟通偏好**：只能在 1 和 2 允许的范围内**进一步收紧**，例如把租户的每周 2 次收紧为每周 1 次，或增加禁止时段。偏好永远不能放宽租户控制。
4. **运营人设**：只决定“怎么说”，不决定“说不说、何时说”。

区分规则：

- “别给我推活动”是**主题偏好**，不是联系限制。它只挡营销目的，服务回访、承诺跟进照常进行。
- “以后都别联系我”是**拒绝联系**，走 ADR-023 的联系限制。
- 对于含糊的陈述，现有拒绝规则（`contact-refusal-rules.v1.json`）的判定优先：命中拒绝规则就是联系限制，否则才考虑作为偏好。

**回复不受时段和频率偏好约束**：消费者来信时的回复属于回复保证，不受时段与频率偏好限制，否则“消费者问了却不回”。渠道偏好仍然适用，回复走消费者来信的那个渠道。

### 4.3 派发时检查的位置

外联稿 §3.2 的闸门链新增偏好闸门。顺序为：控制面暂停 → 联系限制 → 目的与审批 → 测试人设 → 租户勿扰 → **消费者时段偏好** → 租户频率 → **消费者频率偏好** → **渠道偏好** → **主题偏好** → 三层真实派发开关 → 预算。

- 每道闸门拒绝时写入派发拒绝记录，包括闸门名称、规则版本、来源 Claim ID 和计数快照。provider 收到的请求为零。
- 检查在派发事务内读取**当前**的偏好投影，而不是规划时的快照。这满足 AGENTS 的要求：在派发时执行当前约束，而不只是在规划时执行。

## 5. 底线（人设不能覆盖）

以下规则写在代码和派发检查里，人设、分群规则和偏好都不能改变。人设发布时校验，出站前再检查一次：

1. **不使用操纵性话术**：
   - 不制造虚假紧迫，例如“只剩最后 1 个名额”而事实不是这样；
   - 不利用愧疚或恐惧施压；
   - 不虚构社会证明；
   - 不在消费者拒绝之后反复劝说。

   人设的 `forbidden_phrases` 只能**增加**禁用项，不能删除平台底线里的禁用项。平台底线是一份版本化配置 `communication-baseline.v1`，人设不能修改它。
2. **联系限制与拒绝优先**：见 §4.2 第 1 条。
3. **千人千面只作用于沟通方式**：
   - 人设、分群规则、偏好**不进入**价格、折扣、权益、服务范围、退款与补偿的计算；
   - 这些计算的输入中不能出现 `persona_ref` 或人设字段，在受治理 Action 的参数校验中强制执行；
   - 同一服务对不同人设的消费者给出相同的事实与条件。
4. **不冒充真实的人**：人设的名字和署名不得使用真实员工的姓名或照片；如果使用“客服小李”这类称呼，也只是一个运营身份。是否说自己是人类，见 §6。
5. **事实不受人设影响**：人设可以改变措辞，不能改变事实陈述。不确定的事说不确定，未确认的事不说成已确认。这与 v0.1 回执措辞的原则一致：“已接受”不代表“已履行”。

## 6. AI 身份披露

**负责人原话（2026-10-19）**：“是否让消费者知道是 AI，由使用方决定，不是 NexLoop 决定，默认不表明。”

### 6.1 租户级配置

`ai_disclosure`，属于租户级受治理配置，由负责人经 Action 修改并留证：

| 字段 | 取值 | 默认 |
|---|---|---|
| `mode` | `none`（不主动表明）；`first_contact`（首次接触时表明一次）；`always`（每次会话开始时表明） | `none` |
| `statement` | 表明时使用的话术，例如“我是 XX 的智能助理” | 空 |
| `when_asked` | 被直接问到“你是不是真人或 AI”时怎么处理，见 D7：`truthful`（如实回答）、`handoff`（转人工）、`deflect`（按话术回避） | `truthful` |
| `deflect_statement` | 选择 `deflect` 时使用的话术，例如“我是 XX 的服务助手，有什么可以帮您” | 空 |
| `content_label` | 是否在消息上加“AI 生成”标识（渠道支持时） | 关 |

- 人设里的 `ai_disclosure` 话术引用租户配置，不能自行决定 `mode`。
- **合规责任**：不同法域对 AI 生成内容的标识、聊天机器人身份披露有不同的要求。是否合规由使用方负责；NexLoop 提供开关、话术和留证（每次表明或回避都记入轨迹）。部署文档和工作台的配置页需要写明这一点。

### 6.2 被直接问到时（D7 推荐）

消费者真诚、直接地问“你是真人吗？”“你是不是 AI？”时：

- **系统不允许否认自己是 AI，也不允许声称自己是人类**。这一条写在平台底线里（§5），租户不能关闭。
- 在此前提下，租户可以选择如实回答（默认）、转人工，或按配置的话术回避。回避话术也不能包含“我是真人”这类陈述。
- 出站检查器（§3.5）拦截“我是真人”“我不是机器人”一类的陈述；被拦截时按 `when_asked` 的配置重写或转人工。
- 判定“真诚直接地问”：由模型在 Run 中判断，同时由一个确定性的关键词初筛兜底；兜底一旦命中，就强制执行 `when_asked`。

## 7. 与已有部分的关系

| 已有部分 | 关系 |
|---|---|
| **角色**（`RoleDefinition`、`ConsumerRoleLink`） | 角色决定“做什么、能做什么”，人设决定“怎么说”，两者正交。分群规则可以引用角色，例如“售后角色默认用人设 A”，但人设不进入角色的权限上限 |
| **Claim**（NX-019/020） | 偏好类 Claim 是沟通偏好（§4）和人设微调（§3.2）的唯一来源。假设不能成为可强制的偏好。AT-064 边界不变：偏好投影只读取已解析的偏好类 Claim 的结构化值，不进入正式业务事实 |
| **上下文包 v6 / 策略**（NX-023） | 新增必含节 `operator_persona`；Manifest 记录 `persona_ref`。需要 v6 的增量版本，或升级到 v7，见 D5 |
| **外联稿** | 外联稿的勿扰与频率是**租户级**控制，本稿的偏好是**消费者级**的进一步收紧，两者在同一条闸门链上（§4.3）。主动消息同样使用消费者的人设、经过出站检查。外联稿 §3.3 的“附上退订方式”保留，属于平台底线，人设不能删除 |
| **测试人设标记**（ADR-034） | 正交。测试消费者同样有运营人设，以便测试人设效果；它们的指标不进入真实聚合（ADR-034 §3） |
| **候选与审核**（NX-045/046） | 新增候选类别 `operator_persona`（§2.4） |
| **联系限制**（ADR-023） | 优先级最高（§4.2）；偏好不能放宽它 |
| **S7 实验**（NX-041~043） | 分配来源 `experiment_arm`；指标按 `persona_ref` 聚合 |

## 10. 实施切片（拍板后）

1. 契约与平台底线配置 `communication-baseline.v1`；人设版本表、发布 Action、发布时的结构与底线校验；租户默认人设。
2. 分配：单人指定、分群规则与影响预览、分配事件；上下文 `operator_persona` 节；Manifest 写入 `persona_ref`。
3. 出站检查器：长度、禁用说法、表情、“自称真人”；租户 `ai_disclosure` 配置与 `when_asked` 处理。
4. 偏好：从 Claim 到投影、更正与删除传播；工作台查看与“不采纳”。
5. 派发闸门：四道偏好闸门，与外联稿的闸门链合并实施。
6. 指标按 `persona_ref` 聚合；S7 实验分组（`experiment_arm`）。
7. （v2）Agent 提候选与审核类别。

**验收要点**：
- 未发布或已停用的人设不能被分配；Agent 没有任何改人设的路径。
- 每次 Run 的 Manifest 中有 `persona_ref` 与分配来源；同一消费者在没有更换事件时 `persona_ref` 的 `id` 不变；每次更换都有事件与原因。
- 消费者的时段、频率、渠道、主题偏好在派发时各自拒绝，provider 零请求；偏好收紧有效，放宽无效；联系限制下偏好不起作用，一律拒绝。
- 回复不受时段、频率偏好约束。
- 出站检查拦截禁用说法和“自称真人”；被直接问到是否 AI 时，任何租户配置下都不会出现“我是真人”。
- 同一服务对不同人设的消费者，价格、权益和服务条件逐项相同（对比测试）。
- 消费者删除后，偏好投影清除，分配事件只保留 ID。
