结论：今天的系统里，复评 Run 可以调用不触达客户的 Action，但没有任何路径能“先开口”给客户发消息。这是有意的（ADR-023），不是缺陷。本设计在不削弱 ADR-023 的前提下，增加一条**单独的、默认关闭的**主动外发路径。

## 1. 目标与非目标

**目标**
- 系统在没有来信的情况下，可以就**目的清单里登记的目的**给客户发一条消息，开启或续接对话。目的包括承诺跟进、服务回访、计划自定义目的、营销（P2）。
- 只经 EIOS 受治理 Action 和效应路径；派发时逐道检查（§3.2），每一道的通过或拒绝都留证。营销目的的检查一条不少。
- 客户回复后进入现有来信链路，ADR-023 的回复保证照常生效；客户表示不想再收，自动转成联系限制或主题偏好（§4.4）。

**非目标（v1）**
- 批量群发活动与 A/B 测试编排。营销消息仍是“一个客户一条、经复评 Run 判断”的路径，不提供按名单批量下发的入口；实验分组留给 S7。
- 绕过联系限制的任何例外，包括“客户自己要求的提醒”（P6，见 §4.3）。
- 新渠道。v1 只用现有 WebChat 外发通道，渠道 API 的回推另立任务（consumer-channel-api D4）。

## 2. 触发来源与目的清单

主动外发**不由新的定时器直接发出**，而是复用计划复评：触发源只负责“标记计划需要复评并说明目的”；是否外发、说什么，由一次有界 Role Run 判断。它可以判断“不行动”，满足 AT-029。

| 触发源 | 条件（确定性，SQL 判定） | 去重键 | 允许的目的 |
|---|---|---|---|
| 承诺到期前（commitment-keeper） | `due_at - lead_seconds` 到点，承诺仍为 open/in_progress，且有可回报的证据或需要确认 | `commitment_id + stage` | `commitment_followup` |
| 服务/工单回执（外部结果） | 企业交付或服务请求的回执由“未知/进行中”变为“完成/失败” | `intent_id + provider_state` | `service_followup` |
| 计划 `reassess_at` 到点 | 计划设定的复评时间到期，计划未关闭、未暂停 | `plan_id + reassess_at` | 计划声明的目的，必须在清单里登记 |
| 负责人发起（工作台） | 负责人对单个客户发起“联系一次”，填写目的与原因 | `request_id`（稳定业务意图 ID） | 清单内任一目的 |

**目的清单**（`proactive-purposes.v<N>.json`）：
- 可信配置，有版本，由负责人经受治理 Action 发布，每个版本不可变。不在当前清单里的目的，派发时拒绝（`purpose_not_allowed`）。
- 每个目的包含以下字段：

| 字段 | 说明 |
|---|---|
| `purpose_id` | 例如 `commitment_followup`、`service_followup`、`renewal_reminder`（计划自定义）、`marketing_new_product`（营销） |
| `kind` | `commitment_followup` / `service_followup` / `plan_defined` / `marketing` |
| `topic` | 主题，用于消费者主题偏好的匹配（§3.2）。营销目的的主题必须以 `marketing` 开头，例如 `marketing`、`marketing.new_product` |
| `description` | 给负责人和 Role Run 看的说明 |
| `requires_approval` | 是否需要人工审批，默认 `false`（P5）；为 `true` 时见 §3.4 |
| `frequency_class` | 计入哪个频率桶：`service` 或 `marketing`（营销可设更严的上限，§3.2） |
| `content_rules` | 文案约束：长度上限、必须包含的内容（营销必须带退订说明，§4.4）、禁止的内容 |
| `requires_consent` | 仅营销可设：为 `true` 时，这个目的按 opt-in 处理，只有记录了营销同意的客户才能收到，即使租户是默认的 opt-out；默认 `false`，跟随租户的同意模式（§4.5） |
| `active` | 是否启用 |

- **计划自定义目的（P2）**：计划可以声明自己的目的，例如“续卡提醒”，但这个目的必须先在清单里登记。登记由负责人发布新版清单完成，Agent 不能新增目的。计划引用一个未登记或已停用的目的时，复评预检直接判定“不行动”，并记录原因 `purpose_unregistered`。
- 自触发约束沿用 `plan-reevaluation`：同一计划由自身 Run 引起的复评，10 分钟内至多 2 次。

## 3. 受治理的外发路径

### 3.1 新 Action 与记录

- 新增受治理 Action `nexloop.outreach.send:1`：
  - 效应类别 `customer_contact`，`external_effect=true`，受三层开关约束；
  - 参数：`consumer_id`；`conversation_id`（可空，P4：30 天内有会话就续接，否则由服务端新建）；`purpose`；`origin_ref`（触发源引用：承诺 / 回执意图 / 计划 / 负责人请求）；`body`（模型生成，有长度上限）；`channel`（v1 固定为 WebChat 原生通道）。
  - 服务端还会把 `topic` 写入冻结请求，取自目的清单，不由调用方填写。人设稿里的偏好检查读取的就是冻结请求中的 `channel` 和 `topic`。
  - 业务意图 ID = `sha256(tenant, consumer, purpose, origin_ref, 日窗口)`，重试和重启不会产生第二条。
- 外发记录（P1）：`nexloop_outbound_messages` 增加 `origin_kind ∈ {reply, proactive}`。
  - `reply`：`trigger_message_id` 必填，现状不变；
  - `proactive`：`trigger_message_id` 为空，`origin_ref`、`purpose`、`purpose_version` 必填；
  - CHECK 约束保证二者互斥。投递状态，以及渠道接受后物化为 Message 对象（`Message.agent_create:1`），都沿用现有路径。
- 只有复评 Role Run（经 guard 的工具）和负责人工作台的受治理入口能提交这个 Action。兜底回复 Run 不能提交，ADR-023 §2.7 不变。

### 3.2 派发时检查

顺序固定。任何一道拒绝都不会发出，provider 收到的请求为零。

| # | 闸门 | 规则 | 拒绝码 |
|---|---|---|---|
| 1 | 控制面暂停 | 租户、消费者、计划被暂停 | 现有码 |
| 2 | 联系限制 / 拒收 | 消费者处于联系限制时，`proactive` 一律拒绝，不存在绑定放行。退订也会落成联系限制（§4.4） | `contact_restricted`（NXC05） |
| 3 | 目的与审批 | 目的在当前清单里且启用；目的要求审批的，必须有已批准的审批记录（§3.4） | `purpose_not_allowed` / `approval_required` |
| 4 | 营销接收资格 | 仅营销目的。租户为 opt-out（默认）时：客户没有退订记录、没有拒绝营销主题，即可发送；一般性的“别联系我”已在第 2 道拦下。租户为 opt-in，或该目的 `requires_consent=true` 时：还必须有客户的营销同意记录（§4.5） | `marketing_opted_out` / `marketing_consent_missing` |
| 5 | 测试人设与数据模式 | 测试人设（ADR-034，`persona≠real`）或租户 `data_mode='test'` 只能走测试世界的 provider，见 §6 | `persona_excluded` |
| 6 | 租户勿扰 | 租户时区内的勿扰窗口，默认 21:00–09:00（P3） | `quiet_hours` |
| 7 | 租户频率 | 每客户 24 小时内至多 1 条、7 天内至多 2 条（P3），在派发事务内原子计数；营销桶可设更严的上限 | `frequency_capped` |
| 8 | 消费者沟通偏好 | 人设稿 §4 的四道检查，只会更严：消费者陈述的勿扰时段、频率、渠道（只用 / 不用）、主题（拒绝某主题）。主题偏好按前缀匹配，客户说“别给我推活动”即拒绝主题 `marketing`，覆盖所有 `marketing.*` 目的 | `preference_*`（NXC06） |
| 9 | 三层真实派发开关 | 部署 / 租户 / `nexloop.outreach.send` 的 Action 开关 | `real_dispatch_closed` |
| 10 | 预算 | 效应单位预留与模型预算 | `budget_exhausted` |

- 所有检查都放在现有派发检查链上（`nexloop_assert_dispatch_controls` 与 `control.nexloop_contact_assert_intent`），不新增派发路径。所有拒绝写入派发拒绝表，记录闸门、规则版本、计数快照和来源 Claim。
- **租户控制（P3）**：勿扰时段、频率上限、租户时区是 NX-022 控制面的新控制。可信配置写默认值，负责人在工作台用受治理 Action 调整，修改有版本、留证。租户时区也供人设稿的偏好时段使用；目前那里固定为北京时间。
- **偏好与租户控制的关系**：偏好只能收紧（人设稿 D9）。例如租户规定每 7 天 2 条，消费者说“一周最多一次”，实际按 1 条执行；消费者说“随时都可以”，不放宽租户的勿扰时段。
- **营销没有任何豁免**：营销目的走完全相同的 1–10 道检查，另外多一道第 4 道接收资格检查和第 7 道里的营销桶。默认 opt-out 下，客户主动表示不同意的三种方式（退订、拒绝营销主题、“别联系我”）分别由第 4、8、2 道拦下，任何一种都足以停止营销。

### 3.3 内容生成

- 文案由复评 Role Run 生成。Run 的上下文包括：
  - 目的及其清单条目；
  - 触发源证据（承诺 / 回执 / 计划）；
  - 客户画像与钉住的约束、会话近况；
  - **人设节**（人设稿 §3.4，`operator-persona:<id>@<版本>`、AI 身份披露配置、消费者偏好）。

  工具只多一个 `send_proactive`。
- 文案规则：
  - 只说与目的相关的内容，不承诺新的服务；
  - 按人设的表达规则写，出站前做人设稿 §3.5 的机器检查；
  - 遵守目的的 `content_rules`；
  - **营销消息必须带退订说明**（§4.4），由服务端在正文末尾追加固定话术，不依赖模型是否写了。
- 人设和千人千面只影响措辞，不影响价格、权益和服务条件（人设稿 §5）。营销消息中出现的价格或优惠必须来自供给与商业规则，并作为结构化证据进入上下文。

### 3.4 可选审批（P5）

- 默认不审批。目的清单里 `requires_approval=true` 的目的，复评 Run 提交的外发意图先进入“待审批”，不派发。
- 负责人在工作台看到正文、目的、触发证据和人设版本，选择“批准”或“拒绝”。两者都是受治理 Action，必须写原因，留审计。
- 批准后按正常派发检查执行，**派发时重新检查全部闸门**：审批期间客户可能已经拒绝联系。拒绝或超过审批时限（可配置，默认 24 小时）的意图终止，不发送。

## 4. 回复保证（ADR-023）与客户的回应

### 4.1 主动外发本身不登记“待回复”

“待回复”是对**客户来信**的承诺。主动外发没有来信，因此不登记“待回复”，也不会触发兜底回复 Run。它的保证是**投递保证**（§7）。

### 4.2 客户回复之后

- 客户对主动消息的回复是普通来信：受理、保护性检查、登记“待回复”、兜底回复，全部照现状执行。
- v6 上下文新增一项 `opening_outreach`：把开启会话的那条主动消息（目的、正文摘要）作为钉住项，让回复 Run 知道客户在回应什么。

### 4.3 “客户要求的提醒”（P6：不设例外）

例如王先生说“到期前一周提醒我续卡就行”，但他此前说过“以后别联系我”。联系限制只有负责人能解除（ADR-023 §2.4），v1 不为“客户要求的提醒”开例外：
- 承诺仍然登记。到期时 commitment-keeper 发现被联系限制挡住，按现有逻辑报负责人可见的异常（“blocked by a contact restriction”）；
- 由负责人决定是否解除限制，或者改由人工联系。

### 4.4 退订与“不再接收”

**消息里怎么体现**：
- 营销目的的消息，由服务端在正文末尾追加一行固定的退订说明，例如：“不想再收到这类消息，回复‘退订’即可。”
- 话术由租户配置（§4.5），出站检查确认它存在；缺少时拒绝派发（`unsubscribe_notice_missing`），不由模型自行决定是否写。
- 非营销目的（承诺跟进、服务回访、计划目的）不强制退订说明，但仍附上“回复‘别联系我’即可停止”，这一点与第一稿一致。

**客户回复后怎么自动处理**：分两类，都在入站事务里确定性地完成，不需要模型判断。

| 客户回复 | 判定 | 结果 |
|---|---|---|
| “别联系我”“以后都别发了”等 | 现有拒绝规则（`contact-refusal-rules`，0109 入站触发器）命中 | **联系限制**：一切主动触达停止，只有负责人能解除；本条来信仍按 ADR-023 §2.6 回复一次 |
| “退订”“不要再推活动了”“别给我发广告”等 | 新增的退订规则集（`unsubscribe-rules.v1.json`，与拒绝规则同样是版本化、确定性的匹配），只在**最近一条主动消息是营销目的**、且时间在可配置窗口内（默认 30 天）时生效 | **主题退订**：为该客户写一条主题拒绝 `marketing`。来源是这条入站消息，记录在新的“退订记录”里，派发时与消费者主题偏好同样处理。客户不再收到任何营销消息，服务回访与承诺跟进不受影响 |
| 只说“退订”，但最近的主动消息不是营销 | 不能确定客户指的是什么 | 按**联系限制**处理（保守，宁可多停） |

- 退订记录由入站确定性规则写入，不依赖 Claim 提取的时延。之后提取出的同义 Claim（例如“别给我推活动”被提取为主题偏好）只是重复证据。
- 退订之后，只有客户自己的明确表达（例如“以后可以给我发活动”，由确定性规则命中）才能恢复接收营销，恢复会写一条记录。负责人不能替客户恢复，只能看到记录。一般性的“别联系我”属于联系限制，仍只有负责人能解除（ADR-023）。
- 退订和拒绝对“当前这一条回复”都没有影响：客户的这条来信仍会得到一次回复（例如“好的，已为您退订”），这条回复属于绑定来信的回复。

### 4.5 营销合规与配置

- **责任归属**：不同法域对营销信息有不同的合规要求，例如事先同意（opt-in）或可退出（opt-out）、显著的退订方式、发送时段、发送方身份标识。**是否合规由使用方负责**；NexLoop 提供配置项与留证，不替使用方做法律判断。部署文档和工作台配置页需要醒目写明；同意模式的说明里要写清，opt-out 在部分法域不被允许。
- **租户配置**（受治理 Action，有版本、留证）：

  | 配置项 | 取值 | 默认 |
  |---|---|---|
  | `marketing.enabled` | 营销目的总开关 | **关**：租户必须由负责人主动打开，营销目的才可能派发 |
  | `marketing.consent_mode` | `opt_out`：默认可发，客户主动表示不同意即停（负责人 2026-10-19）；`opt_in`：只发给有同意记录的客户 | **`opt_out`** |
  | `marketing.unsubscribe_notice` | 退订话术 | 系统提供一句默认话术，租户可改 |
  | `marketing.frequency` | 营销桶的频率上限，不超过租户总上限 | 每 7 天 1 条 |
  | `marketing.sender_label` | 营销消息的发送方标识 | 空（可选） |

- **“不同意”的记录**（两种模式都用）：
  - 退订记录：来自 §4.4 的入站规则；
  - 营销主题拒绝：来自客户的偏好 Claim（人设稿 §4），或退订规则写入的主题拒绝；
  - 联系限制：来自现有拒绝规则。

  这些都只来自客户本人的表达。负责人不能替客户退订，也不能替客户撤销退订。
- **同意记录**（只在 opt-in 下需要）：来源同样只能是客户自己的明确表达（来信中的确定性规则命中，或渠道侧的同意事件），记录时间、来源消息和规则版本；客户退订即撤销同意。负责人不能凭空添加同意。
- **批量导入**：v1 不提供退订名单或同意名单的批量导入。退订和同意都只来自客户本人在本系统渠道里的表达。使用方在其他渠道收集的退订（例如电话、门店），v1 由负责人按客户逐个设置联系限制来体现；更细的“只退营销”导入需要另立任务并拍板。

## 5. 审计与证据

每条主动外发都能还原一条完整的证据链，并可由演示追踪和工作台读出：

1. 触发事件：承诺阶段、回执变化、`reassess_at` 到点或负责人请求，含去重键；
2. 计划标记与 SQL 预检结论（包括 `purpose_unregistered` 这类“不行动”的原因）；
3. Role Run：上下文清单（Manifest，含人设版本）、模型调用、工具调用，以及外发或不行动的简短决策依据（不要求隐藏推理）；
4. 受治理 Action 意图：参数摘要（正文以摘要和受控原文存储）、业务意图 ID、目的与清单版本；
5. 审批记录（如有）；
6. 每一道闸门的结论：通过或拒绝、规则版本、频率计数快照、偏好来源 Claim、退订记录或同意记录（opt-in 时）；
7. provider 尝试、回执、对账查询；
8. 物化后的 Message、客户之后的回复，以及由此产生的联系限制或退订记录。

- 新增读取：`demo_trace` 和工作台按 `origin_kind='proactive'` 读出上述链路。这是另一个受治理读取，按会话或客户查询，同样遵守演示租户隔离。
- 指标：
  - 按目的类别统计的主动外发数和各闸门拒绝数；
  - 客户回复率；
  - **退订率和拒绝联系率**，按目的与人设版本统计，用于监测误伤，也为 S7 提供输入。

## 6. 测试人设如何排除

- **标记**：ADR-034 的 Consumer `persona` 已在 main（0220），由负责人 Action 设置。
- **派发**：测试人设消费者的主动外发，只能在 `world='test'` 或租户 `data_mode='test'` 下走测试 provider；真实世界下派发时以 `persona_excluded` 拒绝（第 5 道闸门），与真实派发开关一样默认关闭。
- **触发**：触发源扫描默认跳过测试人设消费者，除非租户处于测试数据模式，避免给模拟客户产生大量无意义的复评。
- **分析**：测试人设消费者的主动外发、回复率、退订率，不进入真实指标与客户事实。
- **验收**：测试中故意让测试人设消费者满足触发条件，断言真实世界里 provider 收到 0 个请求，测试世界则正常走测试 provider。

## 7. 失败与未知结果

沿用效应路径的规则（AGENTS 不变量：未知结果先查询或对账，不盲目重试；不声称 exactly-once）：

| 情况 | 处理 |
|---|---|
| provider 明确失败 | 记录失败，不自动重发。目的允许时，由下一次复评重新判断是否再发，受频率上限约束 |
| 结果未知（超时、断连） | 按意图 ID 查询或对账，窗口可配置（参照 `reconcile_window_seconds`）；窗口内不重发。窗口结束仍未知，记录 `outreach_unknown` 并告知负责人，不再发 |
| 派发被闸门拒绝 | 写拒绝记录；计划标记“派发被拒”，按 NX-024 再复评一次（在自触发上限内），通常结论是不行动 |
| 审批被拒或超时 | 意图终止，不发送；计划记录结论 |
| Run 失败或超预算 | 计划记录失败；不退回模板发送；承诺跟进类按 NX-026 的异常上报负责人 |
| 重启或重复触发 | 业务意图 ID 去重：同一目的、同一来源、同一日窗口只会有一个意图 |

## 10. 实施切片（v0.1 冻结之后）

前置条件：人设三个分支（`l3/persona-impl-1`、`l3/persona-impl-2`、`l3/persona-ui`）已合入。本设计直接使用其中的偏好检查（NXC06）、人设节和测试人设标记。

1. ADR 三份（§8）。目的清单的契约、表与发布 Action；租户控制（勿扰、频率、时区、营销配置）的迁移、受治理调整 Action 和工作台页面。
2. `nexloop.outreach.send:1` 的 Action 定义、效应类别与外部效应声明；外发记录 `origin_kind`（迁移）；冻结请求中的 `channel` 与 `topic`；派发检查链加闸门 3、4、5、6、7。闸门 8 直接复用人设稿的偏好检查，并把主题匹配扩展为前缀匹配。
3. 复评角色加 `send_proactive` 工具与文案规则；触发源写入目的与来源；计划自定义目的的登记检查；v6 上下文 `opening_outreach`；人设节进入复评 Run 的上下文（人设稿第一片目前只接入了消息 Run）。
4. 可选审批：待审批状态、负责人批准或拒绝的 Action、审批时限。
5. 退订与同意：退订规则集与入站触发器、退订记录、主题拒绝、恢复接收的记录；租户同意模式（opt-out 默认，opt-in 可选）与 opt-in 下的同意记录；服务端追加退订话术及其出站检查。
6. 投递保证与未知结果对账；指标（含退订率、拒绝联系率）；工作台与演示追踪读取。
7. 演示租户上验证，再更新演示页标注（P7）。

**验收要点**：
- 受限客户的主动外发在派发时被拒，provider 收到 0 个请求；营销目的同样被拒。
- 租户勿扰、租户频率、消费者偏好（时段 / 频率 / 渠道 / 主题）、营销接收资格、真实派发开关关闭、预算不足、测试人设，各自拒绝并留证。
- 营销总开关默认关：未打开时营销目的被拒。打开且同意模式为默认 opt-out 时，没有任何“不同意”记录的客户可以收到营销；客户退订、拒绝营销主题或说“别联系我”之后，营销被拒（分别由第 4、8、2 道闸门拦下）。
- 同意模式为 opt-in，或目的要求同意时，没有同意记录的客户收不到营销（`marketing_consent_missing`）。
- 消费者说过“别给我推活动”后，所有 `marketing.*` 目的被拒，服务回访照常。
- 营销消息一定带服务端追加的退订说明；客户回复“退订”后写入主题退订，之后的营销消息被拒；在非营销消息之后回复“退订”，按联系限制处理。
- 未登记或已停用的目的不能使用；计划引用这类目的时，预检结论是不行动。
- 需要审批的目的在批准前不派发；批准后派发时重新检查全部闸门。
- 同一触发重复到达只产生一个意图；结果未知时只查询、不重发。
- 客户回复后，回复保证与兜底照常；兜底回复 Run 不能调用主动外发。
