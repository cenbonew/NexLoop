## 2. A2：上线前的只读核对（DATA_HOST，调度员，`ro` 见 run-nx057 §0.3）

读取记录只存 hash，看不出哪些消息会抽到 F 或 T，所以要在消息正文上按 recall_terms 的子串规则离线检查：去掉空白、转小写后看是否包含。这里不区分 persona，扫描 world real 近 30 天的**全部**消息，比只看真实 persona 更严。正式的 F 和 T 在写执行单时选定，选法同 Q4：T 的 hash 必须小于 F 和全部 U_i。

```
ro "select count(*) from ontology.objects o where o.tenant_id='$TENANT_ID' and o.world='real' and o.type_name='Message'
    and o.created_at>=now()-interval '30 days'
    and (position(regexp_replace(lower('<F>'),'\s+','','g') in regexp_replace(lower(coalesce(o.properties->>'body','')),'\s+','','g'))>0
      or position(regexp_replace(lower('<T>'),'\s+','','g') in regexp_replace(lower(coalesce(o.properties->>'body','')),'\s+','','g'))>0)"
```

- **预期**：0。不是 0 就换词，不要上线。
- 另外两条：
  - F 和 T 不在现有目录词里，也不包含现有目录词：用 p5-catalog.tsv 离线核对；
  - 夹具类型没有对象，没有 Action 绑定它：发布后用 `ro` 查 `ontology.objects` 和 `control.nexloop_action_definitions`，两者都应为 0。

## 4. A4：退役步骤（放在 R7 之后，作为运行单的固定步骤）

1. **撤掉定义读权限**：从 `stage-principals.v1.json` 的 definition_read_rules 中删去 `S6SyntheticFixture` 的类型和全部属性，然后按部署流程 register（dry-run 应当只显示这一条规则减少）。让运行时抽不到 F 和 T 的有效步骤之一（Q6）。
2. **隐藏属性**：经 F3 的 hide，对 6 个夹具属性各提交一次。0450（召回 hidden 迁移）之后这也是有效的退役手段：hidden 属性不再进召回（Q6）。两步都做，互为保险。
3. **只读核对**：
   - 以 relay_source 的口径，recall_terms 对一句同时包含 F 和 T 的句子返回空。stage 上不能直接扮演 relay_source，所以替代做法是：退役之后，在一次合成读取的记录里，term_hashes 不再出现 hash(F) 和 hash(T)；
   - `ro` 查 definition_read_rule 事实，已经没有夹具类型。
4. **D–H 的候选**（A1）：任何 target_refs 落在夹具上的候选，都不得晋升到会影响真实读取的语义版本。如果已经晋升，就随夹具一起撤回：经语义发布的回退，回到上一个版本。证据里写明数据源是合成夹具。
5. **召回索引里留下的夹具行不删**：读不到，也没有删除入口。每日缺口核对里会持续看到这个类型，这是预期的。
