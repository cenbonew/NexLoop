## 1. 为什么拆分
设计稿 §2.4 第 1 步认为“Run 签发不需要知道 E”。实施时核实，这一点不成立：
- Run 的资源在 bind 之前就定了，写在三个地方：assignment 的 `allowed_actions`、签发 SQL 的白名单和 source proof、`run_credentials.allowed_resources`；
- `runtime_activation` 和本地投递也按 `:1` 校验 Run。

所以只要准入了 `:2`，bind 就会选 `:2`，而 Run 只持有 `:1`，relay 整条链失败。H1 (a) 一旦先合入，下一次 Consumer 发布就会让 relay 全断。因此拆成三步：
1. **M2.1（本步）**：签发链按 Consumer 选 E，加上 bind、intent 和执行端；
2. **M2.2**：context pack v8，以及 Host 同时接受 v7/v8；
3. **M2.3**：H1 (a)，在发布事务内写准入行。它必须在 M2.1 和 M2.2 都合入之后才能启用，开工前先写明有什么机制挡住提前部署。

## 2. M2.1 内容
1. **选择**：
   - `authz.nexloop_effect_bind_action_resource` 先调用 0451 的选择函数。
   - 如果没有任何准入覆盖该 Consumer 版本，就回退到允许名单里的 `:1`，由 A′ 在 intent 时证明，与方案 B 之前相同。这个回退是过渡性的，M4 删除。
   - 有两个准入同时覆盖时仍然拒绝。
   - **follow 完成才选 `:N`**：仿照 registrar 的选择（0446 只选会话持有授权的版本），只有 register 已把 `:1` 的每一条授权都 follow 到 `:N`（每个持有 `:1` 授权的主体也持有 `:N`），才选 `:N`；否则选 `:1`，由 A′ 证明。这样准入和 register 之间没有 relay 失败的窗口，M2.3 的 H1 (a) 也因此安全：发布事务内写了准入，但在 register 之前仍走 `:1`。
   - 另有两个供调用方使用的函数：`authz.nexloop_effect_action_resource_for`（registrar 用，按 verb payload）和 `authz.nexloop_effect_consumer_action_resources`（relay 用，按 Consumer）。
2. **Run 签发**：
   - message Run（v0049 核心、v0190 handoff 包装）和 reply fallback Run（v0110）的 `allowed_actions`、source proof 和 run 凭证，都用为 Consumer 选出的版本。
   - SQL 按 Consumer 当前版本重算，与 assignment 不符就不签发。
3. **bind（M2-a）**：
   - Python 先选 E，再签 executor proof 和 run proof；
   - SQL 用同一函数重算，两份 proof 都必须等于选中的版本，否则 42501；
   - context 显式写入 `action_resource`；
   - 同一 step 重新 bind 时必须是同一个版本；
   - configure 按 EffectControl 指向的 Consumer 选版本。
4. **intent**：
   - 外层接受允许名单里任一 stable_name 的任意正整数版本；
   - v0040 要求 intent 的资源正好等于 `ctx.action_resource`（为空时退回允许名单的 resource，对应在触发器关闭的情况下直接写 context 的夹具）；
   - A′ 分支保留。
5. **执行**：
   - 本地投递授权（0175）的 deliver 动词按 intent 自己的版本校验；
   - Python 的 `local_json_delivery`、`effect_execution`（catalog find）和 `runtime_activation` 都从 Run 或 intent 取版本；
   - effect catalog（v0401、hint）用 stable_name 比对 offering 的 `delivery_action`（设计稿 §2.5，对象数据里的 `:1` 不迁移）。
6. **退役（M2-b，选“拒绝退役”）**：
   - 版本仍被未过期 context 引用时，返回 `referenced_by_unexpired_context`，不做任何改动。
   - 理由：context 不可改，proof 按它的 resource 签过名，“重新选版本”就等于改写已绑定的 context；而 context 几分钟就过期，过期后再退役即可。
7. **复制的函数**：共 11 个，全部放在同一个迁移里，每一处替换都登记在 `tests/support/task_b_m2_edits.py`，copy guard 逐个函数校验。
   - registrar；intent 的 v0040、v0041、v0052；
   - 签发的 v0049、v0190、v0110；
   - catalog 的 v0401 和 hint；
   - 本地投递授权；
   - 退役函数。

## 3. 相对设计稿的偏离
1. **Run 签发需要知道 E**：与设计稿 §2.4 第 1 步相反。relay 在签发前按 Consumer 选出 E，签发 SQL 重算后才签发（见 §1）。
2. **context pack 在 M2.1 仍写 `:1`**：涉及 v2/v4/v6/v7 各个构建函数的 `current_constraints.action`、section ref 和 `effect_supplies`。runtime 的版本只从 Run 取，不读 pack。pack 文本随 v8 在 M2.2 一起切换，所以 M2.1 期间，已准入顾客的 pack 显示 `:1`、实际执行 `:2`。这只是文本显示上的差异，权限仍由 SQL 精确校验。
3. **效应分类和真实投递开关不跟随版本**：
   - `action-effect-categories` 的分类和 externality 按定义 digest 记录，没有声明的定义按“外部效应、customer_contact”处理，也就是默认关闭；
   - 真实投递开关的 Action 层也按精确 resource 记录。
   - 因此准入 `:2` 之后，还要由 configurator 为 `:2` 声明分类（必要时还要打开 `:2` 的开关），执行端才会投递。
   - M2.1 不改变这两个安全控制的语义，由测试 `test_an_undeclared_successor_category_keeps_the_dispatch_closed` 固定。设计稿 §2.6 的 v4（按 stable_name 分类）需要负责人另行决定；在那之前，M3 的运行单要包含“为 `:2` 声明分类”这一步。
4. **本地投递 worker 按 intent 的版本证明授权**：`:2` 的 intent 要求 worker 持有 `:2` 的授权，由 register 的 follow 派生（B5，FOLLOWABLE 增加效应 Action 两条，这部分属于 M2.3/M3 的 register 工作）。测试里用 `follow_facts` 在事实层模拟 register 的派生。
5. **`authz.nexloop_local_delivery_authority` 的 query 动词仍是 `nexloop.service.query:1`**：它不绑定 Consumer 的效应，不在方案 B 范围内。
