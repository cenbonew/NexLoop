# 执行单：AT-050 第二次恢复演练（容器方式，2026-10-20）

- 目的：用真实备份做第二次恢复演练（AT-050），同时补上 AT-059：恢复点之后做一次合成删除，恢复后由恢复日志重放这次删除。
- 与 run-33（10/15，第一次）的区别：恢复改为按 NX-035 部署运行手册 §4.2 的原设计执行，即在**生产 postgres 镜像**里、`--network none` 的一次性容器中，运行 `pgbackrest restore` 和恢复实例。run-33 用的是主机工具链，现在有三个障碍：
  1. APP_HOST 的 `/opt/nexloop/restore-venv` 是 10/15 安装的，catalog 只到 0197，而 stage 现在是 0221。`bootstrap.verify` 要求 lineage 与库完全一致，旧代码会拒绝。
  2. APP_HOST 主机的 pgvector 是 0.8.1，恢复出来的库里扩展是 0.8.7（PG 升级执行单 §5 之后）。
  3. 主机 glibc 2.43 与生产镜像的 2.36 不同，排序规则可能不同（run-33 §10 的限制）。
- 分类：**B** 表示负责人执行（sudo）；**A** 表示调度员可执行的只读核对。本文只用角色名和变量。

## 运行方式的决定

| 项 | 取值 | 理由 |
|---|---|---|
| PG、pgBackRest、pgvector、glibc | 发布 22 的 postgres 镜像 `nexloop/postgres@sha256:647fb7d1…`（PostgreSQL 18.6、pgvector 0.8.7、pgBackRest 2.59.3、Debian bookworm glibc 2.36） | 与 DATA_HOST 生产实例同一个镜像，消除上面三个障碍中的后两个 |
| `nexloop-restore` 的代码 | 发布 22 的 backend 镜像里的 Python（3.12.15）和包，用 `docker cp` 把 `/usr/local` 取到演练目录，以只读方式挂进 postgres 容器运行 | 代码与 catalog（0221）来自签名发布的镜像，与线上完全一致。两个镜像都是 Debian bookworm、glibc 2.36，backend 的 Python 可以直接在 postgres 镜像里运行（CI 演练实测）。不需要在主机上重装 restore-venv：那需要 PyPI 镜像、联网和 sudo pip，而且版本容易与发布不一致 |
| 容器内的身份 | `--user <nexloop-pgbackrest 的 uid>:<gid>` | repo1 的属主是 `nexloop-pgbackrest`；`pgbackrest restore` 和 `pg_ctl start` 都以这个身份运行，pgdata 也归它。镜像里没有这个 uid 的 passwd 条目也不影响：只有 initdb 需要它，恢复流程不调用 initdb（CI 演练实测） |
| repo1 | 宿主路径原样**只读**挂入（`-v $REPO1:$REPO1:ro`） | 恢复只读仓库（CI 演练实测）；lock、spool、log 都放在演练目录 |
| 网络 | `--network none` | 容器只有自己的回环接口，端口不会与主机上的 5432 冲突，所以不需要 `--running-port`；实例只监听 socket |
| 端口 | 容器内 `55433` | 只用于构造 socket 名 |
| socket | `$D/socket` | 代码写入 `unix_socket_directories` |
| `--owner-user` / `--hba-method` / `--dbname` | `nexloop_bootstrap` / `trust` / `nexloop_stage` | 同 run-33 的决定：pg_hba 只有一行 `local all nexloop_bootstrap trust`，只在容器内的 socket 上生效 |
| locale | 镜像自带 `en_US.utf8` | 与生产相同，主机不需要 locale-gen |

## 1. 演练目录与发布 22 的 Python（B，APP_HOST）

```
D=/srv/nexloop/drill/$DRILL_ID
sudo install -d -o nexloop-pgbackrest -g nexloop-pgbackrest -m 0700 "$D" "$D/pgdata" "$D/socket" "$D/journal" "$D/conf" "$D/report" "$D/lock" "$D/log" "$D/spool"
sudo sh -c "docker create --name at050-py-$DRILL_ID '$BE_IMG' >/dev/null && docker cp at050-py-$DRILL_ID:/usr/local '$D/py' && docker rm at050-py-$DRILL_ID >/dev/null"
sudo chown -R root:root "$D/py" && sudo chmod -R go-w,a+rX "$D/py"
```

- `$D` 是 0700 并属于 `nexloop-pgbackrest`，所以容器以它的 uid 运行时能进入目录；`$D/py` 属于 root，容器只读挂载、只读使用。
- **判据**：`sudo ls -la "$D"` 中 9 个目录属于 `nexloop-pgbackrest`、`py` 属于 root。

## 5. 运行恢复（B，APP_HOST，一条 sudo）

```
cd /tmp; date -u +%FT%TZ
sudo docker run --rm --network none --user "$RU:$RG" --cap-drop ALL --security-opt no-new-privileges \
  -e PYTHONHOME="$D/py" -e LD_LIBRARY_PATH="$D/py/lib" -e PATH="$D/py/bin:/usr/lib/postgresql/18/bin:/usr/bin:/bin" \
  -e D="$D" -e DRILL_ID="$DRILL_ID" -e ERASED="<合成删除的顾客 ID>" -e TENANT="<stage 租户 ID>" \
  -v "$D:$D" -v "$REPO1:$REPO1:ro" --entrypoint sh "$PG_IMG" -c '
python3 -c "import sys;from nexloop_eios.backup import restore_main;sys.exit(restore_main())" --source pgbackrest --pgbackrest-bin /usr/bin/pgbackrest \
  --pgbackrest-config-file "$D/conf/pgbackrest-drill.conf" --stanza nexloop --repo 1 --target-name "drill-$DRILL_ID" --drill-mark-file "$D/conf/mark-$DRILL_ID.json" \
  --pg-bin /usr/lib/postgresql/18/bin --pg-path "$D/pgdata" --port 55433 --socket-dir "$D/socket" --owner-user nexloop_bootstrap --hba-method trust \
  --dbname nexloop_stage --restore-ref "drill-$DRILL_ID" --journal-dir "$D/journal" --old-primary-fenced --report-file "$D/report/restore-$DRILL_ID.json" \
  > "$D/report/stdout-$DRILL_ID.json"; echo "restore exit $?"
python3 - <<PY
import json, os, psycopg
d, ref = os.environ["D"], os.environ["DRILL_ID"]
r = json.load(open(f"{d}/report/stdout-{ref}.json"))
print("passed", r.get("passed"), "state", r.get("state"), "lineage", (r.get("lineage") or {}).get("revision"), "journal_entries", r.get("journal_entries"),
      "deletions", (r.get("replay") or {}).get("deletions"), "tool_seconds", r.get("tool_seconds"))
if r.get("passed"):
    with psycopg.connect(f"host={d}/socket port=55433 dbname=nexloop_stage user=nexloop_bootstrap", autocommit=True) as db:
        print("server", db.execute("show server_version").fetchone()[0], "vector", db.execute("select extversion from pg_extension where extname=%s", ("vector",)).fetchone()[0],
              "archive_mode", db.execute("show archive_mode").fetchone()[0], "listen", repr(db.execute("show listen_addresses").fetchone()[0]),
              "state", db.execute("select state from control.nexloop_restore_state").fetchone()[0],
              "erased_again", db.execute("select runtime.nexloop_consumer_erasing(%s,%s,%s)", (os.environ["TENANT"], "real", os.environ["ERASED"])).fetchone()[0])
PY
pg_ctl -D "$D/pgdata" status >/dev/null 2>&1 && pg_ctl -D "$D/pgdata" -m fast -w stop >/dev/null; pg_ctl -D "$D/pgdata" status | head -1'
date -u +%FT%TZ
```

- 这里不加 `--stop`：恢复后先在同一个容器里核对 vector 和删除重放，再停实例。容器退出时，实例无论如何都会结束。
- 顾客 ID 和租户 ID 只经环境变量传入，不出现在报告里；报告只含数字。

**预期**：

| 项 | 预期 |
|---|---|
| `restore exit` | 0 |
| `passed` / `state` | `True` / `verified_readonly` |
| `lineage` | `0221` |
| `journal_entries` / `deletions` | 大于 0 / 至少 1 |
| `server` / `vector` | `18.6 …` / `0.8.7` |
| `archive_mode` / `listen` | `off` / `''` |
| `erased_again` | `True`（AT-059：恢复点之后的删除被日志重放） |
| 最后一行 | `pg_ctl: no server running` |
| `tool_seconds` | 本次 RTO，门槛 7200 |

**失败时**：报告为 `{"passed": false, …}`。不要在原目录上重试：先查看 `$D/pgdata/restore.log` 和 `$D/log`，然后按 §7 销毁，换一个新的 `DRILL_ID` 从 §1 重来。

## 9. CI 主机演练记录（2026-10-19，`nexloop-ci`，rootless docker，合成数据）

脚本做的事情与本单 §1–§5 相同，只把 stage 的身份换成一次性的：

- 发布 22 的 postgres 镜像建源集群：initdb，`archive_command` 为 pgBackRest archive-push，推到本地 repo；
- 用 backend 镜像取出的 Python 执行 `nexloop_eios.bootstrap`，catalog 为 0221；
- 建一张带 HNSW 索引的合成向量表，1000 行；
- pgBackRest full 备份，recorder 身份 `drill_mark('d2')`；
- 恢复点之后删除 100 行（源库剩 900 行）；
- 在第二个 `--network none` 容器里运行 `restore_main`，repo 只读挂载，身份为镜像中没有 passwd 条目的 uid 4242，并加上 `--cap-drop ALL --security-opt no-new-privileges`（与 §5 相同）。

关键输出：

```
python 3.12.15 psycopg 3.3.6 binary catalog head 0221
bootstrap: True 0221   vector: 0.8.7   backups: 1
mark: drill-d2 … tables 6   source rows after deletion: 900
repo mount: ro   restore container: uid 4242, passwd entry: none
restore exit 0
passed True state verified_readonly lineage 0221 roles_set_nologin 9 journal_entries 0 tool_seconds 3.811
controls {'opening_recorded': True, 'owner_only': True, 'per_scope': True, 'report_complete': True, 'unverified_paused': True}
drill_compare {'count_mismatches': 0, 'sample_mismatches': 0, 'catalog_equal': True}
restored: 18.6 (Debian 18.6-1.pgdg12+2) vector 0.8.7 rows 1000 … archive_mode off listen '' state verified_readonly
source still running, rows: 900, restore_state rows: 0
cleanup: removed
```

- 恢复出来的是恢复点时的 1000 行，恢复点之后删除的 100 行回来了。这是普通的行删除，不经恢复日志，所以 `journal_entries` 为 0。stage 上的合成删除走 erasure，会进入恢复日志，恢复后被重放，§5 用 `erased_again` 核对。
- 源库不受影响：仍是 900 行，`restore_state` 为空。
- 另外单独验证过：在没有 passwd 条目的 uid 下 `initdb` 失败，但 `pg_ctl start`、`pg_controldata` 和 `pgbackrest` 都正常。恢复流程不调用 initdb。
- **与 stage 的差异**：
  - CI 上的源库和仓库是一次性的，没有 TLS server、加密口令和 recorder 的真实凭据；
  - 日志为空，没有演练 AT-059 的日志重放。这一项由 `test_restore_drill_pg` 在本地 PG 上覆盖，stage 上由 §5 的 `erased_again` 核对。
