## 1. 合成租户与服务主体（DATA_HOST 一次性容器，B）

### 1.1 入口结论

- **建租户没有独立入口。** 0050 `control.nexloop_configure_manifest` 在第一次受信配置发布时插入 `control.nexloop_tenants(tenant_id, status)`（`0050_trusted_configuration.sql`，约第 89 行；后续迁移重定义时保留）。`service_grants.apply` 发布时用 `tenant_status = 'active'`（`service_grants.py:apply`）。
- 因此 **register 的第一次执行就建立了租户**，同时建立 21 个服务主体、凭据和授权，以及 relay Source 的 `message_read_rule`。
- 不用 `scripts/nx037/real_tenant_init.py`，原因有两个：
  - 它只有 `plan|execute|verify` 三种模式，没有合成模式；
  - 它要求 `--configurator-dsn-file`，没有登录窗口方式，而且它的授权只是 `service-grants.v1.json` 的子集。
- 它的第 2、3 步 `effect_categories.apply`、`observability.apply_rules` 由 1.6 的 `configure` 模式在 register 之后执行（缺口 G2 已补）。`execute` 不在 stage 使用：它按 `service-grants.v1.json` 应用授权，而 stage 的授权清单由 register 管理。
- `enterprise_setup`、`business_setup`、`catalog_setup` 都在租户存在之后，以服务凭据经 API 运行，不建租户。

### 1.2 `--tenant` 取值

- 取一个新生成的小写 UUID：`python3 -c 'import uuid; print(uuid.uuid4())'`。`real_tenant_init.py:parameters` 也要求 UUID 形式，并拒绝沙箱租户 `sandbox_profile.SANDBOX_TENANT`；后续 NX-037 工具沿用这个租户，所以此处一并满足。
- 记为 `$TENANT_ID`，写进私有记录，并在第 4 步作为 `BROWSER_TENANT_ID`。
- 合成租户的含义是：只放合成数据，真实派发关闭。它在库里是普通租户，“合成”靠 D9 和后续数据约束保证。

补充：
- 登录 Python 代码只消耗 `local_login` 一种速率动作。SQL 允许的其余动作（`oidc_start`、`password_reset` 等）stage 不使用。

- 账号属于租户：同一身份库里的账号可以在两个 realm 登录，各自用自己的 cookie，`application_id` 只决定会话 realm 和账号配额。限制谁能进入工作台，属于 NX-037 的 workbench 角色与 operator 授权。

### 4.7 部署闸门：`nexloop-doctor --deploy-gate <spec.json>`

入口是 `doctor.py:main` 调 `deploy_checks.py:deploy_gate`；app 必需输入见 `REQUIRED_INPUTS`。spec 样例：`deploy/stage/deploy-gate.app.example.json`，字段逐项对应 `deploy_gate` 读取的键，`tests/test_deploy_gate_spec_example.py` 核对。复制到 `$GATE_DIR/spec.json`（`$GATE_DIR` 为 0700，其中文件为 0600），把占位符换成实际路径：

- `stage_env`、`inventory_before`、`inventory_after`、`compose_json`、`tls_spec`、`running`：`$GATE_DIR` 里的文件，产生方式见下文。
- `connection_budget`：发布检出中的 `deploy/stage/connection-budget.v1.json`。
- `secret_root`：`$NEXLOOP_ROOT/secrets`。`secret_uids` 按样例填写：后端服务 10001，`agent-host` 与 `agent-host-model` 10020，`gateway` 0。
- `roles_database_url_file`：只读 `nexloop_metrics` 的 DSN 文件 `$NEXLOOP_ROOT/ops/metrics/metrics.dsn`（缺口 G-METRICS-DSN，来源见下面的“metrics 客户端”）。`real_tenant_init.py verify --metrics-dsn-file` 用同一个文件。

**metrics 客户端（G-METRICS-DSN）**：
- **来源**：`stage_secrets.py generate` 写进管理树 `management/metrics/`，共四个文件：`metrics.dsn`、`metrics-pg-client.crt`、`metrics-pg-client.key`、`pg-ca.crt`。
  - 证书由 `issue_certs` 签发，CN 为 `nexloop_metrics`。
  - DSN 为 `sslmode=verify-full`，不带口令，证书路径指向 APP_HOST 上的安装位置。
  - 在这一功能之前生成的树，用 `stage_secrets.py metrics --out <树> --ca-dir <CA> --params <私有 params>` 补齐；已有文件一律不覆盖。
- **安装**（APP_HOST，sudo-A）：
  ```
  install -d -o root -g root -m 0700 $NEXLOOP_ROOT/ops/metrics
  install -o root -g root -m 0600 management/metrics/* $NEXLOOP_ROOT/ops/metrics/
  ```
  它不挂进任何服务，只给 `nexloop-doctor --deploy-gate` 和 `real_tenant_init verify` 用，这两项都以 sudo 运行。
- **数据库侧**：`pg_hba.conf.template` 新增 `hostssl <DB> nexloop_metrics <APP_HOST_ADDR>/32 cert`，位于应用角色那一行之前（pg_hba 按第一条匹配），所以 metrics 只凭客户端证书登录，不要口令。
  - 生效步骤：DATA_HOST 重新渲染 `pg_hba.conf`，然后执行 `docker compose -p nexloop-data kill -s HUP postgres`（sudo-D，**B**）。
  - 核对：在 APP_HOST 上以该 DSN 执行 `select current_user`，结果为 `nexloop_metrics`。
- `admin_roles` 按样例；`disabled_roles` 为 `["nexloop_owner"]`：M9 决定之前 `nexloop_bootstrap` 保持可登录。
- `agent_host_config`：`$NEXLOOP_ROOT/secrets/agent-host/runtime-config.json`。

各输入怎么产生：
- `after.json`：在 4.6 之后，以 `--phase after` 运行 4.5 的命令。
- `tls.json`：格式见 `deploy_checks.tls`：`{"ca", "certificates":[{name, chain, key, purpose, names|cn}], "dsn_files":[{name, path}], "valkey_conf"}`。列出 gateway、agent-host、guard、loopback 服务证书，以及每个 `*-dsn`。
- `compose.json`：`docker compose -p nexloop-app -f … --env-file … config --format json > "$GATE_DIR/compose.json"`。
- `running.json`（缺口 G8 已补工具）：4.6 启动全部服务之后，在 APP_HOST 上以 docker 组内的部署用户执行，不需要 root，也不读任何秘密：

  ```
  python3 "$RELEASE_CHECKOUT/scripts/deploy/running_snapshot.py" --project nexloop-app --out "$GATE_DIR/running.json"
  ```

  工具读取 `docker ps`（本项目正在运行的容器）、`docker inspect` 的标签和 `docker top`（容器内进程），按 `nexloop.budget-service` 标签统计每个预算条目正在运行的容器数，并统计 runtime-worker 中的 guard 子进程（`nexloop_eios.runtime_guard_worker`）。没有标签的运行中容器会记为未登记，闸门因此失败。工具输出一行计数，应看到 `guard_children: 4`。

**运行 doctor**：在 APP_HOST 上，以部署用户用 backend 镜像起一次性容器（镜像按发布清单的 digest）。容器只读挂载 `$GATE_DIR`、发布检出的 `deploy/stage` 和秘密树，以 `--user 0` 运行，因为要按属主核对各服务目录：

```
docker run --rm --user 0 --network none --read-only \
  -v "$GATE_DIR":"$GATE_DIR":ro -v "$NEXLOOP_ROOT/secrets":"$NEXLOOP_ROOT/secrets":ro -v "$RELEASE_CHECKOUT/deploy/stage":"$RELEASE_CHECKOUT/deploy/stage":ro \
  --entrypoint nexloop-doctor "$BACKEND_IMAGE" --deploy-gate "$GATE_DIR/spec.json"
```

- **`--network none` 的例外**：`roles_database_url_file` 要连数据库（只读事务）。这一项需要去掉 `--network none`，改为共享应用的网络命名空间（`--network container:<app-net 容器名，见 docker compose -p nexloop-app ps>`）再运行；或者在管理环境中单独执行 roles 检查。
- 路径在容器内外保持一致，spec 里的路径无需改写。

**通过标准**：
- `foundation_checks_passed: true`，`checks` 全部为 true（任何 `input_provided:*` 为 false 都算不通过）；
- `product_ready` 恒为 false，这是预期的。

### 4.9 撤销

- 停服务：`docker compose -p nexloop-app -f … --env-file … --env-file … down`。卷和秘密保留。
- promote 之后要回退：先 `deploy.py rollback-check --release-root … --target <known_good>`，再按 `NX-032-deploy-runbook.md` 的回退节执行。首次部署没有 known_good，只能 down。
