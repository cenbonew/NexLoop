# grype 0.86.1 → 0.120.0（漏洞库 schema v5 → v6）：仓库改动、CI 主机安装与离线更新库（2026-10-17）

- **原因**：
  - grype 0.86.1 只能读 schema v5 的漏洞库，Anchore 发布的 v5 库最后一次构建是 **2026-03-09**（`toolbox-data.anchore.io/grype/databases/listing.json`）；
  - 因此 NX-036 D12（public 发布要求漏洞库不超过 7 天）永远无法满足；
  - 3 月以后公布的漏洞也不会出现在扫描结果里。分析见 `run-host-python-upgrade-20261017.md` §6。
- **执行时机**：仓库改动在分支上，AT-015（10/20）之后随发布合入。CI 主机上的步骤标为 **[B]**，由负责人执行或逐步授权。开发线未连接任何服务器。
- **版本**：grype v0.120.0（2026-10-02 发布，已满两周）。v0.120.1 发布于 10-06，未满两周，不选。

## 2. 开发机上用新版本实测（只读，2026-10-17）

全部在开发机的 scratchpad 中完成，没有安装到系统：

- grype 0.120.0 和 syft 1.18.1 的 darwin/arm64 档案按官方 checksums 校验通过；
- 漏洞库按 §4 的离线方式取得：用 `latest.json` 中的 sha256 校验后 `grype db import`。`grype db status`：schema `v6.1.10`，built `2026-10-16T06:29:51Z`，valid；
- 扫描对象按 digest 直接从 registry 读取，不经 docker。

| 扫描对象（linux/amd64） | 结果（只记编号与包） |
|---|---|
| `python-build-base`（3.12.15，backend 的最终基础镜像；agent-host 的 `/usr/local` 也来自它） | <ul><li>**CVE-2025-13836 不再出现**；</li><li>python 3.12.15 只有 Medium 和 Negligible 级别的发现；</li><li>sqlite CVE-2025-7458（`3.40.1-2+deb12u2`、wont-fix）仍然出现，被现行 backend 豁免匹配；</li><li>zlib1g 的 CVE-2023-45853 **不再匹配**（v6 库的 Debian 数据已更新），所以三条 zlib 豁免会进入 `cleanup`。这只是列出，不算失败；</li><li>新出现 CVE-2026-5450（libc6、libc-bin，Critical、wont-fix），按 D5 不阻断也不列出；</li><li>有修复的 Critical 和 High 都是 0；public 判定 `problems` 为空</li></ul> |
| `node-host-base`（node 24.13.0-bookworm-slim，agent-host 的基础镜像） | <ul><li>有修复的 Critical：libgnutls30 `deb12u5`、perl-base `deb12u3`；</li><li>有修复的 High：node 24.13.0 本身、libc6 `deb12u13`、libpcre2、libcap2、dpkg 等；</li><li>npm 自带包的 GHSA 发现，在我们的镜像里已经随 npm 一起删除；</li><li>近似估计：public 下有 7 个阻断编号</li></ul> |
| `postgres`（pgvector 0.8.5-pg18-bookworm） | <ul><li>有修复的 Critical：perl 系列 `deb12u3`、libssl3 和 openssl `3.0.20-1~deb12u2`、python3.11-minimal `deb12u7`（修复版本为 deb12u9）；</li><li>Go stdlib 1.24.6 的发现来自 gosu，我们的镜像已删除 gosu；</li><li>近似估计：public 下有 10 个阻断编号</li></ul> |

- **结论**：换成新库以后，public 发布会被**真实存在的**“有修复的 Critical”阻断。阻断来自 Node 和 pgvector 两个基础镜像中过期的 Debian 包，不是工具或数据有误。
- 这需要另立任务处理：
  - 升级 `node-host-base`，到 node 24 的较新 bookworm-slim；
  - 升级 `postgres` 的 pgvector 基础镜像，或在 `deploy/postgres/Dockerfile` 中加入有约束的安全更新；
  - 两者都不在本次改动范围内。
- stage 发布不受影响：stage 只列出，不阻断。

## 3. CI 主机安装 grype 0.120.0 [B]

与 O3（2026-10-11）的方式相同：档案在开发机与 CI 主机各校验一次，安装到 `nexloop-ci` 自己的目录，不需要 root。

```
# 开发机：下载档案与 checksums，核对
curl -LO https://github.com/anchore/grype/releases/download/v0.120.0/grype_0.120.0_linux_amd64.tar.gz
curl -LO https://github.com/anchore/grype/releases/download/v0.120.0/grype_0.120.0_checksums.txt
grep ' grype_0.120.0_linux_amd64.tar.gz$' grype_0.120.0_checksums.txt   # a5a1218dce63acdac152a6b3b5bb366e7267e36f4069848cf455543b3fa5700e
shasum -a 256 -c <<< "a5a1218dce63acdac152a6b3b5bb366e7267e36f4069848cf455543b3fa5700e  grype_0.120.0_linux_amd64.tar.gz"
```

[B] CI 主机，以 `nexloop-ci` 身份执行：

```
sha256sum -c <<< "a5a1218dce63acdac152a6b3b5bb366e7267e36f4069848cf455543b3fa5700e  grype_0.120.0_linux_amd64.tar.gz"
mkdir -p "$HOME/tools/grype-0.120.0" && tar -C "$HOME/tools/grype-0.120.0" -xzf grype_0.120.0_linux_amd64.tar.gz grype
sha256sum "$HOME/tools/grype-0.120.0/grype"       # 4de6935c80c111d3d37b2b09f86d1a30b3d10a2f7146d4dbe74ed86c81f35790
"$HOME/tools/grype-0.120.0/grype" version         # Version: 0.120.0；GitCommit: 10fbc043ecbaf8436daa9efac9f1632557caf277；Supported DB Schema: 6
# PATH 上的 grype 换成新版本；旧版本改名保留（回退用），例如在 PATH 目录中：
mv grype grype-0.86.1 && ln -s "$HOME/tools/grype-0.120.0/grype" grype
```

- 每次扫描所用的库目录由 `GRYPE_DB_CACHE_DIR` 决定。建议固定写在 `nexloop-ci` 的环境里，例如 `$HOME/.cache/grype/db`（grype 的默认值）；更新作业和扫描必须用同一个目录。
- v6 的库放在 `<cache>/6/`，与旧版本的 `<cache>/5/` 互不覆盖，回退时 v5 库仍然可用。

## 4. 离线更新漏洞库 [B]

CI 主机的出站受 NX-033 防火墙限制。最稳妥的做法是在能联网的机器上下载，校验后拷到 CI 主机再导入。CI 主机不需要访问 Anchore。

```
# 有网络的机器（如开发机）：读取当前清单，下载对应档案，核对 sha256
curl -s https://grype.anchore.io/databases/v6/latest.json -o latest.json
P=$(python3 -c "import json;print(json.load(open('latest.json'))['path'])")
C=$(python3 -c "import json;print(json.load(open('latest.json'))['checksum'].split(':',1)[1])")
curl -L -o "$P" "https://grype.anchore.io/databases/v6/$P"     # 约 190 MB（2026-10-16 构建的那一份）
shasum -a 256 -c <<< "$C  $P"
# latest.json 与档案一起拷到 CI 主机
```

[B] CI 主机，以 `nexloop-ci` 身份执行：

```
C=$(python3 -c "import json;print(json.load(open('latest.json'))['checksum'].split(':',1)[1])"); P=$(python3 -c "import json;print(json.load(open('latest.json'))['path'])")
sha256sum -c <<< "$C  $P"
grype db import "$P"
grype db status -o json      # schemaVersion v6.x；built 与 latest.json 一致；valid: true；from: manual import
```

**日更作业**：

- 把上面两段做成每天一次：拉取在有网络的一侧，导入在 CI 主机。是否用定时器、谁持有下载机器，由负责人决定；
- 也可以改为给 `nexloop-ci` 放行 `grype.anchore.io`，属于 **[主机配置变更]**，然后用 `grype db update`。扫描本身仍然不会下载库，因为 `release.py` 关掉了自动更新；
- public 发布前必须确认：`grype db status` 显示的 built 距发布当天不超过 7 天。

## 5. 验证 [B]（CI 主机）

1. `uv run --frozen python -c "import sys; sys.path.insert(0,'scripts/release'); import release; print(release._tool('grype', release.pinned_tools()))"` 输出新 grype 的路径，不报版本不符。
2. 对最近一次 stage 发布目录的**副本**运行 `release.py sbom`：已签名的目录会拒绝重写。或者对下一次发布直接运行。检查结果：
   - 清单的 `scan.tools.grype` 为 `0.120.0`；
   - `scan.db` 为 v6 库的构建时间；
   - `scan.policy` 的 `waived` 含 CVE-2025-7458；
   - `listed` 中**没有**以 python 3.12.15 为包的 CVE-2025-13836。
3. 新旧发现做只读比较，只含编号、包、版本、严重级别和修复状态：

   ```
   for f in sbom/*.findings.json; do echo "== $f"; jq -c '.[] | select(.severity=="Critical" and .fix=="fixed")' "$f"; done
   ```

   整理成一页给负责人，内容与 §2 的预判对照：node 和 pgvector 基础层的阻断项。
4. 运行 `release.py public-preflight`：
   - 第 8 步的库龄检查应当通过；
   - 若存在有修复的 Critical，仍会被阻断，这是正确行为。见 §2 的结论。

## 6. 回退 [B]

- 把仓库的 `versions.lock.json` 换回 0.86.1（`replaces` 中有原值），`release.py` 的 v6 检查随之回退；
- v5 库仍在 `<cache>/5/`；
- 回退后 D12 重新无法满足。
