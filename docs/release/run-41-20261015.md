## 1. 先纠正一个前提：这些 worker 不会因为缺 Action 而退出

- **报错来源**：`published action unavailable` 由 `0008_action_definitions.sql` 的 `authz.nexloop_read_action_definition` 抛出（第 40 行），经 `authz.nexloop_read_action_bundle`（0016）由 `action_definitions.py:PostgresActionDefinitionReader.get_with_schemas` 调用。
- **六个后台 worker**（`background_services.py:run`）：每轮的异常被 `except Exception` 吞掉，等一会儿再试。只有带 `--once` 时才返回 1，而 compose 不带 `--once`。进程**只会因为循环之前的启动步骤失败而退出**：私有文件读不了、角色核对失败、launcher 构造失败、凭据认证被拒。
- **message-relay**（`message_relay_cli.py:run`）也是同样的结构。
- **所以 503 条报错只是每轮重试留下的日志，反复退出另有原因。** 最可能的原因：compose 从 `$NEXLOOP_ROOT/config/` 挂载的 7 个 JSON 文件（见 §2）在 APP_HOST 上不存在，或不是“服务私有文件”。`private_configuration.read_private_text` 要求文件属主是进程用户（10001）、权限 0600。如果宿主机上没有这个文件，Docker 会挂一个空目录进去，读取失败，进程随即退出。
- **现场核对**（APP_HOST，只读）：
  ```
  ls -l $NEXLOOP_ROOT/config/
  docker compose -p nexloop-app logs --tail 20 commitment-keeper   # 应看到固定的 "<标签> unavailable" 启动失败行
  ```

## 3. 业务对象类型与 Action 的发布：原先没有生产入口（A1，已由 §3a 解决，以下为当时的调查记录）

逐个入口查过：

- **唯一的写入路径**是 0050 受信配置清单的 `object_types`、`actions`、`functions` 字段，经 `trusted_configuration.apply_manifest_with_secrets`、以配置者身份写入（`trusted_configuration.py`，FIELDS 与 `validate_manifest`）。`business-actions.v1.json` 的 `decision` 字段也写明要走 0050。
- **构造函数存在，但不写库**：`business_object_types.trusted_object_types`（`deploy/ontology/business-object-types.v1.json`）与 `business_actions.compile_actions`（`deploy/configuration/business-actions.v1.json`，31 个业务 Action）。只有测试夹具调用它们（`tests/commitment_fixture.py:publish_commitment_type`、`tests/load_chain.py`），而且夹具是以管理员**直接插表**，不走 0050。
- **生产里调用 0050 的地方全部传空列表**：`service_grants.apply`、`stage_secrets.register`、`stage_secrets.browser`、`real_tenant_init`。
- **系统 Action 连声明文件都没有**：`nexloop.conversation.route`、`nexloop.service.request`、`NexLoop.queue.operations`、`Goal.create`、`PlanStep.create`、`MessageAssignment.create`、`Consumer.create`、`EffectControl.create`、`nexloop.plan.bind_effect_context`、`nexloop.context.bind`、`nexloop.reply.guarantee`、`nexloop.commitment.keep` 等都不在 `business-actions.v1.json` 里。测试由各夹具分别构造并插表，例如 `message_assignment_contract.message_assignment_action`，以及 `tests/test_message_relay.py:relay_plan` 读取已插入的 `Consumer.create:1`。
- **能力快照来源未定**：`compile_actions` 要求每个能力名都有一个显式的 `CapabilityContractSnapshot`。测试取自 `tests/test_postgres_action_claims.py:governance_inputs`，仓库里没有生产用的能力快照清单。
- **owner 评审不能替代首次发布**：`review_actions.py` 的 `/api/v1/workbench/review-decisions` 只能为**已存在**的类型或 Action 发布后继版本，不能播种第一版。
- **`business_setup`、`catalog_setup`、`enterprise_setup` 都要求 Action 已经发布**，它们以服务凭据经 `nexloop_api` DSN 执行。`business_setup` 的 owner 与 executor 凭据、`catalog_setup` 的 maintainer 凭据对应哪个服务主体，在 `service-grants.v1.json` 与 `stage-principals.v1.json` 中**都找不到**。

**结论**：4.1 无法在不写新代码的情况下发布合成租户的业务内容。不能用管理员直接插表（违反契约），也不能用测试夹具。需要一个设计任务，见 §6 的 A1 到 A3。
