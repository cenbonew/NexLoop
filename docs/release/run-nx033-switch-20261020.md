### 1.3 决定方案（负责人）

> **方案 L 已定**（负责人 2026-10-18）。周二按方案 L 执行，方案 P 改为 v0.1 之后的主机配置任务。§1.1 的周一检查仍然要跑，但用途改为**确认方案 L 的前提**，见 §1.4。下表保留作为背景。

| 情况 | 方案 | 说明 |
|---|---|---|
| §1.2 全部通过，**并且** CI 镜像已就绪 | **P（设计形态）** | 控制器带 `--runner`；`isolation-probe` 作为流水线阶段运行（stages v4） |
| Podman 可用但 CI 镜像未就绪 | **顺延 P，或先走 L** | 仓库里**还没有** CI 镜像的定义与构建（[本地部分实现说明](../implementation/NX-033-local-implementation.md) §4“CI 镜像的构建与固定”）。要在一个镜像里装好 PG 18、Python 3.12 加 uv、Node 24 加 pnpm 和 Pi 构建依赖，并预热缓存，开发线估计要 1–1.5 天，所以周二前来不及 |
| Podman 不可用 | **L，或顺延** | 修订 D2 需要负责人确认 |

**方案 L 的内容**：控制器 `run-once` 不带 `--runner`，以 `nexloop-ci` 用户直接运行。车道 policy 由 `lane_policy.py --without isolation-probe` 派生，与现在发布用的 CI 相同。

- 隔离靠三层：用户隔离、目录权限、按 UID 的 nft 规则；
- AT-054 的证据改由主机层探测取得：以 `nexloop-ci` 身份运行 `probe_isolation.py`，与 run-42 §3a 相同，不再是沙箱内的阶段；
- 这是对 D2（每个 job 一个 rootless 容器）的**降级**，需要负责人确认，并写进 known-risks：测试阶段不在独立网络命名空间里，只靠 nft 拦截。

这一降级已写入 [known-risks-v0.1](known-risks-v0.1.md) §4。

## 4. 5.3 同步用 deploy key（负责人 B）

1. 生成密钥对：

   ```bash
   sudo -u nexloop-git ssh-keygen -t ed25519 -N '' -C nexloop-sync -f ~nexloop-git/.ssh/github_sync
   ```

2. 负责人在 GitHub 仓库的 Settings → Deploy keys 里添加公钥 `~nexloop-git/.ssh/github_sync.pub`，**勾选 Allow write access**：同步要推送 main，只读 key 不够用。这把 key 只对本仓库有效。
3. 写同步 remote：

   ```bash
   sudo -u nexloop-git git -C <GIT_ROOT>/nexloop.git remote add github <GITHUB_SSH_URL>
   ```

   并在 `~nexloop-git/.ssh/config` 里为 GitHub 指定 `IdentityFile ~/.ssh/github_sync` 和 `IdentitiesOnly yes`。
4. 核对：

   ```bash
   sudo -u nexloop-git git -C <GIT_ROOT>/nexloop.git ls-remote github refs/heads/main
   ```

   预期打印 `<MAIN_SHA>  refs/heads/main`。

- **停止条件**：`ls-remote` 失败（出站被拦，或 key 未生效）；或者打印的 SHA 不等于 `<MAIN_SHA>`，说明有人在切换期间推了 GitHub。
- **回退**：在 GitHub 上删除这把 deploy key，删除本地的密钥文件。

## 5. 5.4 推入 main、发放公钥、改 remote（负责人 B + 调度员）

1. **推入 main**（负责人 B）。在 bare 仓库内 fetch，不经过 receive hook，所以不违反“只有控制器能写 main”：

   ```bash
   sudo -u nexloop-git git -C <GIT_ROOT>/nexloop.git fetch <GIT_REPO> <MAIN_SHA>:refs/heads/main
   ```

   核对 `git -C <GIT_ROOT>/nexloop.git rev-parse main` 等于 `<MAIN_SHA>`。
2. **发放公钥**（负责人 B）：把各推送身份的公钥按 `authorized_keys.example` 的格式加入 `~nexloop-git/.ssh/authorized_keys`，每条开发线一个身份，调度员、负责人各一个。公钥由各自在开发机上新生成，私钥不离开开发机。
3. **权限核对**（调度员 A，在开发机上）：

   ```bash
   git push <LAN_URL> HEAD:refs/heads/main
   ```

   用开发线身份执行，预期被 pre-receive 拒绝。

   ```bash
   git push <LAN_URL> HEAD:refs/heads/incoming/<identity>/switch-check
   ```

   预期被接受，并在 `<QUEUE_DIR>/pending/` 入队一项 `check`。
4. **改 remote**（每个开发机检出，调度员 A 指导各线执行）：

   ```bash
   git remote rename origin github
   ```

   ```bash
   git remote add origin <LAN_URL>
   ```

   ```bash
   git fetch origin
   ```

   pre-push hook（`scripts/ci/prepush-scan.sh`）只允许推 `origin`，所以改名后推 LAN 仓库照常扫描，推 `github` 会被拒绝。
- **停止条件**：开发线身份推 main 被接受（hook 没有生效）；或入队失败。
- **回退**：在各检出里执行 `git remote remove origin` 和 `git remote rename github origin`；把 `authorized_keys` 清空到只剩控制器。bare 仓库保留，它不影响现行车道。

第 5 项命令（CI 主机，util-linux ≥ 2.38 的 `unshare`，经 setuid 的 `newuidmap`/`newgidmap` 映射 `nexloop-ci` 的 subuid/subgid；只开用户命名空间，不开网络命名空间，所以连接从宿主网络命名空间发出）：

```bash
sudo -u nexloop-ci -- unshare --user --map-users=auto --map-groups=auto -- setpriv --reuid=1000 --regid=1000 --clear-groups -- bash -c 'sleep 60 & echo "inner pid $!"; cat /proc/self/uid_map; for t in <DATA_HOST_ADDR>:<PG_PORT> <LAN_OTHER_ADDR>:22; do timeout 5 bash -c "</dev/tcp/${t%:*}/${t#*:}" 2>/dev/null && echo "$t REACHED" || echo "$t BLOCKED"; done; wait'
```

另开一个终端核对宿主看到的 UID（应为 subuid 起点 + 1000，例如 166536，落在 `CI_SUBUID_RANGE` 内）：

```bash
ps -o uid=,cmd= -C sleep | grep 'sleep 60'
```

对照（可选，确认探测本身有效）：同一命令把目标换成公网地址（例如 `<PUBLIC_ADDR>:443`）应为 `REACHED`。若 `unshare` 不支持 `--map-users=auto`（util-linux < 2.38），改用 `podman unshare`/rootless docker 容器内的非 root 用户以 `--network host` 运行同样的 `/dev/tcp` 探测；rootless docker 的 `--network host` 是 rootlesskit 的命名空间，不是宿主，不能作为本项证据。

- **停止条件**：任何一项读到了秘密或连上了端口。立即停用控制器（`systemctl stop nexloop-ci-controller.timer`），按停止总规则处理。

### 6.2 AT-053 断连（在 §7 第一次合并之后做）

`sync` 的积压是“上次同步之后 main 新增的提交数”。main 不前进，积压就一直是 0。所以断连演练要在切换完成、能经控制器合并之后做，并且在断开期间合并一次。

1. **基线**：

   ```bash
   sudo -u nexloop-git python3 <TRUSTED_CI_DIR>/scripts/ci/nexloop_ci.py sync --repo <GIT_ROOT>/nexloop.git --queue <QUEUE_DIR> --remote github
   ```

   预期 `"status": "synced"`、`"backlog": 0`。
2. **断开**（负责人 B）：临时加一条 nft 规则，丢弃 `nexloop-git` UID 到 GitHub 的出站。规则放在 NexLoop 自己的表里，并写明注释 `at053-temporary`。
3. **断开期间**（调度员 A）：
   - 再合并一个已审的小分支：推 `integration/<name>`，先入队 `check`，通过后再入队 `merge`；
   - 然后运行 `sync`；
   - 预期：CI 和合并照常完成，main 前进一个提交；`sync` 返回 `"status": "sync_pending"`、`"backlog": 1`；`nexloop_ci.py status` 的 `sync` 中同样显示。
4. **恢复**：删除这条临时规则，再运行 `sync`。预期 `"status": "synced"`、`"backlog": 0`；`ls-remote github refs/heads/main` 等于 bare 仓库的 main。

- **停止条件**：断开期间 CI 也失败了，例如依赖阶段需要外网而缓存未命中，结果是 `dependency_unavailable`。这本身是一条真实发现，要记下来；先恢复网络，再决定后续。
- **回退**：删除临时规则，并核对 `nft list ruleset | grep -c at053-temporary` 为 0。

## 7. 5.6 完整 CI 对照与切换（负责人确认）

1. **对照**（调度员 A）：用新控制器对 `<MAIN_SHA>` 跑一次完整 CI：

   ```bash
   python3 <TRUSTED_CI_DIR>/scripts/ci/nexloop_ci.py enqueue --repo <GIT_ROOT>/nexloop.git --queue <QUEUE_DIR> --identities <PRIVATE_DIR>/identities.json --ref refs/heads/integration/switch-<日期> --sha <MAIN_SHA> --identity <integrator> --kind check
   ```

   然后用 `systemctl start nexloop-ci-controller.service` 触发一次，或直接以 `nexloop-ci` 运行 `run-once`。
   - 预期：`result --sha <MAIN_SHA>` 为 `passed`；`counts` 与现行车道对同一个 SHA 的结果一致，或者差异都能逐项解释。
   - 方案 L 的 policy 与车道相同，计数应当相等；方案 P 多一个 `isolation-probe` 阶段。
2. **切换**（负责人确认后，调度员 A）：
   1. `systemctl enable --now nexloop-ci-controller.timer` 和同步的 timer；
   2. 现行车道仓库 `<GIT_REPO>` 不再接受推 main：在它的 hook 中拒绝 `refs/heads/main`，或把仓库设为只读；保留 `refs/ci/*`，作为过渡期的发布 CI 结果来源；
   3. 在执行记录中写下切换时间与 `<MAIN_SHA>`。
3. **第一次真实合并**（调度员 A）：选一个已审的小分支，推到 `integration/<name>`，入队 `check`；通过后入队 `merge`。
   - 预期：控制器快进 main，写入合并记录，同步任务推到 GitHub；`git ls-remote github refs/heads/main` 等于新的 main。
- **停止条件**：对照 CI 失败，且原因不是已登记的 B 类基线；或者第一次合并没有快进，或同步失败但没有记为 `sync_pending`。
- **回退**：
  1. `systemctl disable --now` 控制器与同步的 timer；
  2. 恢复 `<GIT_REPO>` 推 main 的能力；
  3. 各开发机按 §5 的回退改回 remote；
  4. GitHub 上的 main 不需要回退：同步只快进，不会改写历史。

## 9. 切换后对各开发线与调度员的影响

- **开发线**：推 `origin`（LAN）的 `incoming/<identity>/<topic>`，可以自行入队 `check`。
- **调度员**：在 `integration/<name>` 上组装，入队 `check`；通过后入队 `merge`。不再从开发机推 GitHub。合并门槛仍包括 prepush-scan（`HEAD` 对 `main`）和 publication 扫描，由控制器的 `--merge-gate` 执行。
- **发布用 CI 结果**：改为直接取控制器结果目录里的 `result.json`。[NX-034-release-ci-queue](../implementation/NX-034-release-ci-queue.md) 的车道路径保留到第一次发布从新队列取得结果为止。
