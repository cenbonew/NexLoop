# 执行单 4.2“AT-058 外部探测”命令单（2026-10-15）

**适用状态**：

- 两台主机的防火墙已加载 `inet nexloop_stage` v3（含 `ct direction reply accept`），模板见 `deploy/stage/firewall/*.nft.template`；
- 两台主机的 UFW 默认策略都是 DROP；
- DATA_HOST 只经 Docker DNAT 对 APP_HOST 暴露 PG（55432）与 Valkey（56379）；
- APP_HOST 暴露以下端口：
  - Gateway 8443 与 8080；
  - 参考端点 9643；
  - pgBackRest TLS 58432，只放行 DATA_HOST。

本单只用角色名和占位符，真实地址、网段和 allowlist 写在私有 spec 里。**B** 表示需负责人确认。

## 0. 工具与报告

- **探测脚本**：`scripts/deploy/probe_isolation.py`。
  - 只用标准库，凡有 `python3` 的地方都能跑。
  - 只建连接，并只说出判定结果所需的那部分协议：
    - `tcp`：只建立连接；
    - `pg`：SSLRequest、TLS、可选 SCRAM；
    - `valkey`：TLS、可选 AUTH、PING。
  - 不发送业务数据，不修改任何东西。
- **报告**：只含位置代码、探测与目标代码、期望与实际的判定类别、原因码；不含地址、路径或秘密。
- **退出码**：0 表示全部符合期望；1 表示有不符合的探测；2 表示 spec 错误。
- **spec 样例**：`deploy/stage/probe/*.spec.example.json`，共五份。
  - 每份对应一个位置。APP_HOST 有三处：主机上的 CI 用户、应用网络、Agent Host 命名空间。
  - 复制到私有目录（0700，文件 0600）后，替换 `<...>` 占位符。
  - 端口与 `compose.*.env.example` 一致；改过端口的，按私有 env 修改。

| 位置 | spec 样例 | 运行身份与方式 | sudo |
|---|---|---|---|
| 管理机 | `management.spec.example.json` | 负责人账户，直接运行 | 否 |
| DATA_HOST | `data-host.spec.example.json` | 普通账户，直接运行 | 否（**B**：在 DATA_HOST 上运行由负责人确认） |
| APP_HOST：CI 用户 | `ci-user.spec.example.json` | 以 CI 用户身份运行（uid 1001，出站受 nft `meta skuid` 限制） | sudo-A（`sudo -u <CI 用户>`） |
| APP_HOST：应用网络 | `app-host.spec.example.json` | 一次性容器，接入 compose 的 `app` 网络 | sudo-A（docker） |
| APP_HOST：Agent Host 命名空间 | `agent-host.spec.example.json` | 一次性容器，共享运行中 agent-host 的网络命名空间 | sudo-A（docker） |

五份报告都是 `"passed": true` 才算 4.2 通过。

## 1. 管理机（不需要 sudo）

**管理机的本地代理（127.0.0.1 上的代理端口）**：
- `probe_isolation.py` 用原始 socket 连接，不读 `HTTP(S)_PROXY`，所以环境变量里的代理不影响它。为保险起见，运行时仍清掉代理变量。
- 如果代理客户端开了 TUN 或系统级透明代理，原始连接也会被接管，结果就不可信。运行前先确认去 DATA_HOST 和 APP_HOST 的路由走局域网网卡：
  ```
  route -n get <DATA_HOST_ADDR> | grep interface     # 应为局域网网卡，不是 utun*
  route -n get <APP_HOST_ADDR>  | grep interface
  ```
  如果是 `utun*`，先关闭 TUN 或增强模式，或者把这两个地址加入直连规则，然后再跑。

```
env -u http_proxy -u https_proxy -u all_proxy -u HTTP_PROXY -u HTTPS_PROXY -u ALL_PROXY \
  python3 -I scripts/deploy/probe_isolation.py --spec "$PROBE_DIR/management.spec.json" --out "$PROBE_DIR/report-management.json"
```

| 探测 | 期望 | 依据 |
|---|---|---|
| `data_pg`、`data_valkey` | unreachable | DATA_HOST 的 forward 规则只放行 APP_HOST（`data-host.nft.template` 第 11–15 行）；input 链同理（第 19 行） |
| `app_gateway_https`、`app_gateway_redirect` | reachable | 管理机在 `TRUSTED_LAN_CIDR` 内（`app-host.nft.template` 第 17 行）；不在时应为 unreachable，以私有 spec 为准 |
| `app_pgbackrest_tls` | unreachable | 只放行 DATA_HOST（第 9–10 行） |
| `app_reference_endpoint` | reachable | 参考端点经 DNAT 发布在 APP_HOST 地址上（`reference-endpoint/compose.example.yaml`），nft 没有针对它的规则，UFW 管不到 DNAT。**B**：如果负责人要求参考端点只让 effect worker 访问，就把期望改为 unreachable，并为它补一条 `ct original proto-dst` 规则，那是另一项变更 |
| `app_api_internal`、`app_host_control`、`app_guard` | unreachable | 这三个端口只监听 loopback 或容器内网络，没有发布到主机地址 |

## 2. DATA_HOST（不需要 sudo，B）

把脚本与 spec 拷到 DATA_HOST 的私有目录（`scp`），然后以普通账户运行：
```
python3 -I "$PROBE_DIR/probe_isolation.py" --spec "$PROBE_DIR/data-host.spec.json" --out "$PROBE_DIR/report-data-host.json"
```

| 探测 | 期望 | 依据 |
|---|---|---|
| `app_pgbackrest_tls` | reachable | repo1 的 pgBackRest TLS 只放行 DATA_HOST（`app-host.nft.template` 第 9 行），这是正向用例 |
| `app_gateway_https` | reachable | 前提是 DATA_HOST 在 `TRUSTED_LAN_CIDR` 内；不在时改为 unreachable |
| `app_api_internal`、`app_host_control`、`app_guard` | unreachable | 同管理机 |

DATA_HOST 上 PG 与 Valkey 自身的身份类负例（TLS、客户端证书、错误口令）都放在 APP_HOST 应用网络那一份里，因为只有从 APP_HOST 才能连上这两个端口。

## 3. APP_HOST

先在 APP_HOST 上准备一个私有目录 `$PROBE_DIR`（0700，属主 10001），放入以下文件：
- `probe_isolation.py`；
- 三份 spec；
- 应用网络探测用到的凭据副本，权限 0600，属主 10001：
  - `api` 的 PG 客户端证书与私钥（来自 `secrets/api-1/`）；
  - PG 的 CA；
  - `api` 的口令；
  - cache 用户的 Valkey 客户端证书、私钥与口令；
  - 一个内容随意的 `wrong-password`。

这些都是现有秘密树中的文件，只读复制，探测后用 `shred -u` 删除。

### 3a. CI 用户（sudo-A）

```
sudo -u <CI 用户> python3 -I "$PROBE_DIR/probe_isolation.py" --spec "$PROBE_DIR/ci-user.spec.json" --out /tmp/report-ci-user.json
```
CI 用户需要能读 `$PROBE_DIR` 下的脚本和这份 spec：单独拷一份到它可读的目录，不要放宽 `$PROBE_DIR` 的权限。

| 探测 | 期望 | 依据（`app-host.nft.template` output 链） |
|---|---|---|
| `data_pg`、`data_valkey` | unreachable | 第 39 行：`meta skuid <CI_UID> ip daddr <DATA_HOST_ADDR> drop` |
| `gateway_loopback` | unreachable | 第 40 行：CI 用户访问 loopback 上的内部端口与 Gateway 端口一律丢弃 |
| `pgbackrest_tls` | unreachable | 第 41 行 |

### 3b. 应用网络（一次性容器，sudo-A）

```
sudo docker run --rm --network nexloop-app_app --user 10001:10001 --read-only --cap-drop ALL --security-opt no-new-privileges \
  -v "$PROBE_DIR:/probe:ro" --entrypoint python3 "$BACKEND_IMAGE" -I /probe/probe_isolation.py --spec /probe/app-host.spec.json \
  > "$PROBE_DIR/report-app-host.json"
```
- `$BACKEND_IMAGE` 取发布清单里 backend 的完整 digest，按 digest 引用，不按标签拉取。
- 网络名是 compose 项目名加 `_app`，以 `docker network ls` 为准。

| 探测 | 期望 | 依据 |
|---|---|---|
| `pg_ok` | authenticated | 正向：TLS、verify-full、`api` 客户端证书与 SCRAM |
| `pg_plaintext` | server_refused | 服务端只接受 TLS（pg_hba `hostssl`） |
| `pg_no_client_cert` | server_refused | 服务端要求客户端证书 |
| `pg_wrong_password` | auth_failed | SCRAM 校验失败 |
| `valkey_ok` | pong | 正向：TLS、客户端证书与 ACL 用户 |
| `valkey_default_user` | acl_refused | default 用户被禁用 |
| `valkey_plaintext` | server_refused | 只开放 TLS 端口 |
| `data_other_port` | unreachable | 应用网络只放行 DATA_HOST 的 PG 与 Valkey 两个端口（第 24–25 行） |
| `model_from_application_namespace` | unreachable | 应用网络不能访问模型地址（第 23 行，NX-037 D4） |
| `unlisted_external` | unreachable | 应用网络的其他新连接一律丢弃（第 25 行） |

### 3c. Agent Host 命名空间（一次性容器，sudo-A）

一次性容器共享运行中 agent-host 容器的网络命名空间，不进入 agent-host 容器本身，也不挂载它的任何文件：
```
AGENT=$(sudo docker compose -p nexloop-app ps -q agent-host)
sudo docker run --rm --network "container:$AGENT" --user 10001:10001 --read-only --cap-drop ALL --security-opt no-new-privileges \
  -v "$PROBE_DIR/probe_isolation.py:/probe/probe_isolation.py:ro" -v "$PROBE_DIR/agent-host.spec.json:/probe/agent-host.spec.json:ro" \
  --entrypoint python3 "$BACKEND_IMAGE" -I /probe/probe_isolation.py --spec /probe/agent-host.spec.json > "$PROBE_DIR/report-agent-host.json"
```
这份 spec 不需要任何凭据文件，只挂载脚本和 spec。

| 探测 | 期望 | 依据 |
|---|---|---|
| `model_allowlisted_1`、`model_allowlisted_2` | reachable | agent egress 只放行 allowlist 的 443（第 34 行） |
| **`data_pg_from_agent`、`data_valkey_from_agent`** | **unreachable** | **负例一**：Agent Host 不能连 DATA_HOST（第 33 行） |
| **`unlisted_target_from_agent`** | **unreachable** | **负例二**：不能连非 allowlist 地址（第 35 行） |
| `guard_via_relay` | reachable | agent-link-relay 把 127.0.0.1:GUARD_PORT 转发到应用侧的 guard |
| `api_not_relayed` | unreachable | relay 只承载 guard 一条链路，API 不在其中 |

`<UNLISTED_EXTERNAL_ADDR>` 选一个确定不在 allowlist 里、且通常能连通的公网地址的 443 端口，例如一个公共 DNS 服务的 443。这样“不通”只能归因于规则；不要选本身就不响应的地址。

## 4. 收尾

1. 汇总五份报告：
   ```
   for f in report-*.json; do python3 -c 'import json,sys;r=json.load(open(sys.argv[1]));print(sys.argv[1],r["passed"],[x["probe"] for x in r["results"] if not x["passed"]])' "$f"; done
   ```
   每份都要是 `True` 且失败列表为空。
2. 报告只含代码，可以附进 4.2 的证据。私有 spec 和凭据副本不入证据：
   ```
   shred -u "$PROBE_DIR"/*password* "$PROBE_DIR"/*.key
   rm -r "$PROBE_DIR"
   ```
3. **撤销**：探测只读，没有需要撤销的东西。
4. **不符合时**：
   - 先看 `reason`，它说明的是不通的方式，比如 `timeout` 一般是被丢弃，`refused` 是端口没在监听；
   - 再对照上表依据里的规则行。
   - 改防火墙规则另起变更单，不在 4.2 内进行。

## 5. 与模拟的差异

`scripts/deploy/netns_sim/run.py:probe_specs` 是同一套判定在模拟环境里的版本，那里有五个位置：app、agent、neighbour、outsider、host。本单与模拟的差异：
- 模拟里的 `LAN_NEIGHBOUR`（同网段非 APP_HOST）在真实部署中由管理机承担，它的身份类负例由应用网络那份覆盖；
- 真实部署多了三类目标：pgBackRest TLS、参考端点，以及 Gateway 的 8080 跳转端口。
