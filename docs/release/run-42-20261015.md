## 6a. 防火墙表持久化 G-NFT-PERSIST（两台主机；B；APP_HOST sudo-A，DATA_HOST sudo-D）

**缺口**：
- 两台主机的 `inet nexloop_stage` 表都只在内存里：`nftables.service` 为 disabled，也没有规则文件。
- 主机一重启，隔离规则就全部消失，而 Docker 会照常拉起 Compose 容器（`restart: unless-stopped`）。

**修复**：`deploy/stage/systemd/nexloop-nft.service.example`，加上 `render.py --nft-transaction`。
- **unit 形态**：oneshot、RemainAfterExit，在 `docker.service` **之前**加载，并以 `RequiredBy=docker.service` 挂在 Docker 上。
  - **为什么排在 Docker 之前**：若排在 Docker 之后，Docker 会先按重启策略拉起容器，在规则加载之前容器就已经在无隔离状态下运行。这张表与 Docker 的表、链和接口无关（只匹配地址与连接状态），所以可以先加载。
  - **失败即停**：加载失败（包括文件缺失，用的是 `AssertPathExists`）时 Docker 不启动，容器也就不会在没有规则的情况下运行。
- **加载文件**是一个事务：`table` + `delete table` + `include <渲染后的规则>`，原子地只替换这一张表，不碰 UFW、Docker 的表。
- `reload` 用同一个文件，同样是原子的；`stop` 只删除这张表。

每台主机执行一次。`<host>` 为 `app-host` 或 `data-host`。

1. **目录**：在根文件系统上，**不在** LUKS 卷上，开机时卷还没解锁。
   ```
   sudo install -d -o root -g root -m 0700 $NEXLOOP_ROOT/config/firewall
   ```
2. **渲染规则**：用该主机的私有 `stage.env` 与发布检出中的模板。它必须与当前已加载的规则来自同一份 env 和模板（APP_HOST 需含 §7 之后的模板）。
   ```
   scripts/deploy/render.py --env <stage.env> --template deploy/stage/firewall/<host>.nft.template --out <tmp>/<host>.rules.nft
   sudo install -o root -g root -m 0600 <tmp>/<host>.rules.nft $NEXLOOP_ROOT/config/firewall/<host>.rules.nft
   scripts/deploy/render.py --nft-transaction $NEXLOOP_ROOT/config/firewall/<host>.rules.nft --out <tmp>/<host>.nft
   sudo install -o root -g root -m 0600 <tmp>/<host>.nft $NEXLOOP_ROOT/config/firewall/<host>.nft
   shred -u <tmp>/<host>.rules.nft <tmp>/<host>.nft
   ```
3. **只检查不加载**：`sudo nft -c -f $NEXLOOP_ROOT/config/firewall/<host>.nft`，退出码必须为 0。
   - 仓库的同一检查是 host check `tests/host_checks/nft_check.py`，用示例 env 渲染两台主机的规则并做 `nft -c`。它不在默认测试收集中：CI 用户没有 CAP_NET_ADMIN，而发布门槛不允许任何 skip。
   - 要在主机上以 root 显式运行，在发布检出目录里执行：
     ```
     sudo env PYTHONPATH=packages/eios-core/src python3 -m pytest -q tests/host_checks/nft_check.py
     ```
   - 预期 `2 passed`。没有 nft 或没有权限时它会**失败**，不会 skip。
   - 主机若没有 pytest，只做上面的 `nft -c` 即可。
4. **记下现状**：`sudo nft list table inet nexloop_stage | sha256sum`，以及规则条数 `sudo nft list table inet nexloop_stage | grep -c -E 'accept|drop'`。
5. **安装 unit**：
   - 把 `<NEXLOOP_ROOT>`、`<host>` 填入后，放到 `/etc/systemd/system/nexloop-nft.service`（root，0644）；
   - 然后执行：
   ```
   sudo systemd-analyze verify /etc/systemd/system/nexloop-nft.service
   sudo systemctl daemon-reload
   sudo systemctl enable nexloop-nft        # 同时建立 docker.service 的 RequiredBy 链接
   sudo systemctl start nexloop-nft         # 原子替换为文件中的同一套规则
   ```
6. **核对**：
   - `systemctl is-active nexloop-nft`：`active`；
   - `systemctl is-enabled nftables`：`disabled`，不得启用，因为它默认的配置文件以 `flush ruleset` 开头；
   - `systemctl list-dependencies --reverse nexloop-nft` 中含 `docker.service`；
   - 第 4 步的条数不变。规则文本中的 handle 等可能不同，以条数和第 3 步为准；
   - 重跑本单 §1–§3 的探测，结果与加载前一致。
7. **重启演练**（可选，放在维护窗口，与 OPERATIONS 8a.1 一起）：重启后、LUKS 解锁之前执行 `sudo nft list table inet nexloop_stage`，表应已存在。
- **改规则以后**：重新执行第 2–3 步（输出文件已存在时先 `shred -u` 旧文件），然后 `sudo systemctl reload nexloop-nft`。不要 `restart`：`restart` 会先删表再加载。
- **撤销**：
  - `sudo systemctl disable nexloop-nft`，**不带** `--now`，这样内存中的表保留；然后删除 unit 文件并 `daemon-reload`；
  - `stop` 会删除这张表，只在两个 Compose 项目都已停下时执行。

## 7. 修复 G-APP-SUBNET：应用网络固定子网（APP_HOST；B，sudo-A）

**缺口**：
- 4.2 外部探测（§3b）发现，`compose.app.example.yaml` 的 `networks: app: {}` 没有固定子网，Docker 自行分配了一个子网。
- 而 `app-host.nft.template` 第 28–30 行按 `__APP_CONTAINER_CIDR__` 匹配应用网络，三条规则因此全部落空。
- 实测应用网络能连模型地址的 443 和 DATA_HOST 的 22，NX-037 D4 被破坏；
- 复测中，应用网络还能连**任意外网的 443**：以 APP_HOST 本机可达的公共地址作对照，应用网络内同样能连上。原因相同：第 30 行的 `ct state new drop` 同样按该 CIDR 匹配，因此也落空。
- 另外三个网络（effect_egress、agent_egress、agent_link）一直是固定子网。

**修复**（`l3/app-subnet`）：
- compose 的 `app` 网络改为 `ipam.config[].subnet = ${APP_CONTAINER_CIDR:?}`；
- `compose.app.env.example` 增加 `APP_CONTAINER_CIDR`，值必须与 `stage.env` 相同；
- 守护测试 `tests/test_deploy_render.py::test_every_container_cidr_of_the_app_firewall_is_a_fixed_compose_subnet`：nft 模板中每个容器源 CIDR 都必须是某个 compose 网络的固定子网；
- 部署闸门增加两项：`compose_networks_match_firewall`（渲染后的 compose）与 `running_networks_match_firewall`（运行中的网络，来自 `running_snapshot`）。

**停机影响**：网络的子网不能原地修改，必须 `docker compose down`（不带 `-v`）后重建。期间 APP_HOST 的全部服务都会停止：Gateway、两个 API、所有 worker、agent-host。
- WebChat 与工作台不可用；
- 已受理的消息、队列与效应都在 PG 中（先持久化再 ACK），重启后由 worker 继续处理；进行中的 Run 按租约到期后的既有路径处理；
- DATA_HOST 不受影响；
- 数据目录都是 `$NEXLOOP_ROOT` 下的绑定挂载，秘密以文件挂载，`down` 不带 `-v` 时都不受影响；
- 估计停机 5–10 分钟，不含排障。安排在没有交互的时段，并通知负责人。

### 7.1 准备（不停机）

1. **选定子网**：`stage.env` 中已有的 `APP_CONTAINER_CIDR`，即 nft 规则已经在用的值。
   - 核对它不与 APP_HOST 上其他 Docker 网络、宿主机路由或局域网重叠：
     ```
     sudo docker network ls -q | xargs sudo docker network inspect -f '{{.Name}} {{range .IPAM.Config}}{{.Subnet}} {{end}}'
     ip route
     ```
   - 地址只看不记，不进证据。
2. **私有 env**：在 `$NEXLOOP_ROOT/config/compose.app.env` 中加一行 `APP_CONTAINER_CIDR=<同 stage.env 的值>`（sudo-A，B）。
3. **compose 文件**：把发布检出中修复后的 `deploy/stage/compose.app.example.yaml` 放到 `$NEXLOOP_ROOT/compose.app.yaml`。原文件先备份为 `compose.app.yaml.before-app-subnet`。
4. **渲染核对**（不改运行状态）：
   ```
   sudo docker compose -p nexloop-app -f $NEXLOOP_ROOT/compose.app.yaml --env-file $NEXLOOP_ROOT/config/compose.app.env \
     --env-file $NEXLOOP_ROOT/config/compose.images.env config --format json > "$GATE_DIR/compose.json"
   python3 -c 'import json,sys;print(json.load(open(sys.argv[1]))["networks"]["app"]["ipam"]["config"])' "$GATE_DIR/compose.json"
   ```
   - 第二条输出的子网必须等于 `APP_CONTAINER_CIDR`。
5. **nft 规则**：确认已加载的表中含有该 CIDR，因为规则本身不需要改。若 §6a 已完成，还要确认持久化文件 `$NEXLOOP_ROOT/config/firewall/app-host.rules.nft` 由同一份 stage.env 渲染（`grep -c` 同样为 3），这样重启后加载的也是同一套规则：
   ```
   sudo nft list table inet nexloop_stage | grep -c "ip saddr <APP_CONTAINER_CIDR>"
   ```
   - 应为 3（第 28–30 行）。
6. **记录现状**：现在运行中的应用网络子网，用于对比，不进证据：
   ```
   sudo docker network inspect -f '{{range .IPAM.Config}}{{.Subnet}}{{end}}' nexloop-app_app
   ```

### 7.2 停机重建（B，sudo-A）

```
sudo docker compose -p nexloop-app -f $NEXLOOP_ROOT/compose.app.yaml --env-file $NEXLOOP_ROOT/config/compose.app.env \
  --env-file $NEXLOOP_ROOT/config/compose.images.env down          # 不带 -v
```

- 如果网络仍在，通常是还有容器接在上面，例如本单 §3b 或 run-assembly 的一次性容器。

  - 不要用 `docker network prune`。
- 确认为空后启动：

```
  --env-file $NEXLOOP_ROOT/config/compose.images.env up -d
```

### 7.3 核对

1. **运行中的子网**：
   ```
   sudo docker network inspect -f '{{range .IPAM.Config}}{{.Subnet}}{{end}}' nexloop-app_app
   ```
   - 必须等于 `APP_CONTAINER_CIDR`。effect_egress、agent_egress、agent_link 三个网络同样核对。
2. **服务状态**：`sudo docker compose -p nexloop-app ps`，全部服务 running，不再重启。
3. **部署闸门**（run-34 §4.7）：
   - 用新代码的 `running_snapshot.py` 重新生成 `running.json`，它现在会记录项目网络的子网；
   - 运行 `nexloop-doctor --deploy-gate`，以下两项必须为 true，其余项照旧：
     - `compose_networks_match_firewall`；
     - `running_networks_match_firewall`。
   - doctor 来自发布镜像。镜像中的 `deploy_checks` 还没有这两项，所以本次要像 run-41 §3a.1 那样，挂载 main 源码树并让 PYTHONPATH 优先。
4. **重跑探测**：重跑 §3b（应用网络）与 §3c（Agent Host 命名空间）。`<UNLISTED_EXTERNAL_ADDR>` 先按 §3c 下方做本机阳性对照。应用网络的以下几项必须为 `unreachable`：
   - `model_from_application_namespace`；
   - `data_other_port`，其中包括 DATA_HOST 的 22；
   - `unlisted_external`。
   - 正向的 `pg_ok`、`valkey_ok` 仍须通过。
   - 两份新报告附进 4.2 证据，旧报告标为“修复前”。
5. **业务冒烟**：WebChat 与工作台都能登录；message-relay 与 runtime-worker 日志只有 ready 行。
6. **持久化**：若 §6a 尚未完成，接着做 §6a，否则重启后本节的隔离会随表一起消失。

### 7.4 撤销

- 只在新子网无法启动时才撤销，例如与宿主机路由冲突。
- 步骤：
  1. `down`；
  2. 恢复 `compose.app.yaml.before-app-subnet`，并去掉 env 中的 `APP_CONTAINER_CIDR`；
  3. `up -d`。
- **注意**：撤销会恢复缺口，即应用网络不受 nft 约束。所以撤销后必须停掉需要隔离的服务，至少 agent-host 与各 worker，或者改选一个不冲突的 CIDR，同时修改 `stage.env` 和 nft 规则，另起变更单。
