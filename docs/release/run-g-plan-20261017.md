# 命令单：G-PLAN / G-ROLE-READ 在 stage 上的应用（2026-10-17 编写，AT-015 之后执行）

本单让 plan-reevaluator 在 stage 上有计划可复评，并能发起 Role Run。依据是本地 PG 测试 `tests/test_plan_setup_stage_pg.py`：该测试按 stage 方式组装租户（register → business/catalog/enterprise → relay 登记 → 角色组装），再依次执行本单第 3–6 步，plan-reevaluator 的 stage 命令（`--once`）首轮结果为 `launched: 1`。缺口说明见 [assembly-dryrun-gaps](assembly-dryrun-gaps.md) 中的 G-PLAN、G-ROLE-READ、G-ROLE-CATALOG、G-GOAL。

- 只用角色名与参数，不写主机名、地址、口令或令牌。
- 约定沿用 [run-assembly-20261015](run-assembly-20261015.md)：
  - **B** 表示改动服务器、凭据或数据，每一步都要负责人确认；
  - **sudo-A** 表示 APP_HOST 上由负责人本人输入 sudo；
  - **sudo-D** 表示 DATA_HOST 上由负责人本人输入 sudo；
  - 变量（`TENANT_ID`、`WORKBENCH_APPLICATION_ID`、`RUN`、`APP_RUN`、`NEXLOOP_ROOT`、`KEY_ID`）、两种一次性容器（`$COMMON` / `$WINDOW`、`$APPTOOL` / `$BACKEND`）和源码树分发同 run-assembly §0.2–§0.4。
- **证据性质**：本单所有“预期”都来自本地测试，不是 stage 结果。stage 结果只记在私有证据里（§9）。

## 0. 前提

- 本分支已由调度员合入 main，记为 `$MAIN`。迁移 `0205_nx032_role_source_read.sql` 是临时编号，合入时可能重编号，下文的“0205”指合入后的编号。
- 该迁移已随发布进入 stage 的镜像。没有进入时，本单在 §1 停下。
- 每个消费者 `<C>` 都已完成 run-assembly 的 §6（business、catalog、enterprise）、§7（`role_assembly`）和 §8（relay 登记），并有以下输出：`consumer_id`、`control_id`、`role_id`、`link_id`、`step_id`。
- owner 已有 workbench 账号，并已发布 Context 策略：run-assembly 中的 `workbench_roles --apply` 和 `context_strategy_setup` 两步，输出 `strategy_ref = context-strategy:recent_plus_required@1`。
- **对消息 Run 路径的影响**：0205 只在两个读授权入口加了一个分支：`derivation = 'role-source-v1'` 时转给新函数，其余原样交给前一版本；`property_access_basis` 在前一版本已返回 derived 时直接返回。relay Source 的派生读取不经过新代码。本地回归覆盖了 relay 派生、消息 Run 与 Context 来源（§9 的测试清单）。

## 3. role_source 的目录（APP_HOST，每个消费者一次；**B**，sudo-A）

**G-ROLE-CATALOG**：Role Context 要求目录 binding 的 `source_principal` 就是 Run 的 Source（`service_offerings.read_catalog`）。run-assembly §6.2 建的 binding 指向 relay_source，所以再用现有的 `catalog_setup` 建一份：maintainer 不变，Source 换成 role_source。

- 凭据：`$NEXLOOP_ROOT/secrets/plan-reevaluator/source-credential` 就是 role_source 的令牌。复制到 `$APP_RUN/in/role-source-credential`，属主 10001，权限 0600。
- 配方：用 `catalog-recipe.example.json` 填一份，`request_id` 用新 UUID，不能与 §6.2 重复。

```
docker run $APPTOOL "$BACKEND_IMAGE" -m nexloop_eios.catalog_setup $BACKEND --maintainer-credential-file /in/catalog-maintainer-credential \
  --source-credential-file /in/role-source-credential --recipe-file /in/catalog-role-<C>.json
```

- **预期**：`source_ref = principal:nexloop-service-role-source-principal`，并输出新的 `offering_id`、`binding_id`。同一配方再执行一次，返回相同的 ID。
- **撤销**：同 run-assembly §6，经受治理 Action 停用，不删除。

## 4. NX-022 目标版本（APP_HOST，每个租户一次；**B**，sudo-A）

**G-GOAL**：计划必须引用一个当前的 NX-022 目标版本，而 stage 上原来没有发布目标的入口。`nexloop_eios.goal_setup` 由 owner 以自己的 workbench 会话执行 `Metric.approve` 和 `Goal.publish`，登录方式同 `context_strategy_setup`：用户名和口令都从私有文件读取，不进参数，不打印。

- 配方由 `goal-setup.example.json` 填出：
  - 两个 `request_id` 各取一个新 UUID，固定后重放时用同一个；
  - 目标 ID、目标文本、指标、KR 由负责人定；
  - 时间用 UTC，`period_end` 为试运行期末。

```
docker run $APPTOOL "$BACKEND_IMAGE" -m nexloop_eios.goal_setup --recipe /in/goal-setup.json $BACKEND \
  --identity-database-url-file /run/secrets/api_identity_dsn --username-file /in/owner-username --password-file /in/owner-password \
  --browser-rate-key-file /run/secrets/api_browser_rate_key --browser-origin "$WORKBENCH_ORIGIN"
```

- **预期**：`goal_version_ref = goal:<goal_id>@1`，`metric_replayed: false`，`goal_replayed: false`。再执行一次，两个值都是 `true`。
- **拒绝**：退出码 2。`no grant on the Action` 表示该账号不是 owner 成员；`owner login refused` 表示用户名或口令不对。

## 5. 建立计划（APP_HOST，每个消费者一次；**B**，sudo-A）

**G-PLAN**：`nexloop_eios.plan_setup` 以 plan_reevaluator 自己的身份建立计划：DSN 用 `nexloop_domain_worker`，凭据用 `plan-reevaluator/service-credential`。计划设置取自 plan-reevaluator 挂载的同一个 `config/plan-reevaluation.json`。

### 5.1 配方

配方由 `plan-setup.example.json` 填出：

| 键 | 值 |
|---|---|
| `plan_id` | 新 UUID；它是稳定意图，重放时不改 |
| `consumer_id`、`recipe.control_id` | run-assembly §6.1 的输出 |
| `recipe.role_id`、`link_id`、`step_id` | §7 的输出 |
| `recipe.offering_id`、`binding_id` | 本单 §3 的输出，不是 §6.2 的 |
| `goal_version_ref` | 本单 §4 的输出 |
| `context_strategy_ref` | `context_strategy_setup` 的 `strategy_ref` |
| `steps[0].reassess_at` | 建立后约 5 分钟（UTC）。SQL 把到期时间取为 `max(reassess_at, 建立时刻 + 60 s)` |
| 步骤预算 | 示例值 4 / 8 / 120，不得超过角色组装 ceiling 的 8 / 8 / 120 |

步骤预算超过 ceiling 时，每次发起都会被 Role 签发拒绝，计划会反复 retry。

### 5.2 执行

```
S=$NEXLOOP_ROOT/secrets
PLANTOOL="--rm --network container:$APP_NET --read-only --user 10001:10001 --cap-drop ALL --security-opt no-new-privileges \
  --tmpfs /tmp:rw,noexec,nosuid,size=16m --tmpfs /work:rw,noexec,nosuid,size=16m,uid=10001,gid=10001 \
  -v $APP_RUN/src:/opt/release:ro -v $APP_RUN/in:/in:ro -e PYTHONPATH=/opt/release/packages/eios-core/src \
  -v $S/plan-reevaluator/dsn:/run/secrets/plan_reevaluator_dsn:ro -v $S/plan-reevaluator/pg-client.crt:/run/secrets/plan_reevaluator_pg_client_cert:ro \
  -v $S/plan-reevaluator/pg-client.key:/run/secrets/plan_reevaluator_pg_client_key:ro -v $S/plan-reevaluator/service-credential:/run/secrets/plan_reevaluator_credential:ro \
  -v $S/shared/db-ca.crt:/run/secrets/pg_ca:ro -v $S/shared/signing.key:/run/secrets/signing_key:ro \
  -v $NEXLOOP_ROOT/config/plan-reevaluation.json:/etc/nexloop/plan-reevaluation.json:ro --entrypoint python"
docker run $PLANTOOL "$BACKEND_IMAGE" -m nexloop_eios.plan_setup --database-url-file /run/secrets/plan_reevaluator_dsn \
  --signing-key-file /run/secrets/signing_key --signing-key-id $KEY_ID --artifact-root /work/artifacts \
  --service-credential-file /run/secrets/plan_reevaluator_credential --settings-file /etc/nexloop/plan-reevaluation.json --recipe-file /in/plan-<C>.json
```

- 挂载路径与 compose 中 plan-reevaluator 的 `/run/secrets/<secret>` 一致，因为 DSN 文本里写的就是这些路径。

### 5.3 预期与拒绝

- **预期**：`{"established":true,"replay":false,"version":1,...}`。同一配方再执行一次，`replay: true`。
- **拒绝**：退出码 1，原因写在 stderr：
  - `goal version superseded`：目标版本不是当前版本；
  - `plan refused`：形状不对，或 Context 策略没有发布；
  - `plan id reused with a different recipe`：同一 plan_id 用了不同的 recipe；
  - `plan port refused`：凭据不是 plan_reevaluator；
  - `nexloop_domain_worker role required`：DSN 用错了角色。

## 6. plan-reevaluator 首轮发起 Role Run（只读观察；发起本身是 **B**）

stage 上的 plan-reevaluator 已经常驻（compose，`--tick-seconds 2`），计划到期后自动认领。有两种到期方式：

- 等 §5 的 `reassess_at` 到期；
- owner 在 workbench 上点“手动复评”（`request_plan_reevaluation`），计划立即到期。

**发起前由负责人确认**：Role Run 用 `deepseek-flash`，会产生真实模型调用，每个 Run 不超过 2 CNY（plan-reevaluation.v2）。Run 可能提出 `nexloop.service.request` 意图，它照常受三层真实派发开关、EffectControl 预算和联系约束限制。不想发起时，owner 可以先用 `Control.set` 暂停该消费者，这样 precheck 返回 `paused`，不调用模型。

- **预期**（日志里每轮的计数）：`launched` 加 1；该计划的 feed 项被消费，不处于 retry。
- **失败时**：feed 的 `last_code` 是：
  - `reevaluation_failed`：发起时被拒，按 §7 的查询定位：没有 Run 凭据，说明 READ 或 ceiling 被拒；有 Run 但没有 pack，说明目录或 Context 被拒；
  - `denied`：授权被拒。

  都不重试绕过，报调度员。

**预期**（本地测试值）：

- 每个计划有 1 个 Run；
- `allowed_resources = {eios:action:nexloop.service.request:1}`；
- 策略绑定 1 条，Context pack 1 个；
- runtime job 的队列是 `operations`，预算为 4 / 8 / 120 / 2.00 CNY。

## 8. 撤销与限制

- **停止某个计划的发起**：
  - owner 在 workbench 暂停该消费者（`Control.set`），precheck 返回 `paused`；
  - 或由 plan_reevaluator 端口把计划 mark 为 `invalidated` / `closed`（目前没有 CLI，本地测试用的是同一端口）。

  计划不再是 active 后，role_source 对这些对象的派生 READ 在下一次读取时就失效（`test_role_source_reads_only_the_objects_of_an_active_plan`）。
- **规则的收回**：`register` 只写 `active: true`。从 stage-principals 删除这一段不会让库中的规则失效。要停用，需新增一条 `active: false` 的写入，属后续改动，本单不提供。在此之前，没有 active 计划就没有任何派生。
- **目录、目标和计划都不删除**，只能经受治理 Action 停用。目标的新版本以 `expected_current_version` 递增发布。
